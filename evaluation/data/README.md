# Fraud Golden Set v0.1

## 출처와 권리

- `fraud_golden_v0.1.jsonl`은 FinShield 팀이 2026-08-13 직접 작성한 합성 문장이다.
- 실제 피해자 메시지, 개인정보, 외부 데이터셋 문장을 복사하지 않았다.
- 외부 데이터 라이선스나 재배포 권한에 의존하지 않는다.
- `synthetic: true`가 아닌 사례는 v0.1 로더가 거부한다.

## 라벨 계약

각 줄은 독립 JSON 객체이며 다음을 포함한다.

- `case_id`: 변경되지 않는 `fg-NNN` 식별자
- `text`, `persona`, `state`, 선택적 `url`: API 입력
- `is_fraud`, `expected_fraud_types`: 이진·유형 라벨
- `required_signal_codes`: 반드시 노출돼야 하는 public signal
- `expected_min_risk`: 최소 위험 등급
- `required_action_codes`: 사용자 상태상 반드시 필요한 행동
- `annotation_note`: 판정 이유와 경계 조건

라벨의 사기 유형·행동 코드는 실제 API 계약에 존재해야 하고 중복될 수 없다.
모든 `UserState`가 포함돼야 하며 사례 ID는 유일해야 한다.
평가 결과에는 순서와 라벨을 포함한 정규화 사례의 SHA-256을 기록해 어떤 데이터로
측정했는지 식별한다.

## 이용 한계

이 데이터는 합성 61건의 bootstrap 개발셋이며 독립 held-out 테스트셋이 아니다.
각 `UserState`는 최소 3건을 포함하지만 `received_only`가 43건으로 많아 균형
표본은 아니다. 엔진 오류를
확인하고 규칙을 수정하는 데 사용했으므로 이 결과를 실서비스 탐지 성능이나
일반화 성능으로 주장하면 안 된다. v0.2는 이 파일을 동결한 뒤 별도 작성자 검수와
미사용 held-out 표본을 추가한다.

# Injection Golden Set v0.1

`injection_golden_v0.1.jsonl`. 로더는 `evaluation/injection_golden.py`.

## 무엇이 다른가

**사기 골든셋은 판정을 잰다. 이쪽은 경계를 잰다.** 묻는 것이 "이 문자가 사기인가"
가 아니라 "이 문자에 심긴 지시가 프로바이더까지 도달하는가" 이고, 그 질문은 모델을
부르지 않고 답할 수 있다. 그래서 이 셋의 검사는 CI 에서 돈다
(`tests/test_llm_prompt_injection.py`). **유료 호출이 없다.**

모델이 실제로 지시를 따르는지는 별개의 유료 측정이며, 날짜와 모델을 붙여
`docs/devlog/2026-08-20/prompt-injection-boundary.md` 에 남긴다. 그 숫자를 여기
두면 CI 가 매번 돈을 쓰거나, 낡은 숫자가 테스트인 척하게 된다.

## 라벨 계약

- `case_id`: `pi-NNN`
- `technique`: `direct_override` · `role_assignment` · `english_mixed` ·
  `delimiter_forgery` · `verdict_forgery` · `developer_impersonation` ·
  `output_pinning`
- `text`: 주입 문장이 섞인 문자 원문
- `injected_fragment`: **프로바이더까지 가면 안 되는** 조각
- `evidence_fragment`: **반드시 남아야 하는** 조각. 이쪽이 사라지면 설명이 근거를
  잃는다
- `expected_min_risk`, `note`

두 fragment 는 로더가 `text` 안에 실제로 있는지 검사한다.

## 출처와 권리

FinShield 팀이 2026-08-20 직접 작성한 합성 문장이다. 실제 피해자 메시지나 외부
데이터셋을 복사하지 않았다.

## 이용 한계

7건짜리 개발셋이다. held-out 아니고, 기법 목록이 완전하지도 않다. 실제로 첫
실행에서 3건(`pi-005`·`pi-006`·`pi-007`)이 뚫렸고 그만큼 패턴을 넓혔다 — 즉 이 셋은
**현재 방어를 교정하는 데 쓴 셋**이므로 통과율을 방어 성능으로 주장하면 안 된다.

`pi-004`(구획 위조)는 입력 계층이 **의도적으로 막지 않는다.** 명령문이 아니라
평서문이라 잡으려면 "금융감독원" 이 든 문장을 지워야 하고, 그러면 금융감독원을
사칭한 실제 사기 문자를 통째로 지운다. 이 건은 `validation.py` 의 근거 이탈 검증이
받는다.

> **2026-08-20 갱신.** `pi-002`의 결정론 판정이 `low` 였던 것은 주입과 무관한
> **탐지 공백**이었고 `docs/32` 소관으로 넘겼다. v0.3 엔진 수정에서 은행 자칭
> 어휘를 요구 조건과 함께 넣으면서 `medium` 으로 올라갔고, 골든 레이블도 그에
> 맞춰 고쳤다. 이 셋의 `expected_min_risk` 는 **주입 방어가 아니라 탐지 성능**을
> 기록한다는 점을 기억해야 한다 - 엔진이 좋아지면 이 값도 따라 움직인다.

# Fraud Holdout Set v0.2

`fraud_holdout_v0.2.jsonl`, 72건. 로더는 `evaluation/fraud_golden.py` 를 공유한다
(`load_holdout_cases`).

## 왜 파일을 나눴나

v0.1 개발셋은 엔진 오류가 0건이 되어 **변별력을 잃었다.** 오답이 나오면 어휘를
고쳐 왔으니 당연한 결과이고, 그래서 그 셋의 점수는 더 이상 성능이 아니라 기억이다.

같은 파일에 `held_out` 플래그만 다는 방법도 있었지만 쓰지 않았다. 한 번의
실수로 held-out 사례가 규칙 수정에 쓰이고, 그 사실이 아무 데도 안 남는다.
**경계는 코드가 아니라 파일이 지킨다.** 로더는 한 파일이 반쪽만 held-out 인 것과
`fh-` 사례가 `fg-` ID 를 달고 들어오는 것을 둘 다 거부한다.

## 라벨 규칙

v0.1 계약을 그대로 쓰고 `held_out: true` 하나가 는다. 판정이 갈리는 자리는 아래
규칙으로 고정했고, **측정 전에** 정했다.

- `is_fraud` 는 **문자 자체**가 사기 시도인지만 본다. 사용자 상태와 무관하다.
- `expected_min_risk` 가 `high` 인 경우는 둘 뿐이다. 돈·인증정보·접근수단·설치·
  원격제어를 **명시적으로 요구**했거나, 상태가 `shared_account_access` 이상인 것.
  사칭·압박·링크 유도만 있고 구체적 요구가 없으면 `medium` 이다.
- `required_signal_codes` 에는 **문장에 실제로 드러난 것만** 적는다. 도메인
  평판처럼 바깥 지식이 있어야 아는 것은 요구하지 않는다. `fh-004`·`fh-009` 가
  그래서 링크 신호를 요구하지 않는다 — 요구하면 하지 않기로 한 기능
  (`10-mvp-backlog.md` P1 outbound-fetch)을 못 했다고 감점하는 셈이 된다.
- `required_action_codes` 는 상태 정책이 이미 주는 것과 신호에서 나와야 하는 것을
  함께 적는다.

> **2026-08-20 정정.** 위 마지막 줄은 원래 "교집합으로 채점하므로 중복은 무해하다"
> 였는데 절반만 맞다. `_required_action_coverage` 는 교집합이라 무해하지만,
> `_state_policy_accuracy` 는 `set(required) <= actions` 즉 **부분집합**을 요구한다.
> 하나라도 더 적으면 그 사례는 상태 정책 오답이 된다. v0.2 의 상태 정책 정확도
> 0.681 에는 이 라벨 착오분이 섞여 있을 수 있고, 얼린 파일이라 고치지 않는다.
> v0.3 은 이 사실을 알고 라벨했다.

## 무엇을 일부러 넣었나

- **부정 28건.** 오탐률을 재려면 정상 문자가 있어야 한다. 이 중 몇 건은 사기
  문자와 표면 어휘가 겹치도록 일부러 골랐다 — `fh-064`(서류를 "전달해"),
  `fh-063`("다시 보내"), `fh-068`(본인이 은행 앱을 "설치").
- **상태만 위험한 정상 문자 5건**(`fh-068`~`fh-072`). 상태가 탐지로 새는지 본다.
  주의 등급은 올라가야 하지만 사기 유형이 붙으면 안 된다.
- **예방 안내문 5건**(`fh-057`~`fh-061`). 억제 규칙이 정확히 겨냥하는 형태다.
- **`fh-040`** 은 필수 신호가 비어 있다. 본문만으로는 정상 청첩장과 구분되지
  않는 경계 사례라 신호를 요구하지 않고 남겨 뒀다.

## 출처와 권리

FinShield 팀이 2026-08-20 직접 작성한 합성 문장이다. 실제 피해자 메시지, 개인정보,
외부 데이터셋 문장을 복사하지 않았다. 문장은 공개된 사기 **유형**을 참고해
새로 썼다.

## 이용 한계

**저자가 엔진 어휘를 이미 알고 있다.** 완전한 blind 셋이 아니다. 그래서 지킨 것은
순서다 — 72건을 모두 쓰고 커밋해 동결한 **뒤에** 처음 돌렸다. 커밋 이력이 그
순서를 증거로 남긴다.

합성이고, 72건이며, 한국어 문자·메신저 형식에 한정된다. 음성·통화 녹취는 없다.
분포도 실제 수신 비율이 아니다(`received_only` 45건). 이 숫자를 실서비스 탐지
성능으로 주장하면 안 된다. **가치는 절대값이 아니라 개발셋과의 차이에 있다.**

CI 는 이 셋에 **성능 기준선을 걸지 않는다.** 걸면 빨개질 때마다 이 셋을 보고
규칙을 고치게 되고, 그 순간 held-out 이 아니게 된다. CI 가 지키는 것은 라벨
무결성과 개발셋과의 분리뿐이다.

### v0.2 는 소진되었다

v0.2 의 오답을 읽고 엔진 결함 네 가지를 특정했고, 그 수정을 진행한다. 그 순간부터
v0.2 는 held-out 이 아니라 **개발셋**이다. 이후 v0.2 숫자는 회귀 확인용이지
일반화 성능이 아니다. 파일은 지우지 않고 그대로 둔다 — 지우면 과거 측정이
무엇을 잰 것인지 확인할 수 없게 된다.

# Fraud Holdout Set v0.3

`fraud_holdout_v0.3.jsonl`, 60건(사기 31 · 정상 29). ID 는 `fh-101`~`fh-160`.
로더는 `load_holdout_cases(HOLDOUT_V0_3_PATH)` 이며 **기본 경로가 없다.** "held-out
셋" 이라는 이름으로 부를 수 있게 두면 어느 버전을 쟀는지 기록에 남지 않는다.

## 이 셋이 v0.2 보다 약한 주장을 한다

v0.2 는 결함을 모르는 상태에서 썼다. v0.3 은 **결함 네 가지를 이미 특정하고 수정
방향까지 정한 뒤에** 썼다. 그러므로 이것은 일반화 성능 추정치가 아니라 **표적
회귀 측정**이다. 수정이 의도한 자리에서 작동하는지, 그리고 **의도하지 않은 자리를
망가뜨리지 않는지**를 본다. 후자가 이 셋의 진짜 일이다.

지킨 것은 순서다. 60건을 모두 쓰고 커밋해 동결한 **뒤에** 엔진을 건드린다.
커밋 이력이 그 순서를 증거로 남긴다. 수정 전 기준선도 동결 커밋에 함께 넣어,
"고치고 나서 기준선을 정했다" 는 의심이 성립할 수 없게 했다.

## 무엇을 겨냥해 넣었나

아홉 묶음이고, 각 묶음이 짝을 이룬다. 사기와 정상이 **같은 어휘**를 쓰되 요구의
유무·방향·목적어만 다르게 만들었다. 어휘 목록으로는 절대 가를 수 없는 짝이다.

| 묶음 | 사례 | 무엇을 재나 |
|---|---|---|
| A | `fh-101`~`110` 사기 10 | 기관 자칭 + 위험 요구 |
| B | `fh-111`~`120` 정상 10 | **A 와 같은 기관**의 정상 안내. 요구 없음 |
| C | `fh-121`~`128` 정상 8 | 사용자가 자기 행동을 설명하는 문장 |
| D | `fh-129`~`133` 정상 5 | 전달·다시 보내 + 목적어가 돈이 아님 |
| E | `fh-134`~`138` 사기 5 | **같은 동사** + 목적어가 돈 |
| F | `fh-139`~`143` 사기 5 | 선입금·수수료 요구 (`advance_fee_demand`) |
| G | `fh-144`~`148` 정상 5 | 예방 안내문. 사기 문자와 어휘가 거의 같다 |
| H | `fh-149`~`159` 사기 11 | 나머지 유형과 조합 |
| I | `fh-160` 정상 1 | 정책자금 정상 안내 |

A/B 가 기관 어휘 결함, D/E 가 목적어 결함, C/G 가 요구 맥락 결함을 겨냥한다.
`fh-136`(옮기→옮겨)이 어미 결함을, `fh-138`("넘겨")이 **어휘 공백**을 겨냥한다 —
후자는 맞히지 못할 것을 알고 넣었다. 라벨을 규칙 어휘에 맞추면 그 셋은 아무것도
재지 못한다.

`fh-128`("앱을 다시 설치했습니다 … 인증서는 어떻게 옮기나요")과 `fh-148`(부정문
안의 OTP·비밀번호 + 뒷문장의 명령형)은 **수정이 과했는지**를 보는 자리다.
어미만 넓히거나 요구 판단을 문장 단위가 아니라 메시지 단위로 하면 여기서 걸린다.

## 라벨 규칙

v0.2 규칙을 그대로 쓰고 두 가지를 더했다. 모두 **측정 전에** 정했다.

- `advance_fee_demand` 는 "먼저 보내면 돌려준다·처리해 준다" 구조에 붙인다.
  받은 돈을 넘기라는 요구는 `money_mule_transfer` 그대로다. `fh-152`(검찰 사칭 +
  안전계좌 송금)에는 **붙이지 않았다.** 대가를 약속하지 않기 때문이다. 유형을
  하나 새로 만들었다고 모든 송금 요구에 붙이면 그 유형은 이름값을 잃는다.
- `required_action_codes` 는 **상태와 필수 신호에서 실제로 도출되는 것만** 적는다.
  `_state_policy_accuracy` 가 부분집합을 요구하므로 한 개만 더 적어도 오답이 된다.
  60건 전부를 `STATE_ACTIONS ∪ SIGNAL_ACTIONS` 에 대조해 확인했다.

## 알면서 남긴 불일치

`expected_min_risk` 는 위 규칙("명시적 요구가 있으면 high")을 사람 기준으로
적용했다. 그런데 현재 등급 정책은 **사칭 + 요구** 조합을 두 쌍
(`authority+money_transfer`, `loan+account_access`)만 high 로 올린다. 그래서 10건
(`fh-102`·`103`·`104`·`105`·`110`·`139`·`140`·`141`·`157`·`159`)은 완벽히 탐지해도
medium 에 걸린다.

**이번 수정에서 등급 정책은 건드리지 않는다.** 탐지 수정과 정책 수정을 같이 하면
숫자가 움직였을 때 어느 쪽 덕인지 말할 수 없다. 이 10건은 수정 전후 모두 등급
불일치로 남을 것이고, 그렇게 남는 것 자체가 이번 수정이 탐지 전용이었다는 증거다.
정책 확장은 별도 항목으로 `docs/10-mvp-backlog.md` 에 있다.

FinShield 팀이 2026-08-20 직접 작성한 합성 문장이다. 실제 피해자 메시지, 개인정보,
외부 데이터셋 문장을 복사하지 않았다. 기관명은 실재하지만 문장은 전부 창작이며,
**실제 그 기관이 보낸 안내가 아니다.** 링크는 접속되지 않는 형태(사설 IP 대역이
아닌 예시 주소·단축 링크 형식)로 적었고, 서버는 이 문자열을 절대 열지 않는다.

## 이용 한계

합성이고, 60건이며, 한국어 문자·메신저 형식에 한정된다. 저자가 엔진 어휘를 알고
있고 결함까지 알고 썼다. 그래서 이 숫자는 **실서비스 탐지 성능이 아니고**,
v0.2 와 직접 비교해서도 안 된다(구성이 다르다). 읽는 법은 하나뿐이다 —
**같은 v0.3 에 대한 수정 전과 수정 후의 차이.**

CI 는 v0.2 와 마찬가지로 이 셋에 성능 기준선을 걸지 않는다.
