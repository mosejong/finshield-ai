# 14. Development Workflow

## 목적

FinShield AI의 코드, 설계 판단, 테스트 결과와 리뷰 이력을 함께 남긴다.
새 참여자는 README와 docs만 읽어도 기능이 어떤 이유와 순서로 개발됐는지
재구성할 수 있어야 한다.

## 브랜치와 소유권

- `main`: PM 통합 전용. 기능 브랜치의 PR을 검수한 뒤에만 병합한다.
- `feature/frontend-mvp`: 프론트엔드 담당. 기본 소유 영역은 `web/`이다.
- `feature/fraud-scenario-engine`: 백엔드 담당. 기본 소유 영역은 `app/`, `tests/`다.
- 동일 파일을 두 브랜치에서 동시에 수정하지 않는다.
- `README.md`, `docs/README.md`, 공용 ADR과 운영 문서는 PM이 조율한다.

## 작업 흐름

1. 작업 시작 전에 저장소 지침과 관련 문서를 읽는다.
2. 작업 브랜치와 worktree가 올바른지 확인한다.
3. 해당 날짜와 브랜치의 개발일지 파일을 만든다.
4. 목표, 범위, 변경 이유와 검증 계획을 먼저 기록한다.
5. 구현 중 중요한 설계 결정과 실패·수정 내용을 시간순으로 추가한다.
6. 전체 관련 테스트와 보안·개인정보·공식근거 검토를 수행한다.
7. 코드와 개발일지를 함께 커밋하고 기능 브랜치만 push한다.
8. `main` 대상 PR을 만들고 생성 시각과 URL을 개발일지에 기록한다.
9. PM 리뷰 결과와 수정 내역을 기록한다.
10. 승인 후 PM이 병합하고 병합 시각·커밋을 기록한다.

## 일일 개발일지 경로

```text
docs/devlog/YYYY-MM-DD/<branch-slug>.md
```

한 브랜치가 여러 날 지속되면 날짜별 파일을 나눈다. 같은 날에도 브랜치가
다르면 파일을 분리한다. 모든 시각은 `Asia/Seoul` 기준으로 기록한다.

## 개발일지 필수 항목

- 날짜, 담당 역할, 브랜치, worktree
- 시작·종료 시각
- 목표와 비범위
- 변경 이유와 관련 문서
- 구현 및 데이터 흐름
- 변경 파일
- API·스키마·아키텍처 결정
- 공식 근거와 provenance
- 실행한 검증과 실제 결과
- 보안·개인정보 영향
- 실패, 수정, 리뷰 이력
- 알려진 위험과 다음 작업
- 커밋 SHA
- PR 번호, URL, 생성·병합 시각, 상태

실행하지 않은 테스트를 통과로 기록하지 않으며, mock과 live 데이터를 분명히
구분한다. 공식 확인 전 대응 절차나 금융 정보는 검증된 사실처럼 기록하지 않는다.

**커밋 SHA 는 병합 후에 확정한다.** squash 로 병합하면 작업 브랜치의 커밋들은
main 에서 도달할 수 없게 되고, 그 브랜치가 지워지는 순간 devlog 가 가리키는 SHA 는
죽은 참조가 된다. 그래서 병합 방식과 무관하게 **main 기준 SHA 를 먼저 적고**, 작업
브랜치 SHA 는 그 아래에 부기한다. PR #58 이 실제로 이 문제를 만들었다.

## README 갱신 기준

루트 `README.md`는 다음과 같은 큰 변화가 있을 때 PM이 갱신한다.

- 제품 범위나 Primary Persona 확정
- 주요 기능 또는 사용자 흐름 완료
- 공개 API 계약 변경
- 실행·설치·배포 방법 변경
- 핵심 아키텍처 또는 보안 경계 변경
- 검증 가능한 주요 성과 수치 추가

작은 리팩터링, 개별 버그 수정, 작업 과정은 README가 아니라 개발일지에 남긴다.
문서 구조가 바뀌면 `docs/README.md`와 `docs/devlog/README.md`의 인덱스를 갱신한다.

## 리뷰와 병합 원칙

- 기능 작성자가 `main`에 직접 push하거나 병합하지 않는다.
- PR에는 개발일지, 테스트 결과, 호환성, 보안·개인정보 영향이 포함되어야 한다.
- PM은 실제 diff와 테스트를 독립 검수한다.
- 리뷰 지적은 개발일지에 남기고 동일 브랜치에서 수정한다.
- 병합 후 `main` 기준 회귀 테스트를 실행한다.
