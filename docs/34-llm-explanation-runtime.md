# 34. LLM 설명 계층 런타임 (2026-08-19)

## 0. 이 문서가 생긴 이유

`app/services/llm/` 는 2026-08-17 에 완성돼 있었다. 계약(`contract.py`), 개인정보
최소화(`minimization.py`), 고정 프롬프트(`prompts.py`), 출력 검증(`validation.py`),
그리고 판정을 문장으로 옮기는 `explanation.py` 까지 전부 있고 테스트도 붙어 있었다.

**그런데 요청 경로에 연결돼 있지 않았다.**

`explain_analysis()` 는 프로바이더와 계약을 주입받는 함수다. 주입해 주는 사람이
없으면 아무도 부르지 않는다. 실제로 `app/clients/google_ai_studio.py` 를 import 하는
운영 코드는 하나도 없었고 — 테스트만 import 하고 있었다 — 배포된 서비스는 100%
규칙 기반이었다. `evaluation/results/fraud-benchmark-v0.1.json` 의 `llm_only.status`
가 `"not_run"` 인 것도 같은 원인이다(2026-08-19 에 `measured` 로 옮겼다 — 9절).

이 문서는 그 빈칸을 메운 작업의 기록이다. 무엇을 만들었고, **왜 그렇게 만들지 않을
수도 있었는데 그렇게 만들었는지**를 남긴다. 결정의 이유가 없으면 다음 사람이 같은
자리에서 반대로 결정한다.

관련 파일:

| 파일 | 역할 |
|---|---|
| `app/services/llm/runtime.py` | 신규. 스위치·모델 순서·대체 모델·프로세스 캐시 |
| `app/api/routes/analysis.py` | `POST /api/v1/analyze/explanation` 추가 |

| `tests/test_llm_runtime.py` | 신규 9건 |
| `tests/test_analysis.py` | 라우트 4건 추가 |
| `tests/test_rate_limits.py` | 정책 선택·한도 역전 2건 추가 |

## 1. 무엇이 환경 설정이고 무엇이 코드인가

이 계층에서 가장 먼저 정한 것이다.

**환경이 정하는 것: 켜는가.** `FINSHIELD_LLM_PROVIDER` 하나뿐이다. 값은 `off`(기본),
`stub`, `google_ai_studio`. 배포마다 다르고, 사고가 났을 때 재배포 없이 꺼야 하는
값이라 환경에 둔다.

**코드가 정하는 것: 어떤 모델인가.** `EXPLANATION_MODEL` 과
`EXPLANATION_FALLBACK_MODEL` 은 `runtime.py` 의 상수다. 환경변수로 못 바꾼다.

두 번째가 직관에 어긋나 보이므로 이유를 적는다. `contract.py` 가 이미 같은 판단을
적어 뒀다 — provider 와 model 이 환경변수로 조용히 움직이면, **그 전에 측정한
벤치마크 숫자가 어느 모델의 것인지 아무도 모르게 된다.** 모델을 올리는 것이 코드
변경이어야, 올린 사람이 `evaluation/` 을 다시 돌리게 된다. `tests/test_llm_runtime.py`
의 `test_the_models_come_from_code_not_the_environment` 가 그럴듯한 이름의 환경변수
(`FINSHIELD_LLM_MODEL`, `GEMINI_MODEL`)를 넣어 두고 그래도 코드 상수가 이기는지
확인한다.

### 오타는 off 가 아니다

`FINSHIELD_LLM_PROVIDER=gogole_ai_studio` 를 조용히 off 로 접으면 아무도 오타를 못
찾는다. 서비스는 정상으로 보이고 화면에서 "왜 위험한지" 만 영영 비어 있다. 그래서
모르는 값은 `LlmRuntimeConfigurationError` 로 거부한다.

같은 이유로 **켜 놓고 키가 없는 것도 오류다.** 조용히 끄면 배포에서 키를 빠뜨렸을
때 서비스가 정상으로 보인다. 켠 것과 끈 것은 다른 상태이고, 다르게 다뤄야 한다.

이 검증은 첫 요청이 아니라 `main.py` 의 lifespan 에서 실행된다
(`verify_llm_runtime_configuration()`). 잘못된 설정으로 뜬 컨테이너는 healthcheck 를
통과하지 못하고, 배포가 거기서 멈춘다.

## 2. 모델 선택 — 실측 기록

2026-08-19, Google AI Studio 에 직접 호출한 값이다. 계정은 선불 크레딧이 들어 있는
**유료 등급**이다(`docs/28` P2-2).

첫 탐색(짧은 프롬프트, 각 1회):

| 모델 | 응답 시간 | 비고 |
|---|---:|---|
| `gemini-3.1-flash-lite` | 1.31s | 대체 모델로 채택 |
| `gemini-3.5-flash` | 3.75s | |
| `gemini-3.6-flash` | 5.52s | 주 모델로 채택 |
| `gemini-2.5-flash` | 5.88s | |
| `gemini-3.7-flash` | 6.48s | |
| `gemini-3.1-flash` | — | **존재하지 않는다. HTTP 404** |

마지막 줄은 그대로 남긴다. `gemini-3.1-flash` 를 대체 모델로 쓰기로 했다가 404 를
받고 바꾼 것이다. 이름이 그럴듯하다고 있는 모델이 아니며, 확인 없이 상수에 적었다면
**주 모델이 죽었을 때만** 드러났을 종류의 실패다.

**이 표는 이 계층을 설명하지 못했다.** 라우트를 붙이고 실제로 호출해 보니 주 모델은
한 번도 답하지 않았다. 다음 절이 그 이야기다.

### 2-1. 사고 토큰이 답변 예산을 먹고 있었다

라우트 완성 후 첫 실호출 3회가 전부 대체 모델로 떨어졌다. `available: true`,
`model: gemini-3.1-flash-lite`. 설명은 나왔으니 화면상으로는 정상이었다 — **주 모델이
100% 실패하는데 정상으로 보이는 상태**였다.

원인을 계약 수준에서 재현했다.

```
gemini-3.6-flash   t=8.0   7.52s  UNAVAILABLE  stopped early: MAX_TOKENS
gemini-3.6-flash   t=25.0  7.48s  UNAVAILABLE  stopped early: MAX_TOKENS
```

타임아웃이 아니었다. 25초를 줘도 같았다. 원시 응답의 `usageMetadata` 를 보고 답이
나왔다.

| 요청 | thinking 토큰 | 답변 토큰 | finishReason |
|---|---:|---:|---|
| `gemini-3.6-flash`, 1024 tok | 982 | 38 | **MAX_TOKENS** |
| `gemini-3.6-flash`, 4096 tok | 1025 | 125 | STOP |
| `gemini-3.5-flash`, 1024 tok | 984 | 36 | **MAX_TOKENS** |
| `gemini-3.5-flash`, 4096 tok + `thinkingLevel: low` | 725 | 129 | STOP |
| `gemini-3.1-flash-lite`, 1024 tok | 0 | 105 | STOP |

Gemini 3.x flash 계열은 **사고 토큰이 `maxOutputTokens` 와 같은 예산에서 나간다.**
`MAX_OUTPUT_TOKENS = 1024` 는 "설명은 600자니까 넉넉하다" 는 계산으로 정한 값이었고,
그 계산에 사고 몫이 빠져 있었다. 사고에 982 토큰이 나가면 답변에 38 토큰이 남고,
문장은 중간에 잘리고, `finishReason` 검사가 그 잘린 문장을 (정확하게) 버린다.

사고를 하지 않는 `-lite` 만 통과하고 있었다는 것이 이 버그의 성질을 잘 보여 준다.
**사고 모델을 하나라도 주 모델로 세우는 순간 전부 실패했을 텐데, 대체 모델이 받아
주는 바람에 화면에는 아무 문제도 나타나지 않았다.** 대체 경로가 버그를 가린 것이다.

고친 것 둘:

- `MAX_OUTPUT_TOKENS` 1024 → **4096**. 이 상수는 답변 길이가 아니라 **사고 + 답변의
  합**으로 잡아야 한다. `tests/test_llm_provider_google.py::test_the_token_budget_leaves_room_for_thinking`
  가 실측 사고 토큰의 2배 이상을 요구해서 이 값이 다시 내려가는 것을 막는다.
- `generationConfig.thinkingConfig.thinkingLevel = "low"` 추가. 확정된 판정을 3~5문장
  으로 옮기는 일에 깊은 사고는 필요 없고, 출력은 어차피 검증기를 통과해야 한다.
  `gemini-3.5-flash` 는 이것으로 실패에서 4.34초 성공으로 바뀌었다.
  사고를 완전히 끄는 `thinkingBudget: 0` 은 `gemini-3.6-flash` 에서 **HTTP 400** 이라
  쓰지 않는다. `thinkingLevel` 을 모르는 모델도 400 을 낼 텐데, 그러면
  `LlmUnavailable` 로 접혀 다음 모델로 넘어간다 — 조용히 나빠지는 대신 그 모델이
  통째로 빠진다.

고친 뒤 라우트 전 경로 3회:

| 회차 | 응답한 모델 | 총 소요 |
|---|---|---:|
| 1 | `gemini-3.6-flash` | 7.69s |
| 2 | `gemini-3.6-flash` | 8.17s |
| 3 | `gemini-3.6-flash` | 7.65s |

타임아웃은 이 실측의 약 1.7배로 잡았다 — 주 모델 14초, 대체 모델 6초. 모델마다 다른
이유는 `fraud_explanation_contract` 에 적었고, **둘의 합(20초)이 이 계층의 최대 지연**
이라 `tests/test_llm_runtime.py::test_the_worst_case_wait_is_bounded_and_the_fallback_is_the_shorter_one`
가 그 합에 상한을 건다.

### 지금 이 조합이 최선인지는 별개 문제다

주 모델은 7.7~8.2초이고 매 요청 800~1030 토큰을 사고에 쓴다. 대체 모델은 1.6~1.9초에
사고 토큰이 0 이고, 나온 문장은 검증기를 통과했으며 읽기에도 손색이 없었다. **이 과제
— 확정된 판정을 근거 안에서 3~5문장으로 옮기기 — 에서 사고가 사 주는 것이 무엇인지는
아직 측정되지 않았다.** `evaluation/` 에서 두 모델을 비교하기 전까지 이 배치는 근거가
아니라 선택이며, 뒤집는 데 필요한 것은 상수 한 줄이다.

### 대체 모델이 `-lite` 인 것은 타협이 아니다

주 모델이 막혔을 때 필요한 것은 같은 품질이 아니라 **응답이 돌아오는 것**이다. 그리고
어느 모델이 쓰든 출력은 `validate_explanation` 을 통과해야 한다 — 근거에 없는 연락처,
URL, 주민번호 형태는 어느 쪽에서 나와도 버려진다. 품질의 하한은 모델이 아니라 검증기가
잡는다.

두 모델이 **사고 여부에서 갈리는 것도 의도**다. 2-1 이 보여 준 것이 바로 그것이다 —
성질이 같은 모델 둘을 세우면 같은 이유로 함께 죽는다.

### 어느 모델이 답했는지 함께 돌려준다

`ExplanationResult.model` 과 응답의 `model` 필드다. 대체 모델로 넘어갔는데 주 모델
이름을 기록하면, 나중에 이 문장이 어느 모델의 것인지 평가에서 다시 세울 수 없다. 위
1절에서 모델을 코드에 박아 지키려던 것과 정확히 같은 성질의 문제다.

## 3. 왜 별도 엔드포인트인가

`POST /api/v1/analyze/explanation` 을 새로 만들었다. `AnalyzeResponse` 에 `explanation`
필드를 더하지 않았다. 이유가 둘이다.

**첫째, 지연이다.** 설명 한 문단에 약 8초가 걸린다(2-1 실측). 판정 응답에 붙이면 위험
수준을 보여 주기까지 그 8초를 기다리게 된다. 지금 의심 문자를 받은 사람에게 가장
나쁜 설계다. 지금 구조에서는 판정이 먼저 그려지고 설명이 그 뒤에 채워진다 —
`analyze_fraud()` 자체는 200회 반복 측정에서 평균 0.041ms 였고, 네트워크 왕복을
얹어도 설명의 8초와는 자릿수가 다르다.

**둘째, 의존 방향이다.** 판정 응답이 설명을 품으면 "설명이 없으면 판정도 없다" 는
상태가 코드 모양으로 **가능해진다.** 나눠 두면 그 상태를 만들 수 없다. `CLAUDE.md` 의
첫 non-negotiable — LLM 은 판정의 권위가 아니다 — 을 주석이 아니라 구조로 지킨다.

### `available` 은 `explanation is None` 과 다르다

| `available` | `explanation` | 뜻 | 화면 |
|---|---|---|---|
| `false` | `null` | 계층이 꺼져 있다 | "왜 위험한지" 블록을 아예 만들지 않는다 |
| `true` | `null` | 켜져 있는데 이번에 못 만들었다 | 블록은 두고 "설명을 불러오지 못했습니다" |
| `true` | 문장 | 정상 | 문장 표시 + 모델 표기 |

꺼져 있을 때 404 나 503 으로 답하지 않는 것이 중요하다. 그러면 프론트엔드가 이것을
장애로 다룬다. 설명이 없는 것은 장애가 아니다.

## 4. 클라이언트는 설명받을 판정을 고를 수 없다

이 라우트에서 가장 중요한 결정이다.

엔드포인트는 `AnalyzeResponse` 가 아니라 **`AnalyzeRequest` 를 받는다.** 그리고 서버가
`analyze_fraud()` 를 다시 돌려 판정을 스스로 만든 뒤, 그 판정만 설명한다.

`AnalyzeResponse` 를 받게 했다면 클라이언트가 위험 수준을 `low` 로, 신호를 빈 배열로
적어 보내는 것만으로 모델이 "이 문자는 크게 위험하지 않습니다" 를 써 준다. 결정론
엔진을 두고도 설명이 조작되는 경로가 생긴다. 화면에 붙는 것은 판정이 아니라 문장이므로,
사용자가 실제로 읽는 것은 조작된 쪽이다.

`analyze_fraud` 는 순수 함수라 같은 입력에 같은 판정이 나오고, 다시 부르는 비용은
8초 옆에서 무시할 만하다.

`tests/test_analysis.py::test_the_client_cannot_supply_the_verdict_it_wants_explained`
가 이것을 주장하지 않고 관측한다 — 요청 본문에 `risk_level: "low"` 와 가짜 `summary`
를 섞어 보낸 뒤, 모델이 **실제로 받은 프롬프트**에 서버가 계산한 위험 수준이 들어갔고
가짜 문구는 없는지 확인한다.

## 5. 요청 한도 — 밟을 뻔한 함정

설명 경로는 이 서비스에서 가장 비싼 경로다. 유료 외부 호출이 나가고, 대체 모델까지
가면 한 요청에 두 번 나간다. 그래서 `analyze_explanation` 정책을 **10회/분**으로
따로 뒀다(`analyze` 는 30회/분).

함정은 순서와 매칭 방식에 있었다.

- `analyze` 정책은 `exact_path=True` 다. `/api/v1/analyze/explanation` 은 `/api/v1/analyze`
  와 문자열이 다르므로 **이 정책에 걸리지 않는다.**
- 정책을 따로 두지 않으면 이 경로는 아래의 `write` 정책(60회/분)으로 떨어진다.
- 즉 **더 비싼 경로가 더 헐거운 한도를 갖게 된다.**

실제로 확인한 값이다. `analyze_explanation` 을 목록에서 빼고 정책을 고르면
`write / 60` 이 나온다. `tests/test_rate_limits.py::test_the_explanation_path_is_not_looser_than_the_paths_it_sits_under`
가 이름이 아니라 **숫자의 대소**를 검사하는 이유다 — 이름만 맞고 한도가 뒤집혀 있으면
검사가 아무것도 증명하지 못한다.

정책은 `analyze` 보다 **위에** 있어야 한다. 목록은 위에서부터 먼저 맞는 하나만
적용하기 때문이다.

**남는 위험:** 한도는 IP 단위다(`rate_limits.py` 첫머리의 이유 참고). 분산된 남용은
막지 못한다. 그것은 여기가 아니라 프로바이더 쪽 예산 한도로 막을 문제이고, 아직 하지
않았다 — 9절에 남겨 둔다.

## 6. 실패 모드

설명 계층은 **어떤 실패에서도 판정 경로를 죽이지 않는다.** 각 경우가 어떻게 되는지.

| 상황 | 결과 | 확인하는 테스트 |
|---|---|---|
| 계층이 꺼져 있음 | 200, `available: false` | `test_explanation_is_absent_but_the_endpoint_still_answers` |
| 프로바이더 이름 오타 | 기동 실패 | `test_a_typo_in_the_provider_name_is_refused` |
| 켰는데 키 없음 | 기동 실패 | `test_turning_it_on_without_a_key_is_an_error_not_a_silent_off` |
| 주 모델 응답 없음 | 대체 모델 시도 | `test_the_fallback_answers_when_the_first_model_is_down` |
| 모든 모델 실패 | 200, `available: true`, `explanation: null` | `test_every_model_failing_yields_no_explanation` |
| 안전 필터 차단 / 잘린 응답 | `LlmUnavailable` → 다음 모델 | `google_ai_studio.py` 의 `finishReason` 검사 |
| 없는 연락처를 지어냄 | 그 모델 출력 폐기 → 다음 모델 | `test_output_that_invents_a_hotline_is_dropped_and_falls_through` |

마지막 줄이 이 계층에서 가장 신경 쓴 곳이다. 가짜 신고번호를 알려 주는 것은 이
서비스가 낼 수 있는 가장 나쁜 출력이다 — 사용자가 그 번호로 전화를 건다. 거부가
**대체 모델 시도로 이어지는지**까지 테스트로 고정했다.

`explain_with_fallback` 은 "프로바이더가 죽음" 과 "출력이 거부됨" 을 구분하지 않고
둘 다 다음 모델로 넘긴다. 호출하는 쪽에서 보면 둘 다 "설명이 없다" 이고, 어느 쪽이든
다음 모델을 시도할 가치가 있기 때문이다. 대신 한 요청에 유료 호출이 두 번 나갈 수
있으므로 **계약 목록은 짧게 유지한다**(현재 2개).

## 7. 스트리밍을 하지 않는다

설명이 늦게 나오는 것이 답답하니 토큰을 순차적으로 흘리자는 안을 검토했고,
**하지 않기로 했다.**
나중에 같은 제안이 다시 나올 것이므로 이유를 남긴다.

**(1) 검증을 통과하지 않은 문장을 보여 주게 된다.** 이 계층의 마지막 방어선은
`validate_explanation` 이고, 그것은 **완성된 출력 전체**를 보고 판정한다 — 근거에
없는 연락처가 들어왔는지는 그 연락처가 다 나온 뒤에야 알 수 있다. 스트리밍하면
`02-1234-5678` 이 화면에 찍힌 다음에 거부 판정이 난다. 그때 할 수 있는 일은 이미 읽힌
문장을 지우는 것뿐이고, **사기 경고 화면에서 방금 보여 준 연락처를 회수하는 것**은
8초를 기다리게 하는 것보다 훨씬 나쁘다. `explanation.py` 가 이미 같은 판단을 적어
뒀다 — "검증에 실패하면 설명 없이 간다. 설명이 없는 결과는 불편하지만, 검증을
통과하지 못한 설명이 붙은 결과는 위험하다."

**(2) 기다리는 대상이 이미 바뀌었다.** 3절의 분리 덕분에 사용자는 그 8초 동안 빈 화면을
보지 않는다. 위험 수준·신호·권고 행동·공식 근거는 첫 응답에 이미 다 들어 있고, 늦게
차는 것은 "왜 위험한지" 블록 하나다. 그 블록 하나를 위한 스켈레톤은 스트리밍보다
싸고, 무엇보다 **취소할 수 있다.**

**(3) 지연을 줄이는 더 싼 손잡이가 남아 있다.** `gemini-3.1-flash-lite` 가 1.31초다.
설명 품질이 충분하다고 측정되면 주 모델을 바꾸는 것만으로 8초가 1.7초가 된다(2절 끝).
스트리밍은 SSE 경계·프록시 버퍼링·중간 취소·부분 출력 로깅을 전부 새로 다뤄야 하는
작업인데, 그것을 하기 전에 상수 하나로 4초를 줄일 수 있는지부터 재는 것이 순서다.

**다시 검토할 조건:** 위 (3)을 측정했는데도 사용자에게 필요한 문장이 3초를 넘고,
동시에 출력 검증을 **증분으로** 할 수 있는 방법이 생겼을 때. 두 조건이 함께 만족되기
전에는 이 결정을 뒤집지 않는다.

## 8. 켜는 방법

로컬(스텁, 네트워크 없음):

```powershell
$env:FINSHIELD_LLM_PROVIDER = "stub"
uvicorn app.main:app --reload
```

로컬(실제 모델):

```powershell
$env:FINSHIELD_LLM_PROVIDER = "google_ai_studio"
$env:GEMINI_API_KEY_FILE = "secrets/gemini_api_key.txt"
uvicorn app.main:app --reload
```

컨테이너:

```powershell
docker compose -f compose.yaml -f compose.gemini.yaml --env-file .env.docker up -d
```

`compose.gemini.yaml` 이 별도 파일인 이유는 `compose.public-data.yaml` 과 같다. compose 의
`secrets:` 항목은 파일이 실제로 있어야 하므로, 기본 `compose.yaml` 에 넣으면 키가 없는
사람은 `docker compose up` 자체가 실패한다. **없는 쪽이 기본이어야 한다.**

키는 환경변수가 아니라 파일로 받는다. 값으로 주면 `docker inspect` 와 프로세스 목록에
남는다. `secrets/` 디렉터리 전체가 `.gitignore` 되어 있고,
`tests/test_runtime_secrets.py` 가 `git check-ignore` 로 실제 동작을 확인한다 — 이번에
그 검사를 **override compose 파일까지** 훑도록 넓혔다. 기본 파일만 보고 있었기 때문에,
선택 기능의 키는 항상 검사 밖에서 추가되는 구조였다.

## 10. 프론트엔드 연결 (2026-08-19)

`/check/result/[id]` 의 "왜 위험한지" 블록에 붙였다. 관련 파일:

| 파일 | 역할 |
|---|---|
| `web/lib/api/explanation.ts` | 응답 어댑터, 서버·클라이언트 호출 |
| `web/app/api/proxy/analyze/explanation/route.ts` | 신규 프록시 |
| `web/lib/store/explanation-store.ts` | 원문 인계, 결과 캐시, 훅 |
| `web/components/safety/WhyRiskyPanel.tsx` | 설명 자리 추가 |

### 결정론 요약을 대체하지 않는다

이 블록에는 원래 백엔드의 `summary` 가 들어 있었고, 그것은 규칙에서 바로 나오는
값이다. 모델 문장으로 **갈아 끼우지 않고 아래에 덧붙였다.**

이유는 `CLAUDE.md` 의 첫 non-negotiable 과 같다. 판단 근거의 자격을 갖는 것은
결정론 쪽이고, 모델 문장은 그것을 쉬운 말로 옮긴 것이다. 갈아 끼우면 8초 동안
"왜 위험한지" 가 통째로 비어 있게 되고, 모델이 실패한 배포에서는 영영 비어 있다.
덧붙이면 결정론 요약은 즉시 뜨고 모델 문장만 나중에 채워진다.

화면에는 어느 모델이 썼는지와 함께 "위험 수준과 행동은 이 문장이 아니라 규칙
엔진이 정합니다" 를 적는다. 사용자가 이 문단을 판정으로 읽으면 안 된다.

### 원문을 sessionStorage 에 넣지 않았다

이 엔드포인트는 판정이 아니라 **원문**을 받는다(4절). 즉 결과 화면이 설명을
받으려면 사용자가 붙여넣은 문자를 다시 갖고 있어야 한다.

판정 결과는 `sessionStorage` 에 있다(`analysis-store.ts`). 원문도 거기 넣으면
간단했지만 넣지 않았다. 판정은 가공된 값이고 원문은 가공되지 않은 그대로여서,
이름·계좌번호·연락처가 그대로 들어 있을 수 있다. `share/pending.ts` 가 공유로
받은 원문을 화면이 집어가는 즉시 저장소에서 지우는 것과 같은 판단이다.

대신 모듈 메모리로만 넘긴다. **대가는 새로고침하면 설명이 다시 붙지 않는 것**
이다. 판정·신호·행동·공식 근거는 그대로 남고 "왜 위험한지" 는 결정론 요약으로
돌아간다. 원문을 저장소에 남기는 것보다 이쪽이 낫다고 봤다.

요청을 만든 뒤에는 메모리에서도 곧바로 버린다. 결과 `Promise` 는 id 별로
캐시하는데, 유료 호출이 개발 모드의 StrictMode 이중 실행이나 화면 재방문만으로
두 번 나가는 것을 막기 위해서다.

### 예시 결과에는 붙이지 않는다

`/check/result/demo` 는 화면 구조를 보여 주는 예시다. 여는 것만으로 유료 모델
호출이 나가면 안 되므로 훅을 끈다. mock 모드도 같다 — `explainOnServer` 는 mock
모드에서 그럴듯한 문장을 지어내지 않고 `off` 를 돌려준다. 다른 mock 데이터와
성격이 다르기 때문이다. 화면 구조를 보여 주는 예시 값과, 모델이 실제로 뭐라고
말하는지는 서로 대신할 수 없다.

### 상태 세 가지

`available` 과 `explanation` 을 합치지 않고 그대로 옮겼다(3절 표).

| 상태 | 화면 |
|---|---|
| `off` | 설명 자리를 아예 만들지 않는다 |
| `failed` | 자리를 두고 "설명을 불러오지 못했습니다" + 위 요약이 판단 근거라고 안내 |
| `ready` | 문장 + 답한 모델 표기 |

합치면 계층을 켜지 않은 배포에서 매번 "불러오지 못했습니다" 가 뜬다.

### 타임아웃

프론트 기본값은 8초인데(`lib/api/client.ts`), 설명만 25초로 늘렸다. 백엔드가
최악의 경우 20초를 쓰므로(2-1) 기본값을 그대로 두면 백엔드가 정상적으로 답하는
중에 프론트가 먼저 끊는다.

### 실측

`next dev` → 프록시 → 백엔드 → Gemini 전 경로 1회: **9.29초, `gemini-3.6-flash`**.
백엔드 직접 호출이 7.40초였으므로 프록시와 dev 서버가 약 1.9초를 더한다.
프로덕션 빌드에서는 이보다 짧을 것이나 측정하지 않았다.

```python
minimized   = minimize_for_provider(message)            # 1. 개인정보
neutralized = neutralize_instructions(minimized.text)   # 2. 모델을 향한 지시문
raw         = provider.generate(prompt)
return validate_explanation(raw, ..., risk_level=response.risk_level)  # 3. 출력
```

순서가 의미를 갖는다. 개인정보를 먼저 걷어내지 않으면 `[전화번호]` 로 바뀌었어야 할
자리가 지시문 자리표시자 **안에** 숨어 두 계층의 건수가 어긋난다.

### 판정은 이 경계 바깥에 있다

`analyze_fraud()` 가 **원문을 보고** 판정을 끝낸 뒤에야 `explain_analysis()` 가
호출된다. 그래서 입력 정화가 아무리 과해도 **위험 등급을 낮출 수 없다.** 이건 설계
의도가 아니라 타입 구조의 결과이고, 테스트가 고정한다.

### 고정 프롬프트는 그대로다

두 계층 다 **프롬프트가 아니라 치환되는 값**을 고친다. 따라서
`FRAUD_EXPLANATION_PROMPT_SHA256` 이 불변이고, 이 변경은 2절·9절의 유료 측정
재실행을 요구하지 않는다.

### 출력 검증에 위험 수준이 인자로 들어온다

`validate_explanation(..., risk_level=...)` 로 시그니처가 바뀌었다. 판정이
`medium`/`high` 일 때만 "안심시키는 문장" 을 거부하기 때문이다. `low` 판정에서는
같은 문장이 정상이다.

이 검사의 첫 판은 **서술어만** 봤고, 관측된 정당한 경고 8건 중 **4건을 거부했다.**
한국어 안전 안내가 "…확인하시는 것이 안전합니다" 로 끝나기 때문이다. 지금은
**메시지를 가리키는 주어**를 함께 요구해서 8건 모두 통과한다. 상세는 데브로그.

### 좁히는 단위는 문장 → 절 → 구간이다 (2026-08-20 후속)

코덱스 검토가 두 가지를 짚었고 재현하면서 두 가지가 더 나왔다. 요지만 적는다.

- **서술어 목록만으로는 부족하다.** "이 문자는 믿으셔도 됩니다", "안심하고
  안내대로 송금하세요" 가 `high` 판정에서 통과했다. 뒤엣것은 판정을 부정하지 않고
  **행동만 뒤집어서** 더 위험하다.
- **마침표가 없는 문자가 통째로 지워졌다.** 한국어 문자는 부호 없이 종결어미로
  끝나는 것이 보통이다. 절 단위 경계와, 그것도 없을 때의 구간 단위 교체를 넣었다.
- **줄바꿈이 패턴을 갈라 놓으면 아무것도 안 걸렸다.** 조각만 검사하던 탓이다.
- **자리표시자 뒤에 지시문이 남아 있었다.** 정화 결과에 `contains_instruction` 이
  참이면 실패하는 검사를 새로 뒀다.

전문은 `docs/devlog/2026-08-20/prompt-injection-boundary.md` 후속 절.

## 12. 실패에 이름을 붙였다 (2026-08-24)

9절에 두 줄이 따로 적혀 있었다. **안전 필터 차단율을 모른다**, 그리고 **이 계층은
아무것도 기록하지 않는다.** 붙여 놓고 보니 한 줄이었다. 기록할 것이 없었던 게 아니라
**셀 것이 없었다** — 실패가 전부 `None` 하나로 접혀 있었기 때문이다.

사유가 세 번 버려지고 있었다.

| 자리 | 버리는 것 |
|---|---|
| `google_ai_studio.py` | HTTP 오류·타임아웃·차단·잘림을 전부 `LlmUnavailable` 로 올린다. 구분은 **자유 문자열 메시지**에만 있었다. |
| `explain_analysis` | 그 예외를 잡아 `None` 을 돌려준다. 메시지째 사라진다. |
| `explain_with_fallback` | `ExplanationResult(None, None)` 을 돌려준다. |

그래서 "설명이 40% 비어 있다" 를 관측해도 다음 행동을 정할 수 없었다. 안전 필터
문제면 프롬프트를 고쳐야 하고, 타임아웃이면 예산을 늘려야 하고, 모델이 없는
신고번호를 지어내는 문제면 그건 **프롬프트가 아니라 모델을 바꿔야 하는 신호**다.

### 사유를 문자열로 남기지 않는다

가장 쉬운 길은 예외 메시지를 그대로 label 로 올리는 것이고, 그건 하면 안 된다.
그 문자열은 **provider 응답에서 온다.** 400 응답은 요청 조각을 되돌려주기도 하고,
Prometheus label 은 한 번 늘어나면 줄지 않는다. ADR 0006 이 마스킹 대신 허용 목록을
고른 것과 같은 이유다 — 마스킹은 빠뜨린 것을 흘리고, 허용 목록은 모르는 것을 버린다.

그래서 닫힌 어휘를 만들었다(`app/services/llm/outcomes.py`, 20 개). 어휘가 닫혀
있으려면 **모르는 것을 담는 칸도 어휘 안에** 있어야 한다 — `stopped_early`(모르는
`finishReason`)와 `unspecified`(사유를 안 붙인 남의 provider)가 그 칸이다.

갈라 놓은 것 중 의미가 있는 둘.

- **`prompt_blocked` vs `safety_blocked`.** 앞은 `promptFeedback.blockReason`(우리
  입력이 거부됨), 뒤는 `finishReason: SAFETY`(모델이 스스로 멈춤). 9절이 원래
  걱정한 것은 앞쪽이었는데 이름은 뒤쪽을 가리키고 있었다.
- **`timeout` vs `transport_error`.** 타임아웃은 **우리 예산 이야기**다. 2절 실측이
  7.7~8.2초, 예산이 14초다. 이 비율이 오르면 예산을 바꾸라는 신호이고, 연결 실패와
  같은 칸에 있으면 그 신호가 안 보인다.

`promptFeedback` 은 **키가 있는지만** 본다. 값을 읽는 순간 그 문자열이 우리 코드로
들어오고, 들어온 것은 언젠가 나간다.

### 타입이 거짓말을 못 하게

`explain_analysis` 의 반환이 `str | None` 에서 `ExplanationAttempt(text, outcome)`
로 바뀌었다. 불변식은 하나 — **`text` 가 있는 것과 `outcome` 이 `ok` 인 것이 정확히
같다.** 어긋나면 지표는 성공을 세는데 화면은 비어 있고, 그 상태는 계측이 없는 것보다
나쁘다. 숫자가 있으니 아무도 안 찾아본다.

예외 쪽은 비대칭으로 뒀다. `LlmOutputRejected.outcome` 은 **필수**이고
(`validation.py` 안에서만 올라온다), `LlmUnavailable.outcome` 은 **선택**이다
(`LlmProvider` 가 Protocol 이라 남의 구현이 사유 없이 던질 수 있다). 남이 던질 수
있는 예외는 사유를 요구할 수 없다. 대신 **우리 코드가 그 칸을 쓰지 않는지**를
테스트가 구문 트리로 확인한다 — `app/` 안의 모든 `raise` 에 `outcome=` 이 있다.

### 세는 자리는 조립하는 자리다

카운터는 `runtime.py` 에 있고 `explanation.py` 에는 없다. `evaluation/` 이
`explain_analysis` 를 직접 부르기 때문이다. 순수 계층에 카운터를 두면 벤치마크 한
번에 운영 지표가 수십 건씩 오염되고, 그 지표로는 경보를 걸 수 없다.

시도와 결과를 나눠 센다. 대체 모델이 있으므로 요청 하나가 시도 둘을 만들고, 그때
실패 하나와 성공 하나가 **같이** 일어난다. 시도만 세면 "설명이 결국 비었다" 를,
결과만 세면 "주 모델이 얼마나 막히는가" 를 계산할 수 없다. 전부 실패했을 때 결과에
남는 것은 **마지막** 사유다 — 사용자가 빈 화면을 본 직접적인 이유가 그것이고, 앞선
실패는 시도 지표에 이미 각각 남아 있다.

다음 모델로 넘어가는 판단은 **여전히 사유를 보지 않는다.** 6절의 결정 그대로다.
사유는 세기 위한 것이지 분기하기 위한 것이 아니다.

### 새 엔드포인트를 열지 않았다

`/internal/metrics` 에 덧붙인다. endpoint 를 새로 열면 그것이 새 외부 표면이고
CLAUDE.md 의 보안 검토 대상이 되는데, 여기서 필요한 것은 표면이 아니라 숫자다.
지표군·로그 필드 목록은 `docs/27`.

~~**셀 수 있게 됐고, 아직 숫자는 없다.**~~ 2026-08-25 에 유료 실행을 돌렸다. 분모가

를 내고, 셋이 바뀌면 `stale` 을 낸다 — 계측이 있다는 것과 측정했다는 것은 다르고,

### `fh-1007` — 대체 모델은 이 실패의 안전망이 아니다

164건 중 설명이 끝내 안 나간 것은 하나다. 그리고 그 하나가 **주 모델과 대체 모델이
똑같이 번호를 지어낸** 사례다.

```
fh-1007  "112 신고 접수 결과 안내입니다. 접수번호로 처리 결과를 조회하실 수 있습니다."
         라벨: 정상, 판정: low
         gemini-3.6-flash        → rejected_invented_contact
         gemini-3.1-flash-lite   → rejected_invented_contact
         결과: 설명 없음
```

대체 모델을 둔 이유는 6절에 적혀 있다 — 주 모델이 막히는 동안 "왜 위험한지" 가 계속
비어 있지 않게 하는 것. 그 설계는 **프로바이더 장애**를 가정한다. 여기서 일어난
것은 장애가 아니라 **같은 성질의 두 모델이 같은 충동을 보인 것**이고, 그때 대체
모델은 아무것도 막아 주지 않는다. `runtime.py` 가 "같은 성질의 모델 둘을 세워 두면
같은 이유로 함께 죽는다" 며 사고 여부가 갈리는 모델을 고른 것이 이 방향의 대비였는데,
사고 여부는 이 충동을 가르지 않았다.

원인은 근거 쪽이다. 이 사례는 `low` 이고 신호도 행동도 출처도 없어서, 모델이 받은
근거 블록이 통째로 이렇다.

```
- 없음
- 없음
- 없음
```

`build_grounded_text` 가 검증 기준이므로 **근거가 비면 어떤 번호든 지어낸 것이 된다.**
모델은 사용자 문장에 있는 `112` 를 되읊었을 가능성이 높고, 그것은 실재하는 번호다.
그래도 이 거부는 옳다 — 사용자 문장은 적대적 입력이고, 거기 적힌 번호를 근거로
인정하면 사기 문자에 적힌 번호를 그대로 안내하는 경로가 열린다. **문자 안의 번호가
진짜인지 가짜인지는 문자를 봐서 알 수 없다. 그것이 바로 사기범이 고르는 값이기
때문이다.**

그래서 이 한 건은 규칙의 실패가 아니라 **규칙의 가격**이다. 다만 값을 치르는 자리가
어디인지는 이제 이름이 붙었다 — **엔진이 할 말이 없을 때 모델도 할 말이 없어야 하는데,
모델은 그때 말을 만든다.**

### 이 절이 재지 않은 것

**문장이 읽을 만한가는 여전히 모른다.** 여기 있는 숫자는 전부 계약 준수율이다 —
없는 것을 만들지 않았는가, 판정을 뒤집지 않았는가, 길이를 넘지 않았는가. 사회초년생이
그 220자를 읽고 무엇을 해야 하는지 알게 되는가는 다른 질문이고, 이 문서에 아직
답이 없다.

채점을 전부 정규식으로 한 것도 그 한계와 한 몸이다. "이 문장이 근거를 벗어났는가" 를
모델에게 물으면 **지어내는 쪽과 채점하는 쪽이 같은 성질**이 된다. 그래서 재는 자와
막는 자를 같은 함수로 뒀다(`validate_explanation`). 대신 그 함수가 못 보는 것은
이 표에도 없다.

## 14. 지시문 v2 — 겨냥한 곳은 못 맞히고 다른 다섯 곳을 맞혔다 (2026-08-25)

13절이 남긴 숫자는 하나였다. **164건 중 6건에서 근거에 없는 전화번호가 나왔고, 그중
5건은 이미 돈이나 계좌 접근이 넘어간 뒤의 사례였다.** 검사기가 전부 걸러 냈으니
사용자에게 나간 문장은 없지만, 걸러 낸다는 것은 그 5명에게 "왜 위험한지" 가 비어서
나갔다는 뜻이기도 하다.

그래서 지시문을 고쳤다. `fraud_explanation_v1` → `fraud_explanation_v2`.

### 14.1 무엇을 더했나

세 줄이 늘었고, 셋 다 13절에서 실제로 본 실패를 겨냥한다.

| 규칙 | 겨냥한 실패 |
|---|---|
| `[사용자가 받은 문자]` 는 근거가 아니다. 거기 적힌 번호와 기관명은 **보낸 쪽이 고른 값**이다. | 모델이 사기 문자 안의 번호를 그대로 옮기던 것 |
| 세 칸에 전화번호가 없으면 설명에도 쓰지 않는다. 어디로 연락하라고 말하는 대신 **무엇이 정상 절차와 다른지**만 말한다. | 근거가 비었을 때 모델이 빈칸을 채우려 하던 것 |
| 위험 수준이 medium/high 이면 그 문자가 안전하다고 말하지 않는다. | `rejected_contradicts_verdict` |

첫 두 줄은 같은 이야기를 두 각도에서 한 것이다. 하나는 **출처를 부정**하고("문자는
근거가 아니다"), 하나는 **행동을 지정**한다("없으면 안 쓴다, 대신 이것을 써라").
금지만 적으면 모델은 금지된 것을 뺀 자리에 다른 것을 넣는다 — 무엇을 넣을지까지
적어야 그 자리가 채워진다.

v1 은 지우지 않고 `FRAUD_EXPLANATION_PROMPT_V1` 로 그대로 남겼다. **나아졌다는 말은
무엇과 비교했는지가 남아 있을 때만 확인 가능한 주장이다.** 사본이 정확한지는
테스트가 본다 — 계산한 sha256 이 v1 시절에 **먼저 박혀 있던** 값과 맞는지 비교한다.

### 14.2 무엇이 달라졌나

두 홀드아웃 셋(v1.2 80건, v1.3 84건)을 v2 로 다시 태웠고, 같은 조건에서 한 번 더
태웠다. 반복 실행을 한 이유는 14.4 에 있다.

| | v1.2 v1 | v1.2 v2 | v1.2 v2 반복 | v1.3 v1 | v1.3 v2 | v1.3 v2 반복 |
|---|---:|---:|---:|---:|---:|---:|
| 사례 | 80 | 80 | 80 | 84 | 84 | 84 |
| 시도 | 84 | 81 | 81 | 87 | 87 | 84 |
| 설명 나감 | 79 | 79 | 79 | 84 | 84 | 84 |
| 대체 모델 사용 | 4 | 1 | 1 | 3 | 3 | 0 |
| 근거 이탈 | 5 | 2 | 2 | 3 | 3 | 0 |
| **지어낸 연락처** | **5** | **2** | **2** | **2** | **0** | **0** |
| 판정 뒤집기 | 0 / 57 | 0 / 54 | 0 / 54 | 1 / 52 | 3 / 52 | 0 / 49 |
| 안전 필터 차단 | 0 | 0 | 0 | 0 | 0 | 0 |
| 길이 p50 / p95 | 233 / 300 | 217 / 302 | 220 / 292 | 220 / 288 | 201 / 266 | 203 / 267 |

**지어낸 연락처는 164건 7시도 / 6사례에서 2시도 / 1사례로 줄었다.** 두 번 다 같은
값이 나왔고, 두 셋에서 방향이 같다. 남은 1건은 `fh-1007` 하나다.

사라진 다섯 사례는 이렇다.

```
v1.2  fh-1038 [high]  fh-1040 [high]  fh-1065 [high]
v1.3  fh-1147 [high]  fh-1170 [high]
```

전부 `high` 이고, 13절이 "돈이나 계좌 접근이 이미 넘어간 뒤" 라고 적은 그 사례들이다.
이 다섯은 **주 모델이 거부당하고 대체 모델이 받아 준** 자리였다 — 즉 v1 에서도
사용자에게 나간 문장은 안전했지만, 그 안전이 검사기와 재시도 한 번으로 산 것이었다.
v2 에서는 처음부터 나오지 않는다. 대체 모델 사용이 4→1, 3→0 으로 줄어든 것이 같은
사실의 다른 면이다.

### 14.3 겨냥한 한 건은 못 고쳤다

두 번째 규칙("세 칸에 전화번호가 없으면 쓰지 않는다")은 **`fh-1007` 을 보고 쓴
문장이다.** 그리고 `fh-1007` 은 그대로 남았다. 주 모델과 대체 모델이 여전히 둘 다
거부당한다.

왜인지 보려고 같은 사례를 다시 불러 봤다.

```
gemini-3.6-flash        → rejected_invented_contact   걸린 토큰: 112
  "…경찰청 112 신고 관련 처리가 진행 중임을 알리는 일반적인 안내 문자입니다."

gemini-3.1-flash-lite   → rejected_invented_contact   걸린 토큰: 112
  "해당 문자는 112 신고 접수 결과에 대한 안내로 확인됩니다."
```

**모델은 어디로 연락하라고 말하고 있지 않다. 이 문자가 무엇인지 말하고 있다.**
지시문은 "연락처를 쓰지 말라" 고 했고 모델은 연락처를 쓰지 않았다 — `112` 는 설명
대상의 이름으로 들어가 있다.

검사기(`_CONTACT_PATTERN`)는 문장 어디에 있든 `1\d{2,3}` 을 잡는다. **"112 로
전화하세요" 와 "이것은 112 안내입니다" 를 구분할 수 없다.** 구분하려면 문장의
의도를 읽어야 하고, 그것은 정규식이 하는 일이 아니다.

### 14.4 그래서 검사기를 느슨하게 하지 않는다

여기서 손대고 싶은 자리는 검사기다. "안내입니다" 같은 서술형 문맥을 예외로 두면
`fh-1007` 이 통과하고 표의 마지막 1건이 사라진다.

하지 않는다. **두 방향의 오류가 같은 값이 아니기 때문이다.**

- 잘못 거부하면 → 사용자가 설명 문장 하나를 못 본다. 위험 수준·신호·행동·근거는
  그대로 나간다. 잃는 것은 문장 하나다.
- 잘못 통과시키면 → 사기범이 고른 번호가 "공식 안내" 의 얼굴로 사용자에게 간다.
  잃는 것은 사용자다.

한쪽 비용이 다른 쪽보다 압도적으로 크면, **모호한 자리는 비싼 쪽을 피하는 방향으로
닫아야 한다.** 표의 숫자를 예쁘게 만들려고 검사기를 여는 것은 정확히 반대 방향이다.

고칠 자리는 프롬프트도 검사기도 아니다. **근거가 비었을 때 모델에게 문장을 요구하는
것 자체가 잘못된 요청이다.** `build_grounded_text` 가 `- 없음` 세 줄이면 모델이 무엇을
쓰든 정의상 근거 밖이고, 지시문으로 그 사실을 바꿀 수는 없다. 13절이 "엔진이 할 말이
없을 때 모델도 할 말이 없어야 하는데, 모델은 그때 말을 만든다" 고 적은 자리다.

그래서 다음 회차는 **근거가 비면 아예 부르지 않는 것**이다. 실패가 아니므로 거부도
차단도 아닌 결과 이름이 하나 더 필요하고(`SKIPPED_NO_EVIDENCE` 류), `explained_rate`
의 분모를 어떻게 할지도 정해야 한다. 이번에 같이 넣지 않은 이유는 하나다 — **한
회차에 한 변경.** 지시문과 건너뛰기를 함께 넣으면 줄어든 숫자가 어느 쪽 덕인지 아무도
말할 수 없다.

### 14.5 반복 실행이 말해 준 것

v1.3 에서 `rejected_contradicts_verdict` 가 1 → 3 으로 **늘었다.** 판정 뒤집기를
막으려고 규칙을 추가한 회차에서 그 지표가 나빠졌으니, 그대로 두면 "v2 가 판정
뒤집기를 악화시켰다" 는 문장이 표에서 저절로 읽힌다.

확인해 봤다.

- 걸린 세 사례(`fh-1124`, `fh-1129`, `fh-1164`)를 각각 5번씩, 총 15번 다시 불렀다 →
  **0건 재현.**
- 같은 셋을 통째로 한 번 더 태웠다 → **0 / 49.**

`temperature=0.0` 은 결정론을 보장하지 않는다. 그리고 이 표의 값들은 한 자릿수다.
**1 과 3 의 차이에 이야기를 붙이기 전에, 같은 조건이 저절로 얼마나 움직이는지를 먼저
봐야 한다.** 그래서 반복 실행 파일을 저장소에 같이 넣는다 — 다음에 누가 이 표를
읽을 때, 한 칸의 변화가 신호인지 잡음인지 판단할 재료가 파일로 남아 있어야 한다.

같은 잣대를 개선 쪽에도 댄다. 지어낸 연락처 5→2, 2→0 은 **두 실행에서 같은 값**이고
두 셋에서 방향이 같다. 이쪽은 잡음으로 설명되지 않는다.

### 14.6 곁가지로 확인된 것

- **문장이 짧아졌다.** p50 233→217, 220→201. 제약을 더하면 모델이 말을 줄인다.
  600자 상한에서 한참 아래이므로 잘린 것이 아니다. 다만 **짧아진 것이 더 읽기 쉬워진
  것인지는 이 표가 답하지 않는다.**
- **안전 필터 차단은 네 실행 모두 0.** 9절이 가장 오래 들고 있던 걱정(사기 문자를
  분석하려다 안전 필터에 막힌다)은 328시도째에도 한 번도 일어나지 않았다.
- **대체 모델 호출이 줄어 비용도 줄었다.** 설계 목적은 아니지만 사실이다.

### 14.7 벤치마크가 스스로 낡았다고 말한다

`_explanation_layer` 가 지시문 sha256 도 본다. 셋이 같아도 배포된 지시문과 다르면
`stale` 이다.

이 검사가 없었다면 이번 회차에서 정확히 이런 일이 일어났을 것이다 — 프롬프트를 v2 로
바꾼 뒤에도 보고서가 v1 의 숫자를 `measured` 로 계속 내놓고, 그 표를 읽는 사람은
그것이 낡았다는 사실 자체를 알 수 없다. 결과 파일 이름에도 지시문 판을 넣은 것이 같은
이유다(`…-prompt-v1.json` / `…-prompt-v2.json`). **덮어썼다면 13절이 인용하는 값이
조용히 사라지고, 문서가 없는 숫자를 가리켰을 것이다.**

### 이 절이 재지 않은 것

13절의 한계는 그대로다 — 문장이 **읽을 만한가**는 여전히 모르고, 채점은 전부
정규식이다. 여기에 하나가 더해졌다. **`fh-1007` 이 알려 준 것은 검사기가 "의도" 를
못 본다는 사실이고, 그 눈먼 자리는 지금 거부 쪽으로만 기울어 있다.** 반대쪽, 즉
검사기가 놓치고 통과시키는 문장이 있는지는 이 표에 없다. 그것을 재려면 정규식이 아닌
잣대가 필요하고, 그 잣대를 모델로 만들면 13절이 거부한 자리로 돌아간다.

## 15. 근거가 비면 부르지 않는다 (2026-08-25)

14.4 가 커밋된 문장으로 적어 둔 자리다. **고칠 곳은 프롬프트도 검사기도 아니고, 근거가
빈 채로 모델에게 문장을 요구하는 것 자체다.** 이번 회차는 그것만 바꿨다. 엔진도 셋도
지시문도 모델도 그대로다.

### 15.1 규칙은 한 줄이고, 판단 근거는 근거 자체다

```python
def has_grounded_evidence(response: AnalyzeResponse) -> bool:
    return any(block != _EMPTY_BLOCK for block in _grounded_blocks(response))
```

`_grounded_blocks` 는 프롬프트에 실제로 들어가는 세 블록(위험 신호 · 권고 행동 · 공식
근거)을 만드는 바로 그 함수다. 셋이 전부 `- 없음` 이면 모델이 무엇을 쓰든 정의상 근거
밖이므로, 그 상태에서 문장을 요구하지 않는다.

**`risk_level == "low"` 으로 분기하지 않았다.** 이 두 셋에서는 둘이 정확히 같은 집합을
가리키지만(15.8), 같은 값이라는 것과 같은 뜻이라는 것은 다르다. 프롬프트에 들어가는
것은 등급이 아니라 블록이고, 판단은 **모델에게 실제로 건네지는 것**을 보고 해야 한다.
등급으로 분기해 두면 `low` 인데 신호가 하나 붙는 조합이 생기는 날 조용히 설명을 잃는다.

같은 이유로 `_EMPTY_BLOCK` 을 상수로 올려 `_grounded_blocks` 안에서 쓰게 고쳤다. 처음
쓴 판은 블록 생성 쪽에 `"- 없음"` 리터럴이 세 번, 판정 쪽에 상수가 한 번 있었다.
**한쪽만 고쳐지는 날 이 함수는 조용히 거짓말을 한다.**

### 15.2 실패가 아닌 결과에 이름을 붙였다

`ExplanationOutcome.NOT_ASKED_NO_EVIDENCE`. 12절이 만든 닫힌 어휘에 한 칸을 더했지만
자리는 따로 뒀다 — **거부도 차단도 아니다.** 거부는 모델이 말을 했는데 우리가 막은
것이고, 차단은 프로바이더가 막은 것이다. 이건 아무도 말을 하지 않은 것이다.

셈에서도 갈라 둔다.

- **결과(result)** 로는 센다. 그런 판정이 몇 건인지는 알아야 한다.
- **시도(attempt)** 로는 세지 않는다. 호출이 없었으므로 지연도 사유도 없다.

`ProbeCase` 에 불변식을 박아 이 둘이 어긋나지 못하게 했다.

```python
@model_validator(mode="after")
def _attempts_match_asked(self) -> ProbeCase:
    if bool(self.attempts) is not self.asked:
        raise ValueError(...)
```

물어보지 않았다고 적힌 사례가 시도를 들고 있거나, 물어봤다는 사례에 시도가 없으면 파일
자체가 안 읽힌다. 12절이 `ExplanationAttempt` 에 건 것과 같은 종류의 장치다 —
**타입이 거짓말을 못 하게.**

### 15.3 분모는 물어본 건수다

`explained_rate` 와 `fallback_rate` 의 분모를 `cases` 에서 `asked` 로 바꿨다.

바꾸지 않았다면 이번 표의 v1.3 이 **0.5833** 으로 찍힌다. 아무것도 실패하지 않은
회차에서. 부르지 않은 35건을 "설명이 나가지 못한 사례" 로 세는 것이기 때문이다.
**비율이 재는 것은 물어본 것 중 몇이 답을 받았는가이지, 세상의 몇 퍼센트가 설명을
받았는가가 아니다.** 후자를 알고 싶으면 `not_asked_rate` 를 같이 보면 된다 — 그래서 그
값도 보고서에 넣었다.

이건 11절이 `rejected_contradicts_verdict` 의 분모를 medium/high 로 좁힌 것과 같은
결정이다. **검사가 돌지 않은 자리를 분모에 넣으면 그 비율은 검사에 대해 아무 말도 하지
않는다.**

### 15.5 유료 호출이 37.5% 줄었고, 잃은 것은 없다

시도 **168 → 105**. v1.2 는 81→55, v1.3 은 87→50 이다.

비용 절감은 설계 목적이 아니었다. 목적은 지어낸 번호였고, 줄어든 호출은 그 규칙의 다른
면이다 — **근거가 없어서 모델이 말을 만들던 자리가 곧 부를 필요가 없던 자리였다.**

잃은 것이 없다고 말할 수 있는 이유는 그 61건에서 화면이 비지 않기 때문이다. "왜
위험한지" 블록은 결정론 요약(`verdict.summary`)이 먼저 채우고, 모델 문장은 그 아래
"쉬운 말로 다시 설명하면" 에 붙는다(10절). 근거가 없다는 것은 요약이 이미 "명시적인
위험 신호가 확인되지 않았습니다" 를 말하고 있다는 뜻이고, **거기에 모델이 덧붙일 수
있는 것은 정의상 근거 밖의 문장뿐이다.**

그리고 `fh-1007` 이 사라졌다. 13절이 "164건 중 유일하게 설명이 안 나간 사례" 로
적었고, 14절이 그 한 건을 겨냥해 쓴 규칙으로 못 고쳤고, 14.4 가 "검사기를 열어서
지우지 않는다" 고 적은 그 건이다. **검사기는 그대로인데 사라졌다** — 애초에 물어보지
않게 됐기 때문이다.

### 15.6 화면에는 상태가 세 개 필요했다

`ExplanationResponse` 에 `asked` 를 더했다.

| 응답 | 뜻 | 화면 |
|---|---|---|
| `available: false` | 설명 계층이 꺼진 배포다 | 안 그린다 |
| `available: true, asked: false` | 물어볼 근거가 없어 부르지 않았다 | 안 그린다 |
| `available: true, asked: true, explanation: null` | 물어봤는데 문장을 못 받았다 | "불러오지 못했습니다" |

10절이 `off` 와 `failed` 를 나눈 것과 같은 이유가 한 겹 더 생겼다. **`explanation ===
null` 하나로 뭉치면 이 164건 중 61건에서 화면이 "설명을 불러오지 못했습니다" 라고
말한다. 아무것도 실패하지 않았는데.** 37%의 사용자에게 제품이 스스로 고장 났다고
보고하는 셈이다.

앞의 둘은 화면에서 똑같이 아무것도 그리지 않는다. 그래도 합치지 않았다 — 같은 모양인
것과 같은 일인 것은 다르고, 한쪽만 다르게 그려야 하는 날 합쳐 둔 것을 다시 갈라내야
한다. `asked` 의 기본값을 `true` 로 둔 것은 이 필드가 없던 백엔드와도 맞물리기
위해서다. 배포 순서가 어긋난 잠깐 동안 없던 상태가 생기지 않는다.

### 15.7 호출 정책도 구성의 축이다

`ExplanationProbeRun` 에 `call_policy` 를 넣고, 벤치마크가 그것도 본다.

```python
if probe.call_policy != EXPLANATION_CALL_POLICY:
    return {..., "status": "stale", "reason": "설명 계층 실행이 다른 호출 정책에서 나왔다."}
```

14.7 이 지시문 sha256 으로 한 일과 같다. 셋도 지시문도 같은데 표만 다른 실행이 이번에
실제로 생겼다 — 호출이 37% 줄고, 운영에서는 일어나지 않을 거부(`fh-1007`)가 옛 표에는
남아 있다. **이 필드가 없으면 보고서가 그 옛 표를 `measured` 라고 부른다.**

낡음을 판별하는 검사를 회차마다 새로 짜지 않으려면 규칙이 하나 필요하다 — **구성의 각
축이 실행 파일 안에 이름으로 남아 있어야 한다.** 지금 세 축이다: 셋 sha, 지시문 sha,
호출 정책.

여기서 한 번 잘못 갈 뻔했다. 새 필드가 생기자 `test_no_explanation_text_was_committed`
가 여섯 개의 옛 파일에서 깨졌다. 저장된 키 집합이 스키마와 정확히 같은지 보는 검사이고,
모델 문장이 저장소에 섞여 들어오지 못하게 막는 자리다. `==` 를 `<=` 로 풀면 즉시
초록이 된다. **하지 않았다.** 스키마가 늘어난 것을 이유로 개인정보 가드를 느슨하게
하는 것은 방향이 반대다. 대신 옛 파일 여섯 개에 `"call_policy": "ask_always"` 를
채웠다 — **그 실행들이 실제로 그 정책에서 나왔으므로 이건 참인 값이다.** 넣기 전에
읽고 다시 쓴 결과가 바이트 단위로 같은지 먼저 확인했고, diff 는 정확히 6줄 삽입이다.

### 15.8 `low` ⟺ 근거 없음 은 이 두 셋의 사실이지 규칙이 아니다

두 셋 164건을 갈라 보면 이렇다.

| | 근거 있음 | 근거 없음 |
|---|---:|---:|
| `low` | **0** | 61 |
| `medium` | 64 | 0 |
| `high` | 39 | 0 |

정확히 겹친다. 그래도 규칙은 근거를 보고, 테스트가 그 갈라짐을 못으로 박아 둔다 —
`low` 이면서 신호가 하나 붙은 판정을 합성해 넣고 **불렀는지** 확인한다. 이 표가 오늘의
엔진에 대한 관찰이지 계약이 아니라는 사실을, 나중에 코드를 읽는 사람이 표가 아니라
테스트에서 알 수 있어야 한다.

### 이 절이 재지 않은 것

- **문장이 길어진 것(p50 217→242, 201→231)은 품질 이야기가 아니다.** 남은 사례가
  근거가 많은 쪽으로 쏠렸으므로 모집단이 바뀐 결과다. 같은 사례들의 문장이 길어졌는지는
  이 표가 답하지 않는다.
- **지연은 두 셋에서 반대로 움직였다.** v1.2 주 모델 p50 6535→2866ms, v1.3
  6194→7114ms. 우리가 바꾼 것으로 설명되지 않는다 — 이 회차에 지연에 대해 할 수 있는
  말은 없다.
- **셋당 한 번씩만 태웠다.** "설명 100% / 지어낸 번호 0" 은 통계가 아니라 구조다 —
  부르지 않은 호출은 번호를 지어낼 수 없고, 남은 호출은 근거를 들고 있다. 반대로
  `rejected_contradicts_verdict` 의 0→1, 3→1 은 14.5 가 잰 자체 변동폭(같은 조건 15회
  재호출 0건 재현, 반복 실행 0/49) 안이므로 **이 회차의 효과로 읽지 않는다.**
- **그 61건에서 결정론 요약만으로 충분한가는 아직 모른다.** 화면이 비지 않는다는 것은
  확인했지만, 사회초년생이 그 요약을 읽고 무엇을 해야 하는지 아는가는 13절·14절과
  똑같이 숫자가 없다.
- 14절이 남긴 눈먼 자리는 그대로다. **검사기가 놓치고 통과시키는 문장**은 여전히 이 표에
  없다.
## 16. 안 부른 자리에 무엇이 남는가 (2026-08-27)

15절이 재지 않았다고 이름만 적어 둔 것을 쟀다 — **그 61건에서 결정론 요약만으로

### 16.1 61건이 받는 문장은 한 가지다

## 17. 통과한 문장은 아무도 안 봤다 (2026-08-27)

`docs/10` 이 오래 들고 있던 항목이 하나 있었다.

> 출력 검증이 거부한 건수(`rejected_*`)는 세지만, **통과한 문장이 근거에 붙어
> 있는지는 아무도 안 본다.**

이 항목은 판정자가 필요해 보였다. 근거 이탈률을 재려면 문장이 근거에 붙어
있는지 판단할 무언가가 있어야 하고, 그건 유료 호출이다. 그래서 계속 밀렸다.

그런데 재는 것과 **막는 것**은 다른 일이다. 막는 쪽은 지금 코드에 무엇이
있는지만 보면 되고, 그건 유료 호출이 필요 없다.

### 검증기가 근거와 대조하는 것은 하나뿐이었다

`validation.py` 가 보던 것:

| 검사 | 근거와 대조하는가 |
|---|---|
| 비어 있음 | — |
| 길이 상한 | — |
| URL | 아니오 (있으면 무조건 거부) |
| 주민등록번호 | 아니오 (있으면 무조건 거부) |
| 판정을 뒤집는 안심 문구 | 아니오 (형태만) |
| 연락처 | **예** |

근거에서 파생한 허용 목록에 대조하는 검사는 **연락처 하나**였다. 파일의 독스트링
자체가 그걸 인정하고 있었다: "한계도 분명하다. 이것은 사실 검증기가 아니다."

한편 `CLAUDE.md` 의 비협상 조항은 이렇게 적혀 있다.

> **Never fabricate products, rates, eligibility, laws, institutions, or
> official guidance.**

여섯 가지 중 출력 쪽에서 강제되던 것은 **0개**였다. 연락처는 그 목록에 없다.

### 18건을 넣어 봤다

근거에 없는 기관·법령·기한·비율·상품·절차·적격성을 지어낸 문장 18개를 만들었다.
전부 연락처도 URL도 주민등록번호도 안심 문구도 없다 — 즉 기존 검사 다섯 개가
잡을 만한 것이 하나도 없는 문장들이다.

**18개가 모두 통과했다.**

```
전기통신금융사기 피해 방지 특별법 제17조에 따라 …   PASSED
국가금융안전센터에 신고하시면 …                     PASSED
피해 신고는 사고 발생 후 72시간 이내에만 접수됩니다.  PASSED
정부 지원 서민 대출은 연 2.5퍼센트 금리로 …         PASSED
본인 과실이 없으므로 은행이 손실을 부담하게 됩니다.   PASSED
```

유료 호출은 0회다. 이건 모델이 실제로 저런 문장을 쓰는지에 대한 측정이 아니라,
**쓰면 그대로 나간다**는 코드에 대한 측정이다.

### 발상은 이미 파일 안에 있었다

연락처 검사가 하는 일은 "근거에서 허용 목록을 만들고 거기 없는 것을 거부한다"
이다. 그 발상은 옳고, 좁았던 것은 **대상**이었다. 그래서 같은 모양을 기관 이름,
법령 인용, 숫자 주장, 결과 약속에 그대로 폈다.

| 검사 | 허용 목록 | 사유 값 |
|---|---|---|
| 기관 이름 | 근거 | `rejected_ungrounded_org` |
| 법령 인용 | 없음 (있으면 거부) | `rejected_law_citation` |
| 비율·기한·건수 | 근거 **+ 문자 원문** | `rejected_ungrounded_number` |
| 결과 약속 · 적격성 단정 | 없음 (단정형이면 거부) | `rejected_ungrounded_promise` |

### 분모가 어디까지인가 — 코드를 쓰기 전에 걸린 문제

숫자의 허용 목록을 근거로만 두면 이 문장이 죽는다.

```
문자는 24시간 이내에 처리하지 않으면 압류한다고 압박하고 있습니다.
```

`24시간 이내` 는 **사기 문자가 쓴 말**이다. 설명은 그걸 지목해야 하고, 지목하는
것은 지어내는 것이 아니라 설명해야 할 대상이다. 근거에는 그런 숫자가 없다 —
근거는 신호·행동·출처 세 블록뿐이고 문자 원문은 안 들어간다.

문자를 허용 목록에서 빼고 재 봤다.

| 문장 | 문자 포함 | 문자 제외 |
|---|---|---|
| 문자는 24시간 이내에 … 압박하고 있습니다 | 통과 | **거부** |
| 24시간 이내라는 기한을 앞세워 … | 통과 | **거부** |
| 처리율 100퍼센트를 보장한다는 표현은 … | 통과 | **거부** |
| 350만 원을 특정 계좌로 납부하라는 요구는 … | 통과 | 통과 |

**넷 중 셋이 죽는다.** 그래서 숫자의 허용 목록은 근거 + 문자다.

### 연락처만은 반대다

같은 논리를 연락처에 적용하면 안 된다. 사기 문자에 `02-9999-8888` 이 적혀
있다고 해서 우리 설명이 그 번호를 되읽으면, 검증기가 **사기범의 번호에 정당성을
붙여 주는** 꼴이 된다. 사용자가 그 번호로 전화를 건다.

그래서 이 계층에는 방향이 반대인 두 허용 목록이 있다.

- 숫자: 근거 + 문자 (문자를 되읽는 것이 **일**이다)
- 연락처: 근거만 (문자를 되읽는 것이 **사고**다)

비대칭은 빠뜨린 것이 아니라 규칙이고, 테스트가 양쪽 방향을 다 지킨다.

### 재고 나서 고친 것 둘

**정규화가 구두점을 남기고 있었다.** 설계 측정에서 정상 문장 하나가 죽었다.

```
경찰청 사이버범죄 신고시스템에 신고하실 수 있습니다.   ← 거부됨
```

근거에는 `- 경찰청: 사이버범죄 신고시스템` 으로 들어 있다. 공백만 지우면 콜론이
남아 `경찰청:사이버범죄신고시스템` 과 `경찰청사이버범죄신고시스템` 이 다른
문자열이 된다. **실재하는 공식 창구를 정확히 안내한 문장**이 죽은 것이고, 고칠
곳은 규칙이 아니라 정규화였다. 이 검사 전체에서 나온 오거부는 이것 하나였다.

**건수 규칙에서 금액을 뺐다.** `건|명` 만 본다. 금액은 문자에 `200만원`, 설명에
`200만 원` 으로 갈리는데 정규화로 붙일 수 있는 것은 공백까지이고 `이백만원` 까지는
못 붙인다. 지어낸 통계는 거의 언제나 건수·인원으로 오므로 금액을 빼도 잡을 것은
잡는다. 실제로 `1만 2천 건` 은 여전히 걸린다.

### 꼬리로 기관을 잡되 청·원은 못 쓴다

기관 이름을 형태로 잡으려면 꼬리가 필요한데, `청` 과 `원` 은 쓸 수 없다.
요청·신청·지원·직원·병원이 같은 꼬리를 갖는다. `저` 지시관형사를 제외했던
것(15절)과 같은 모양의 문제다.

그래서 기관에만 붙는 꼬리만 남겼다: 센터·위원회·공단·공사·진흥원·감독원·
보안원·수사대·협회·거래소·포털·신고시스템·지킴이. `금융감독원` 처럼 `원` 으로
끝나는 기관은 더 긴 꼬리(`감독원`)로 잡는다. 여기에 일반명사 꼬리 제외 목록을
붙였다 — `은행 고객센터에 문의하세요` 는 특정 기관을 지목한 것이 아니라 사용자가
이미 아는 창구를 가리키는 말이다.

### 결과

| | 변경 전 | 변경 후 |
|---|---:|---:|
| 지어낸 문장 18건 중 통과 | **18** | **3** |
| 정상 문장 37건 중 거부 | 0 | **0** |

정상 문장 37건에는 문자의 숫자를 되읽는 4건과 `보장`·`대상` 을 인용하되 단정하지
않는 6건이 들어 있다. 검사를 넓힐 때마다 이 저장소가 지키는 순서 그대로,
**값을 치를 문장을 테스트 파일 맨 앞에 놓았다.**

### 안 잡히는 3건 — 통과를 요구하는 테스트로 적어 뒀다

```
경찰청은 이 수법을 올해 최다 피해 유형으로 지정했습니다.
청년 안심 전환 대출로 갈아타시면 이자 부담을 줄일 수 있습니다.
통신사 대리점에서 명의도용 차단 서비스를 무료로 신청할 수 있습니다.
```

실재하는 기관에 지어낸 발표를 붙인 문장, 지어낸 상품명, 지어낸 절차다. 셋 다
형태가 정상 문장과 같아서 형태 규칙으로는 닿지 않는다. 첫 번째가 특히 그렇다 —
기관 이름은 근거에 있고, 틀린 것은 **그 기관이 했다고 한 말**이다.

이 셋은 `test_what_the_grounding_checks_still_do_not_catch` 에 통과를 요구하는
테스트로 들어 있다. 통과가 옳다고 주장하는 것이 아니라 **무엇이 남았는지를 코드
안에 적어 두는 것**이다. 나중에 규칙이 늘어 하나가 잡히면 그 테스트가 실패하고,
그 실패가 곧 진전이다.

**이것은 여전히 사실 검증기가 아니다.** 15/18 은 18/18 보다 낫지만 18/18 이
아니고, 남은 셋은 규칙으로 좁힐 수 있는 종류가 아니다.

### 이 절이 재지 않은 것

- **모델이 실제로 저런 문장을 쓰는 비율.** 이 절은 "쓰면 나간다" 를 재고 고쳤을
  뿐이고, 얼마나 쓰는지는 유료 실행 한 번이 있어야 안다. 새 사유 네 칸이
  `/internal/metrics` 에 이미 붙어 있으므로 그 실행에서 바로 읽힌다.
- **근거 이탈률.** `docs/10` 항목의 나머지 절반이다. 통과한 문장이 근거에 붙어
  있는지를 **판단**하려면 여전히 판정자가 필요하다. 이번에 한 것은 판단이 아니라
  거름이다.
- 새 검사가 정상 운영에서 오거부를 내는 비율. 37건은 우리가 쓴 문장이고, 모델이
  쓰는 문장은 아니다.

## 18. 안 잰다고 적어 둔 칸이 26.9% 였다 (2026-09-04)

17절의 마지막 줄은 이렇게 끝난다.

> 새 검사가 정상 운영에서 오거부를 내는 비율. 37건은 우리가 쓴 문장이고,
> **모델이 쓰는 문장은 아니다.**

여드레 뒤에 그 칸을 쟀다. **26.9% 였다.**

### 어떻게 발견했나 — 제출용 시연 입력을 찍다가

공모전 기능명세서에 "심사자가 배포 URL 에서 이렇게 확인한다" 를 쓰려면 예상
결과를 지어낼 수 없다. 그래서 공개 URL 에 실제로 넣어 보고 돌아온 답을 적기로
했고, 첫 입력이 이것이었다 — 검찰 사칭 + 고립 요구 + 원격 앱 + 송금 요구가
한 문장에 다 들어 있는, 이 서비스의 대표 시연 입력.

```
POST https://finshield-ai.duckdns.org/api/proxy/analyze/explanation
→ 200, {"status":"failed","text":null,"model":null}   (11.7초)
```

판정은 정상이었다(`level: high`, 신호 4종, 행동 5건, 출처 3건). **설명만
죽었다.** 그것도 주 모델과 대체 모델이 **둘 다.**

### 사유는 유료 호출 없이 재현됐다

로컬에서 같은 입력을 태우니 두 모델 다 `rejected_ungrounded_org` 였다. 검사가
지목한 이름을 찍어 보고 원인이 드러났다.

| 모델 | 검사가 "근거에 없다" 고 지목한 이름 |
|---|---|
| 주 모델 | `필요하다면보이스피싱통합신고대응센터` |
| 대체 모델 | `나한국인터넷진흥원` |

**두 기관 다 근거 안에 있다.** 보이스피싱 통합신고대응센터는 1순위 행동이고,
한국인터넷진흥원은 공식 출처 두 건의 발행 기관이다. 모델은 지어내지 않았다.
지어낸 것은 우리 정규식이다.

`_ORG_PATTERN` 은 기관 꼬리 앞의 어절을 **세 개까지 함께 삼킨다.** 이름 앞에
보통 낱말이 오면 — "필요하다면 보이스피싱 통합신고대응센터", "1394나 한국인터넷
진흥원" — 잡힌 덩어리가 근거에 없는 문자열이 되고, 근거에 **있는** 기관을 부른
문장이 지어낸 것으로 거부된다.

앞 어절을 함께 삼키는 것 자체는 필요하다. `국세청 사기방지센터` 를 잡으려면
`사기방지센터` 만 봐서는 안 된다. 틀린 것은 **삼킨 덩어리를 통째로 근거에
대조한 것**이다.

### 왜 테스트 61개가 이것을 못 잡았나

정상 문장 37개를 먼저 놓는 순서는 지켰다. 그런데 **37개가 전부 기관 이름을 절
맨 앞이나 쉼표 바로 뒤에 두고 있었다.**

```
"보이스피싱 통합신고대응센터에 상담하시면 대응 절차를 안내받을 수 있습니다."
"경찰청 사이버범죄 신고시스템에 신고하실 수 있습니다."
"금융보안원 안내에 따르면 이런 요청은 정상 절차에 없습니다."
```

세 문장 다 앞에 삼킬 어절이 없다. 규칙이 안전해서 통과한 것이 아니라
**셋이 그 질문을 한 적이 없다.** 판정 엔진 쪽에서 같은 문장을 이미 적어 뒀다
(`docs/35` 7.2-b) — 셋이 조용한 것은 안전하다는 뜻이 아니라 셋이 안 물어봤다는
뜻이다. 이번에는 설명 계층에서 같은 일이 일어났고, 다른 점은 **이번 것은 운영에
나가 있었다**는 것이다.

### 고친 규칙

통과하는 길을 둘로 나눴다. 둘 다 좁다.

1. 잡힌 덩어리 **전체**가 근거 안에 있다 (기존 규칙 그대로).
2. 덩어리의 **어절 경계 뒷조각 하나가 근거의 온전한 기관 이름과 같다.**

2번을 부분 문자열이 아니라 **일치**로 둔 것이 이 회차가 치른 값이다. 부분
문자열로 열었다면 `국세청 신고시스템` 이 근거의 `사이버범죄 신고시스템` 안에
`신고시스템` 이 들어 있다는 이유로 통과했을 것이고, 사용자는 국세청이 운영하는
창구가 있다고 읽는다. 앞에 무엇이 붙어 있든 **뒷조각이 근거의 이름과 같아야
한다.**

거부 쪽 테스트에 두 줄을 그래서 새로 넣었다 — `국세청 신고시스템`,
`국세청 통합신고대응센터`. 둘 다 고치기 전에도 거부됐지만, **고친 규칙이
느슨해지면 처음 통과할 문장**이다.

### 잰 숫자 — held-out 두 셋, 유료 1회

같은 유료 호출 한 번에서 옛 규칙과 새 규칙을 **메모리 안에서 둘 다** 돌렸다.
모델 문장은 저장하지도 출력하지도 않는다(ADR 0006).

| 셋 | 물어본 건수 | 옛 규칙의 오거부 | 비율 |
|---|---:|---:|---:|
| held-out v1.2 | 55 | **17** | 30.9% |
| held-out v1.3 | 49 | **11** | 22.4% |
| 합계 | 104 | **28** | **26.9%** |

고친 뒤 주 모델 성공은 v1.2 51/55, v1.3 46/49 다. 진짜 거부는 그대로 남아
있다 — 기관 5건, 법령 1건, 지어낸 연락처 1건. **오거부만 사라졌다.**

숫자 하나를 더 적어 둔다. 옛 규칙에서 저 28건은 주 모델이 거부된 뒤 **대체
모델을 한 번 더 부른다.** 대체 모델도 같은 규칙에 걸리므로(대표 시연 입력이
그랬다) 그 호출은 대부분 그냥 버려졌다. 이 결함은 화면만 죽인 것이 아니라
**호출을 두 배로 태우고 있었다.**

### 이 절이 재지 않은 것

- **개발셋 61건과 나머지 열 셋.** 두 셋 104건으로 방향과 크기는 충분히 정해졌고,
  전 셋 재측정은 유료 예산의 문제다.
- **고친 규칙의 오거부율.** 0 이라고 주장하지 않는다. 이번에 잰 것은 "옛 규칙이
  몇 건을 잘못 죽였나" 이고, 새 규칙이 남긴 5건이 전부 정당한 거부인지는
  문장을 읽어야 아는 일이다.
- **저장된 프로브 결과 파일.** `evaluation/results/` 의 여덟 개는 2026-08-25 —
  기관·법령·숫자·약속 검사가 **들어오기 전**의 실행이다. 그래서 그 파일들에
  `rejected_ungrounded_org` 가 한 건도 없고, 그 사실이 이 결함을 여드레 동안
  가렸다. 검사를 넓힌 회차가 프로브를 다시 돌리지 않으면, 저장된 표는 새 검사에
  대해 **아무 말도 하지 않으면서 최신처럼 보인다.**
