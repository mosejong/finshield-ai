- 이미 송금·정보 제공을 한 사용자에게는 예방이 아니라 수습 순서로 화면이 전환된다.

  만들지 않는다.

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

[ 문제 ]

금융 사기 대응에서 가장 어려운 순간은 사기를 몰라서가 아니라, 문자를 받은 그
3분 동안 물어볼 사람이 없어서 생긴다.

사기 문자는 세 가지를 동시에 한다. 기관을 사칭해 권위를 만들고, "수사기밀이니
가족에게도 알리지 마라" 로 확인 경로를 끊고, 시간을 압박해 판단을 못 하게 한다.
마지막 것이 핵심이다. 피해자는 판단력이 없는 사람이 아니라, 확인할 곳을
차단당한 사람이다.

기존 대응 수단은 이 순간에는 잘 닿지 않는다.

- 예방 캠페인·교육 : 문자를 받기 전에 도착한다. 정작 받은 뒤에는 기억나지
  않는다.
- 스팸 차단 앱 : 발신번호·URL 기반이라 번호가 깨끗한 신종은 지나간다.
- 기관 상담 전화 : 연결까지 시간이 걸리고, "이게 전화할 일인가" 를 먼저
  판단해야 한다.
- 검색 : 검색어가 곧 사기 문구라 무엇이 공식 안내인지 가려내기 어렵다.
- 주변에 물어보기 : 사기 문자가 가장 먼저 끊는 것이 바로 이 경로다.

그리고 이미 넘어간 사람이 설 자리는 드물다. 대부분의 안내가 "이런
문자를 받으면 응하지 마세요" 에서 끝난다. 이미 응한 사람은 지급정지·신고·
명의보호를 어떤 순서로 해야 하는지 모른 채, 가장 급한 순간에 검색을 시작한다.

[ 왜 사회초년생인가 ]

- 금융 경험의 표본이 적다. "은행이 원래 이렇게 하나?" 를 판단할 기준선이 없다.
  기관 사칭이 통하는 이유는 지식 부족이 아니라 비교 대상 부족이다.
- 첫 대출·첫 전세·첫 카드가 동시에 온다. 금융 결정의 밀도가 가장 높은 시기에
  경험은 가장 얕다.
- 물어볼 상대가 제도가 아니라 사람이다. 사기 문자의 고립 요구가 정확히 그
  사람을 끊는다.
- 손실의 절대액이 작아도 회복 기간이 길다. 같은 300만 원이 자산 대비 비중과
  회복 시간에서 전혀 다른 사건이 된다.

[ 왜 문자·메신저 채널인가 ]

- 사기의 첫 접점이 문자·메신저인 경우가 많다. 전화로 넘어가기 전에 문자가
  먼저 오는 형태가 흔하다.
- 텍스트는 붙여넣을 수 있다. 통화 녹음·화면 캡처보다 진입 장벽이 압도적으로
  낮고, 그 낮은 장벽이 "3분 안에" 를 가능하게 한다.
- 스마트폰 문자 앱의 공유 시트에 직접 붙을 수 있다(PWA 공유 타깃 구현 완료).
  앱 전환 없이 받은 문자를 그대로 넘길 수 있다.

[ 왜 지금 생성형 AI 인가, 그리고 왜 AI 만으로는 안 되는가 ]

사기 문자는 문구가 매번 바뀐다. 키워드 차단이 못 따라가는 이유이고, 언어를
이해하는 모델이 필요한 이유다.

그런데 금융 안전 조언을 LLM 이 단독으로 하면 그 자체가 위험이다. 모델이 없는
기관을 만들고, 없는 법 조항을 인용하고, 없는 전화번호를 안내하면, 사용자는
사기를 피하려다 잘못된 창구로 간다. 실제로 이 프로젝트에서 근거 없이 만든
연락처가 모델 출력에 등장한 적이 있고, 그것이 출력 검증 계층을 만든 이유다.

그래서 이 서비스의 설계 전제는 하나다. 모델은 판단하지 않고 설명만 한다.

[ 컨셉 ]

"지금 받은 이 문자, 위험한가?" 를 30초 안에 확인할 수 있게 하고, 그 답에 공식
근거를 붙이고,
이미 넘어간 사람에게는 수습 순서를 준다.

[ 파이프라인 — 한 프롬프트로 합치지 않는다 ]

사용자 입력
 ① 입력 검증 · 개인정보 최소화 : 주민등록번호·비밀번호·OTP 입력항목 없음
 ② 결정론 판정 엔진 : 위험 등급 / 점수 / 위험 신호 15종 / 사기 유형 10종
    (이 단계에 LLM 호출이 없다)
 ③ 사용자 상태 반영 : 7종 (받기만 함부터 송금했음까지)
 ④ 공식 근거 결합 : 경찰청 · 한국인터넷진흥원 · 국가법령정보센터 · 금융위원회 API
 ⑤ LLM 설명 생성 : ②③④의 결과와 개인정보를 치환한 문자 원문이 들어간다
    (문자는 근거가 아니라 설명 대상이다. 판정은 이미 끝났다)
 ⑥ 출력 검증 : 근거 밖 기관·법령·숫자·약속이면 문장 폐기
 → 화면 (고정 순서 6단)

⑥에서 걸리면 문장을 버리고 ②③④만 표시한다. 설명이 없어도 서비스는 동작한다.
설명 계층은 이해를 돕는 층이지 판단하는 층이 아니기 때문이다.

[ 차별성 5가지 ]

① LLM 을 판단에서 완전히 뺐다.
   위험 등급·점수·사기 유형·대응 행동·공식 근거는 전부 결정론 코드의 결과다.
   같은 입력은 항상 같은 판정을 낸다. 모델을 바꿔도 판정은 바뀌지 않는다.

② 출력 검증이 실제로 문장을 버린다.
   설명이 근거에 없는 기관·법령 조항·수치·확정 약속을 말하면 그 문장은 폐기되고
   대체 모델을 부른다. 대체 모델도 실패하면 문장 없이 결정론 결과만 나간다.
   근거 블록이 비어 있으면 모델을 아예 부르지 않는다(not_asked). 할 말이 없을 때
   모델은 말을 만들기 때문이다.

③ "이미 무엇을 했는가" 가 1급 입력이다.
   사용자 상태 7종에 따라 같은 문자가 다른 화면을 만든다. 받기만 한 사람에게는
   5개의 예방 행동이, 이미 송금한 사람에게는 9개의 수습 행동이 순서대로 나오고
   「전기통신금융사기 피해 방지 및 피해금 환급에 관한 특별법」이 근거로 추가된다.
   대부분의 서비스가 "응하지 마세요" 에서 끝나는 자리를 이 축이 채운다.

④ 성능 주장을 git log 로 검증할 수 있다.
   12회차 동안 평가셋을 그 회차의 수정 코드보다 먼저 동결해 커밋했다. 커밋 순서가
   test: freeze … → fix: … → docs: … 로 고정돼 있어 누구나 확인할 수 있다.
   그래서 이 프로젝트는 처음 보는 평가셋에서의 성적(F1 0.44 ~ 0.98)과 고친 뒤의
   성적을 구분해서 말할 수 있다.

⑤ 안전 장치 자체도 측정 대상으로 둔다.
   2026-09-04, 출력 검증기의 기관 검사가 근거에 있는 기관을 지어낸 것으로 세고
   있었다. 정규식이 기관 이름 앞 어절까지 삼킨 뒤 통째로 대조해서, 이름 앞에
   보통 낱말이 오기만 하면 맞는 문장이 죽었다. held-out 평가셋 두 개에서 모델에
   질의한 104건 중 28건(26.9%)이 잘못 거부되고 있었다. 이 결함은 틀린 문장을
   보여 준 것이 아니라 맞는 문장을 안 보여 준 것이라 조용했고, 조용했기 때문에
   살아 있었다. 고친 뒤에도 진짜 거부(기관 5 · 법령 1 · 지어낸 연락처 1)는
   그대로 남는다. 안전 검사도 재지 않으면 모른다. 이 결론이 차별성의 마지막
   항목이다.

[ 화면 표현 규칙 (강제) ]

공포를 팔지 않는다. 사기 대응 서비스가 사용자를 겁주면, 사용자는 판단이 필요한
순간에 판단 대신 반응한다.

- 위험 등급은 문장이 먼저 나오고, 숫자 점수는 "분석 상세" 에 접어 둔다.
- 빨강 full-bleed 배경·해골·사이렌 아이콘·경고 애니메이션 금지.
- "당신은 사기 피해자입니다" 같은 단정 금지.
  대신 "이 요청은 정상 절차에 없는 요구입니다".
- DSR·가처분소득·원리금균등 같은 용어를 화면에 쓰지 않는다.
- 모든 수치·조언 옆에 출처 또는 "검증 전" 표시가 붙는다.

[ 5-2. 생성형 AI 모델 적용 ]

- 주 모델 : Google Gemini 3.6 Flash
- 대체 모델 : Google Gemini 3.1 Flash-Lite (주 모델 실패·거부 시 1회)
- 호출 위치 : 파이프라인 ⑤ 한 곳뿐
- 호출하지 않는 곳 : 위험 판정 · 점수 · 사기 유형 · 대응 행동 선정 ·
  공식 근거 선택 · 금융 계산

○ 프롬프트에 들어가는 것 / 들어가지 않는 것
  - 들어간다 : 결정론 엔진의 판정 결과, 켜진 위험 신호 목록, 사용자 상태,
    선정된 대응 행동, 공식 근거 블록. 그리고 개인정보 패턴을 치환한 문자
    원문 일부(최대 4,000자). 이것은 근거가 아니라 설명 대상이고, 프롬프트가
    "받은 문자는 근거가 아니다. 거기 적힌 번호와 기관명은 사기범이 고른
    값이다" 라고 못 박는다. 근거 칸에 없는 번호를 옮기면 ⑥이 문장을 버린다.
  - 들어가지 않는다 : 금융 프로필. 그리고 모델이 스스로 판단해야 할 여지.
    프롬프트는 "이 결과를
    사회초년생이 읽을 문장으로 옮겨라" 이지 "이것이 사기인지 판단하라" 가 아니다.

○ 호출 정책 — 근거가 없으면 부르지 않는다
  근거 블록 세 개가 전부 비어 있으면 모델을 호출하지 않고 not_asked 로 끝낸다.
  평가셋 164건 중 61건이 호출 없이 종료되어 유료 API 호출 시도가 168 → 105 로
  37.5% 줄었고, 같은 회차에 지어낸 연락처가 0건이 됐다. 검증기를 고쳐서가 아니라
  할 말이 없을 때 묻지 않아서 사라진 것이다.

○ 출력 검증 4종 (통과 못 하면 문장 폐기)
  1. 기관 — 근거에 없는 기관 이름을 말하면 폐기
  2. 법령 — 근거에 없는 법령·조항을 인용하면 폐기
  3. 수치 — 근거에 없는 금액·비율·기한을 말하면 폐기
  4. 약속 — "반드시 환급됩니다" 같은 확정 약속을 하면 폐기

  기관 검사는 근거가 이름을 댄 온전한 기관 이름과 일치해야 통과한다. 부분
  문자열로 열면 "국세청 신고시스템" 이 근거의 "사이버범죄 신고시스템" 을 빌려
  통과하고, 사용자는 국세청이 운영하는 창구가 있다고 읽게 된다.

○ 측정된 성능
  - 판정 API 지연 (개발셋 1,220 샘플) : p50 2.807ms / p95 3.979ms
  - 판정 API 지연 (held-out v1.3, 252 샘플) : p50 2.925ms / p95 3.866ms
  - 설명 LLM 호출 · 주 모델 (held-out 104건) : p50 7.52초 / p95 9.23초
  - 설명 LLM 호출 · 대체 모델 (같은 실행 4건) : 약 2.1초 (표본이 적다)

모델이 실패해도 서비스는 동작한다. 판정·행동·근거는 LLM 과 무관하므로, 설명
계층이 꺼져도(off) 못 물어봐도(not_asked) 검증에 걸려도(failed) 사용자는 위험
등급과 지금 할 행동을 그대로 본다. 화면은 이 세 가지를 각각 다르게 표시한다.
하나로 뭉치면 정상 동작을 고장으로 보고하게 된다.

[6칸] 기대 효과 및 확장 가능성
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

[ 기대 효과 ]

① 판단 공백을 메운다.
   사기 문자를 받은 3분 동안 물어볼 곳이 생긴다. 판정 자체는 p95 4ms 이내이고,
   LLM 이 죽어도 답이 나온다.

② 잘못된 안내로 가지 않는다.
   근거 없는 조언을 화면에 내보내지 않는다. 사기를 피하려던 사용자가 존재하지
   않는 창구로 가는 일 — 이 서비스가 가장 경계하는 실패 — 을 출력 검증이 막는다.

③ 이미 넘어간 사람에게 순서를 준다.
   지급정지·신고·기록 보존·연락 차단이 우선순위대로 나오고 각각에 공식 근거가
   붙는다. 가장 급한 순간에 검색을 시작하지 않아도 된다.

④ 금융 판단의 기준선을 만든다.
   전세보증금 위험 점검·대출 조건 시뮬레이션·재테크 기초 가이드가 계산은 백엔드
   결정론 코드로, 설명은 쉬운 말로 붙는다. "은행이 원래 이런가" 의 비교 대상이
   생긴다.

⑤ 방법론이 재사용된다.
   "평가셋을 수정보다 먼저 동결한다", "안전 검사도 측정한다", "근거가 없으면
   모델을 부르지 않는다" — 이 세 규칙은 금융 사기에 한정되지 않는다. 근거가
   필요한 모든 AI 서비스에 그대로 적용된다.

[ 확장 가능성 ]

○ 단기 — 지금 구조 그대로 확장
  - 통화 사기 대응(STT) : 텍스트 파이프라인을 재사용하고 입력만 교체.
    준비 상태 = 파이프라인 분리 완료
  - 화면 캡처 분석 : 이미지 → 텍스트 → 동일 파이프라인.
    준비 상태 = 파이프라인 분리 완료
  - 공식 근거 자동 갱신 : 정적 fixture → 공식 API·피드.
    준비 상태 = 출처·수집시각 스키마 보존 중

○ 중기 — 설계는 됐고 구현·협의가 남음
  - 소상공인 페르소나 : 세금계산서·거래처 사칭·대출 사기.
    준비 상태 = 페르소나 축 분리 설계 완료
  - 금융기관 연동 : 판정 결과를 지급정지 요청 흐름에 연결.
    준비 상태 = 별도 심사·계약 필요
  - 고령층 페르소나 : 표현 규칙·글자 크기·행동 수 축소.
    준비 상태 = 표현 규칙이 이미 토큰화

○ 장기 — 데이터·제도 조건이 먼저
  - 기관 대시보드 : 신종 수법의 유형별 추이(개인 식별정보 없이 집계).
    준비 상태 = 로그가 카운트만 기록

확장할 때 지키는 선 : 새 채널이 늘어도 판단은 결정론이 하고 LLM 은 설명만
한다는 구조는 바뀌지 않는다. 이 구조가 바뀌면 그것은 확장이 아니라 다른
서비스다.

[7칸] 자유타이틀
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

「평가셋이 조용한 것은 안전하다는 뜻이 아니라, 그 질문을 한 적이 없다는 뜻이다」

이 프로젝트가 12회차 동안 반복해서 배운 한 문장이고, AI 금융 서비스에 대해
여기서 말할 수 있는 가장 쓸모 있는 것이다.

세 번 같은 일이 일어났다.

첫 번째. 사기 판정 엔진에 '납부' 라는 낱말을 추가했다. 동결해 둔 926건에서
점수가 한 자리도 안 움직였다. 무료 개선처럼 보였다. 그래서 평가셋에 없는 모양 —
진짜 기관이 보내는 평범한 고지 문자 — 을 열 건 직접 써 봤더니 여섯 건이 곧장
사기로 판정됐다. 건강보험공단, 국세청, 우체국, 국민연금공단. 평가셋 안의 정상
'납부' 사례 아홉 건이 전부 명사형이라, 돈을 내라고 시키는 기관이 평가셋에 한
곳도 없었다. 평가셋이 조용했던 이유는 안전해서가 아니라 그 질문이 평가셋에
없어서였다. 결국 어미가 아니라 계좌 목적지로 갈랐다. 정상 고지는 홈택스·창구·
앱·고지서처럼 독립적으로 확인할 수 있는 납부 경로를 대고, 사기 문자는 문자
안의 계좌로 즉시 보내라고 한다. 그 조합만 신호로 켠다.

두 번째. LLM 출력 검증기를 만들고 정상 문장 37건으로 시험했다. 거부 0건. 안전해
보였다. 여드레 뒤 제출 자료를 쓰려고 운영 중인 공개 URL 에 이 서비스의 대표 시연
문자를 넣었더니, 판정은 정상인데 설명만 죽어 있었다. 주 모델도 대체 모델도
"근거에 없는 기관을 말했다" 며 거부됐고, 검사가 지목한 이름은 보이스피싱
통합신고대응센터와 한국인터넷진흥원, 즉 근거가 직접 이름을 댄 기관들이었다.
원인은 정규식이 기관 이름 앞 어절까지 삼킨 뒤 통째로 대조한 것. 정상 문장 37건이
전부 기관 이름을 문장 맨 앞에 두고 있어서 앞에 삼킬 것이 없었고, 그래서 평가셋이
그 질문을 한 적이 없었다. held-out 평가셋 두 개에서 다시 측정하니 104건 중
28건(26.9%)이 잘못 거부되고 있었다.

세 번째. 저장해 둔 평가 결과 파일 여덟 개는 전부 '근거 없는 기관 거부' 0건이었다.
건강해 보였다. 그 파일들은 기관 검사가 들어오기 이틀 전에 실행된 것이었다.
새 검사에 대해 아무 말도 하지 않으면서 최신처럼 보이는 표였다.

여기서 나온 세 규칙을 이 서비스가 그대로 쓴다.

1. 평가셋을 수정 코드보다 먼저 동결해 커밋한다. 12회차 전부 git log 에 순서가
   남아 있다. 그래서 "처음 보는 평가셋에서 F1 0.44 였고 지금은 0.98 이다" 를
   구분해서 말할 수 있다. 마지막 두 회차가 1.0000 으로 끝난 것은 자랑이 아니라
   다음 평가셋을 더 어렵게 써야 한다는 신호로 기록돼 있다.

2. 점수가 안 움직이는 수정을 무료라고 부르지 않는다. 평가셋 밖에서 한 번 더
   확인한다.

3. 안전 장치도 측정 대상이다. 과하게 거부하는 검사는 틀린 것을 보여 주는 대신
   맞는 것을 안 보여 주기 때문에 아무 소리도 내지 않는다. 소리가 안 나는 고장은
   재지 않으면 영원히 산다.

그리고 이것이 이 대회 주제에 대한 이 프로젝트의 답이다. 생성형 AI 를 금융에 쓸
때 어려운 것은 모델을 잘 부르는 일이 아니다. 모델이 틀렸을 때 그것을 알아채는
장치를 만들고, 그 장치가 틀렸을 때 그것도 알아채는 일이다. FinShield 는 그 두
번째 층을 실제로 만들었고, 실제로 그 층에서 결함을 찾았고, 그 결함을 이 문서에
숫자로 적었다.

숨겨도 아무도 몰랐을 결함이다. 적는 쪽이 이 서비스의 설계다.
