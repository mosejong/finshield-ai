# 재는 자리가 말라붙었다 — held-out v1.1 과 상태·창구

2026-08-24

## 한 줄

**이번 회차의 발견은 엔진이 아니라 셋에 있었다.** 열 회차 동안 사용자 상태를 재는 사례가
27건에서 6건까지 조용히 줄어들었고 아무도 그것을 정하지 않았다. 상태를 다시 분모에 넣은
79건을 얼렸더니 `scenario_policy_accuracy` 가 0.9571 에서 **0.6582** 로 내려앉았다 —
엔진이 나빠져서가 아니라 재지 않던 것을 재기 시작해서다. 세 곳을 고쳐 **0.8354** 로,
필수 action coverage 0.7869 → **0.8852**, 금지 행동 회피 0.9664 → **1.0000** 으로 갔고,
놓친 필수 행동 39건이 **21건**으로 줄면서 남은 21건은 전부 신호 어휘의 하류가 됐다.

## 0. 이번 회차의 방향

| 회차 | 수정의 방향 | 값을 치르는 자리 |
|---|---|---|
| v0.2~v0.5 | 넓히기 | 정상 문장 (오탐) |
| v0.6 | 좁히기 | 사기 문장 (미탐) |
| v0.7 | 올리기 | 정상 문장의 등급 (천장) |
| v0.8 | 넓히기 5 + 좁히기 1 | 양쪽 다 |
| v0.9 | 갈아 끼우기 + 올리기 1 + 좁히기 1 | 옛 셋의 라벨 |
| v1.0 | 넓히기 5 | 정상 문장 (오탐과 천장) |
| **v1.1** | **분모 바꾸기 + 넓히기 3** | **셋 자신** |

앞의 여섯 회차는 전부 *엔진의 어느 자리가 비었나* 를 물었다. 이번엔 먼저 *우리가 무엇을
재고 있었나* 를 물었고, 답이 결함이었다.

### 재는 자리가 열 회차에 걸쳐 말라붙었다

각 셋에서 `received_only` 가 아닌 사례의 수:

```
v0.1  v0.2  v0.3  v0.4  v0.5  v0.6  v0.7  v0.8  v0.9  v1.0
 18    27    21    15    14    17    16    14     8     6
```

**아무도 이 추세를 결정하지 않았다.** 매 회차의 결함이 문장 안에 있었고 — 어휘, 어미,
절의 자리 — 문장 안의 결함을 가장 깨끗하게 재는 방법은 상태를 `received_only` 로 고정하는
것이었다. 상태는 등급 바닥과 행동 목록을 함께 움직이므로, 어휘 하나를 재려는 사례에
상태를 얹으면 신호가 섞인다. **회차마다 옳은 선택이었다.** 열 번 쌓이자 제품의 절반이
측정에서 빠졌다.

v1.0 의 `scenario_policy_accuracy` 0.9571 은 사실상 `received_only` 에 대한 진술이었다.
상태 정책이 일곱 갈래인데 그중 하나가 표본의 91% 를 차지하면, 나머지 여섯 갈래가 통째로
무너져도 그 숫자는 거의 움직이지 않는다.

**지표가 만점에 가까울 때 물어야 할 것은 "무엇이 남았나" 가 아니라 "이 숫자의 분모가
무엇인가" 다.**

### 상태가 있는 정상 문장의 천장은 그 상태가 강제하는 바닥이다

v0.7 이 정상 사례에 `expected_max_risk` 를 도입했을 때 모든 정상은 `received_only` 였고
천장은 전부 `low` 였다. **상태가 있는 정상에는 그것이 통하지 않는다.** 계좌 정보를 이미
넘긴 사람은 `STATE_MINIMUM_RISK` 때문에 등급이 `high` 로 강제되고, 그것이 옳다. 거기에
`low` 천장을 걸면 그 라벨은 **상태 정책 자체를 결함으로 선언**하는 라벨이 된다.

그 문장이 사기가 아니라는 사실은 등급이 아니라 **유형과 행동으로** 표현되어야 한다.
그래서 v1.1 의 상태 있는 정상은 천장을 그 상태의 바닥과 같게 선언한다. 링크를 눌렀다는
사실이 등급을 medium 으로 올리는 것은 상태의 몫이고 맞는 일이다 — 거기서 한 칸이라도 더
올라가면 그것은 문장이 올린 것이고, 문장이 정상이면 틀린 것이다.

`test_holdout_v1_1_ceilings_a_stateful_normal_at_the_floor_its_state_forces` 가 정상
38건 전부를 그렇게 검사한다.

## 3. 세 수정 (`902837a`)

### D1 — 상태가 예방 행동을 반복한다

일곱 상태 중 **둘만** 예방 행동을 냈다. `CLICKED_LINK` 는 `DO_NOT_CLICK` 을,
`RECEIVED_UNKNOWN_MONEY` 는 `DO_NOT_FORWARD_MONEY` 를 돌려받는데, 계좌 권한을 넘긴 사람 ·
앱을 깐 사람 · 개인정보를 준 사람 · 이미 송금한 사람에게는 그 자리가 비어 있었다.

```python
STATE_PREVENTION_ACTIONS: dict[UserState, tuple[str, ...]] = {
    UserState.SHARED_PERSONAL_INFO: ("DO_NOT_SHARE_ACCESS",),
    UserState.SHARED_ACCOUNT_ACCESS: ("DO_NOT_SHARE_ACCESS",),
    UserState.INSTALLED_APP: ("DO_NOT_INSTALL",),
    UserState.TRANSFERRED_MONEY: ("DO_NOT_FORWARD_MONEY",),
}
```

**이미 한 번 넘긴 사람이 가장 다시 넘기기 쉬운 사람이다.** 사기는 한 번으로 끝나지 않고,
같은 통화 안에서 "이번엔 두 번째 계좌로" 가 이어진다.

#### 상태는 신호를 대신하지 않는다

이 표를 무조건 적용하면 v1.1 의 상태 있는 정상 문장들이 전부 깨진다.

```
fh-974 "알려 주신 급여이체 계좌로 4월분부터 지급됩니다"   → shared_account_access, 정상
fh-969 "사내 보안 프로그램 설치가 완료되었습니다"         → installed_app, 정상
fh-975 "이체가 정상 처리되었습니다"                       → transferred_money, 정상
fh-967 "예약하신 진료는 내일 오후 3시입니다"              → shared_personal_info, 정상
```

계좌를 알려 주는 일도, 앱을 까는 일도, 송금하는 일도 **대부분은 정상**이다. 상태만 보고
"권한을 넘기지 마세요" 를 내면 정상적으로 일을 마친 사람에게 경고를 붙이는 셈이다.

그래서 게이트를 `bool(signals)` 로 걸었다 — **위험 신호가 하나라도 켜진 메시지에서만**
상태가 예방 행동을 반복한다.

이 게이트가 실제로 가르는지 **D1 이 건드리는 네 상태의 24건(사기 19 · 정상 5)을 전부
덤프해서** 확인했다.

- 정상 5건(`fh-967`·`fh-968`·`fh-969`·`fh-974`·`fh-975`)은 **신호가 하나도 안 켜진다.**
  게이트가 닫히고 예방 행동이 붙지 않는다.
- 사기 19건 중 11건에서 신호가 켜지고 예방 행동이 붙는다.
- 남은 사기 8건(`fh-906`·`fh-908`·`fh-910`·`fh-922`·`fh-923`·`fh-925`·`fh-926`·`fh-937`)은
  신호가 **하나도** 안 켜져서 게이트가 닫힌다. 그런데 그 여덟은 전부 이번 회차가
  손대지 않기로 한 어휘 공백 목록에 이미 이름이 적혀 있다.

**게이트의 결함이 아니라 어휘의 결함이다.** 게이트를 무조건으로 바꾸면 그 여덟을 얻는
대신 정상 다섯을 잃는다 — 그 교환은 하지 않는다. 이 사실을 코드 주석과 문서에 그대로
적어 두었다.

### D2 — 사건 어휘가 창구를 가리킨다

창구를 **기관 자칭 신호에서만** 찾고 있었다. 그런데 사기 문자의 절반은 자기가 누구인지
말하지 않고 **무슨 일이 일어났는지만** 말한다.

```
"해외 결제 5건이 승인되었습니다"          → 카드 뒷면 번호가 창구다
"환급 대상자로 확인되었습니다"            → 홈택스가 창구다
"진행 중인 수사와 관련된 사안입니다"      → 112 가 창구다
```

기관명이 없어도 읽는 사람이 갈 곳은 명확하다. 그런데 v0.9 가 세운 규칙 —
*확인하라는 조언은 창구가 있을 때만 낸다* — 이 그 자리에서 창구가 없다고 판단하고
폴백으로 `VERIFY_BY_KNOWN_CONTACT`(이전부터 쓰던 연락처) 를 냈다. **미탐 하나가 틀린 행동
하나를 함께 낸다** — v0.9 가 배운 "틀린 행동은 없는 행동보다 나쁘다" 가 그대로 재발한다.

```python
def mentions_official_channel_event(text: str) -> bool:
    """이 문장이 공식 창구가 실재하는 사건을 말하고 있는가."""
```

어휘에서 **일부러 뺀 것**이 이 수정의 절반이다 — `확인`·`절차`·`신청` 은 너무 흔하고,
무엇보다 **창구를 지목하지 않는다.** "확인" 이라는 낱말은 어느 창구로 가라는 뜻이 아니다.
이 선택이 `fh-917`·`fh-918`(창구가 없는 고립 요구라 `VERIFY_OFFICIAL_CHANNEL` 을 금지하는
사례)을 지킨다.

두 가지 제약을 더 걸었다.

- **등급을 올리지 않는다.** 사건 어휘는 위험의 증거가 아니라 창구의 이름이다.
- **신호가 이미 켜진 메시지에서만 읽는다.** 진짜 은행 승인 문자에 "확인하세요" 를
  덧붙이지 않기 위해서다. `fh-976`·`fh-977`·`fh-978` 이 이 자리를 지킨다.

### D4 — 고립을 어휘가 아니라 어형으로 본다

`secrecy_isolation` 의 어휘 목록은 **동사에 바로 붙는 금지형**만 담고 있었다.

```
"가족에게도 알리지 마세요"       → 목록에 있다
"가족에게 말씀하시면 안 됩니다"  → 아무것도 안 걸린다
```

같은 요구인데 활용이 하나 끼면 통째로 빠진다. **어휘를 더 적으면 다음 활용이 또 빠진다** —
어형은 무한하고 어휘는 유한하다.

그래서 고립의 **대상**과 **금지**를 따로 세우고 둘이 한 절 안에 있을 때만 켠다.

```python
ISOLATION_PROHIBITION_PATTERN = re.compile(
    r"(?:" + "|".join(ISOLATION_PROHIBITION_TARGETS) + r")"
    r"(?:는|은|도|만|와|과)?\s*"
    r"[^.!?\n]{0,14}?"
    r"(?:" + "|".join(ISOLATION_PROHIBITED_ACTS) + r")"
    r"[^.!?\n]{0,8}?면\s*안\s*[되돼됩됐된될]"
)
```

v1.0 이 요구를 세는 쪽에서 이미 만난 그 어형(`-(으)면 안 됩니다`)이다. **같은 어형이 두
회차에 걸쳐 두 자리에서 결함을 냈다.**

`외부에` 는 일부러 넣지 않았다 — v1.0 `fh-865`("외부에 공유하지 말아 주세요", 사내 공지)를
정상으로 못 박았고 v1.1 `fh-955` 가 그 자리를 지킨다. `보내`·`전달` 도 뺐다. 그것을
막는 문장은 고립이 아니라 **보안 안내**다.

## 4. 넓히기의 값을 어형이 직접 치른 자리

고립 어형을 넓히자마자 v0.9 `fh-741` 이 오탐이 됐다.

```
"인증번호는 저희를 포함해 누구에게도 알려 주시면 안 됩니다"   ← 정상, 한국에서 가장 흔한 보안 문자
"가족에게 말씀하시면 안 됩니다. 저와만 진행하시는 편이…"      ← 사기
```

어형이 겹치는 게 아니라 **글자까지 겹친다.** 대상(`누구에게도`/`가족에게`)도 금지
어미(`-면 안 됩니다`)도 같은 층에 있다.

첫 안은 **화자를 예외로 두는가**(`저희를 포함해`)로 가르는 것이었다. 버렸다 — 사기 문자는
그 어구를 그대로 흉내 낼 수 있다. "저희를 포함해 누구에게도 알리지 마시고, 지금 말씀드리는
계좌로만…" 은 아무 비용 없이 쓸 수 있는 문장이다.

가르는 자리는 **금지의 대상**이다.

| | 무엇을 말하지 말라고 하나 |
|---|---|
| 고립 | **이 대화 자체** — 누가 연락했는지, 무슨 일이 벌어지는지 |
| 보안 안내 | **읽는 사람이 이미 쥔 비밀** — 인증번호, 비밀번호, 보안카드 |

**인증번호를 말하지 말라는 문장은 인증번호를 요구하지 않는다.** 사기범은 화자 표현을
흉내 낼 수 있지만 금지의 대상은 흉내 낼 수 없다 — 대상을 비밀 쪽으로 옮기는 순간 그
문장은 요구를 잃는다.

```python
ISOLATION_SECRET_OBJECTS = (
    "인증번호", "비밀번호", "보안카드", "공인인증", "일회용", "otp",
)
```

예외는 **어형 층에만** 적용된다. 어휘 목록(`아무에게도 말하지 마`)은 그대로 켠다 —
그쪽은 이미 여섯 회차를 버틴 판단이고, 예외를 두 층에 다 걸면 넓힌 만큼을 도로 잃는다.
그리고 예외는 **절 안에서만** 본다. 메시지 전체에서 보면 사기 문자가 뒤에 "인증번호"
한 단어를 붙이는 것으로 고립 탐지를 통째로 끌 수 있다.

v0.9 는 수정 전과 **완전히 동일한 값**으로 돌아왔다.

## 5. 예측이 반증된 자리

동결 전에 D3 으로 적어 둔 결함 — `DEMAND_MARKERS` 에 `-하셔야 합니다` 종결형이 없다,
v1.0 `fh-806` 이 남긴 예고 — 는 **결함이 아니었다.**

`fh-911`·`fh-912`·`fh-914` 가 동결 시점에 이미 전부 통과한다. `주셔야` 가 이미 목록에
있었고, `-하셔야` 계열은 위험 행동 어간(`설치`·`이체`·`입력`)이 받고 있었다. 같은 층으로
묶어 뒀던 `fh-913` 하나만 실패하는데 그 원인은 종결형이 아니라 `공인인증서` 라는 **어휘
공백**이다.
