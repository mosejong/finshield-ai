# held-out 셋을 만들고, 처음으로 성능이 아닌 숫자를 봤다

2026-08-20 · `feat/fraud-holdout-v0.2`

## 왜 지금

개발셋 61건에서 엔진 오류가 **0건**이 된 지 하루가 지났다. precision 1.0, recall 1.0,
오탐 0. 그 숫자를 문서에 적으면서 같이 적은 문장이 이거였다.

> 성능이 완벽해진 것이 아니라 개발셋이 변별력을 잃은 것이다.

맞는 말인데, 맞다는 것을 **보여 준 적은 없었다.** 백로그에도 "다음 측정의 전제" 로
적혀만 있었다. 그래서 이번에는 다른 셋을 만들고, 거기서 얼마나 떨어지는지 봤다.

## 파일을 나눈 이유

같은 파일에 `held_out: true` 플래그만 달 수도 있었다. 안 했다.

플래그는 한 번의 실수로 넘어간다. 오답을 보다가 문장 하나를 개발셋에 옮겨 적고,
어휘를 고치고, 그걸로 재면 held-out 은 끝난다. 그리고 **그 사실이 아무 데도 안
남는다.** 파일이 다르면 최소한 diff 에 나온다.

로더가 두 가지를 더 막는다.

```
a dataset must be entirely held-out or entirely not
case ID prefix must match held_out: ['fg-900']
```

한 파일이 반쪽만 held-out 인 것, 그리고 `fh-` 사례가 `fg-` ID 를 달고 개발셋에 섞여
들어오는 것. 둘 다 사람이 눈으로 잡을 수 없는 종류의 사고다.

## 순서를 지켰다

72건을 다 쓰고 **커밋해서 동결한 다음에** 처음 돌렸다. 커밋 두 개로 나눈 것은
그래서다.

```
5d848c5  test: freeze a held-out fraud evaluation set before measuring it
    ↓ 여기서 처음 실행
(다음 커밋)  측정 결과와 오류 분석
```

라벨 규칙도 측정 전에 정해서 `evaluation/data/README.md` 에 적었다. 특히 `high` 의
정의(돈·인증정보·접근수단·설치·원격제어를 **명시적으로 요구**했거나 상태가
`shared_account_access` 이상)를 먼저 고정하지 않으면, 결과를 보고 나서 라벨을
느슨하게 만들고 싶어진다.

## 결과

| | 개발셋 61건 | held-out 72건 |
|---|---|---|
| precision | 1.000 | 0.854 |
| recall | 1.000 | 0.795 |
| f1 | 1.000 | 0.824 |
| 오탐률 | 0.000 | 0.214 |
| 상태 정책 정확도 | 1.000 | **0.681** |
| 필수 signal coverage | 0.981 | 0.836 |
| 공식 근거 coverage | 1.000 | 1.000 |

품질 게이트 기준선(precision 0.75 / recall 0.65 / FPR 0.25)은 held-out 에서도 넘는다.
게이트가 느슨해서가 아니라, 처음 정할 때 개발셋 만점을 기준으로 잡지 않았기 때문이다.

가장 크게 떨어진 것은 상태 정책 정확도다. 1.000 → 0.681. 이 지표는 사례 하나에서
등급과 행동이 **둘 다** 맞아야 1점이라, 한쪽만 어긋나도 0 이 된다.

## 미탐 9건 — 세 가지 원인

**어휘가 없다 (6건).** 국민은행·카카오뱅크·신한카드·건강보험공단·국세청·병무청.
전부 신호 0개. `authority_impersonation` 재현율이 0.333 이다.

이건 몰라서 생긴 구멍이 아니다. 어제 `docs/32` 에 이렇게 적었다.

> 국세청·건강보험공단… 골든셋 밖 정상 문장에서 오탐이 5건 났다. 되돌렸다.
> 넣으려면 held-out 셋으로 오탐을 재고 넣는다.

이제 그 셋이 생겼고, 같은 셋이 **왜 맨 기관명을 넣으면 안 되는지도** 같이 보여
준다. `fh-052`(국세청 홈택스 정상 안내)와 `fh-053`(건강보험료 정상 고지)이 같은
파일에 있다. 기관명을 넣으면 미탐 2건이 오탐 2건으로 바뀔 뿐이다. 필요한 것은
기관명이 아니라 **자칭 형태와 요구의 결합**이다.

**분류 표에 구멍이 있다 (1건).** `fh-017` "작업비를 먼저 송금해 주시면".
`money_transfer_request` 신호는 켜졌고 위험 등급도 `high` 로 올라갔는데
`fraud_types` 가 비었다. `classify_fraud_types` 에 이 코드로 들어오는 분기가 없다.

사용자에게는 **"위험은 높은데 무슨 사기인지는 말 못 하는"** 출력으로 보인다.
어휘를 아무리 늘려도 이건 안 닫힌다.

**어미를 못 넘는다 (1건).** 어휘는 `제3자 계좌로 옮기`, 문장은
`제3자 계좌로 옮겨`. 부분 문자열 매칭이라 한 글자에 통째로 빠진다.

나머지 1건(`fh-040`)은 라벨 단계에서 필수 신호를 비워 둔 경계 사례라 결함으로
세지 않았다.

## 오탐 6건 — 원인은 하나다

```
fh-050  요청하신 체크카드 재발급 건이 등기로 발송되었습니다   → 체크카드
fh-060  안전계좌라는 것은 존재하지 않습니다                  → 수사기관·안전계좌
fh-063  주소가 바뀌었으면 다시 보내 주세요                   → 다시 보내
fh-064  영수증 사진을 담당자에게 전달해 주세요               → 전달해
fh-068  국민은행 스타뱅킹 앱 설치했는데 로그인이 안 돼요      → 앱 설치
fh-072  창구에 가서 계좌 비밀번호를 직접 변경하고 왔습니다     → 비밀번호
```

여섯 건 모두 **단어가 문장에 있다는 사실만으로** 켜졌다. 누가 누구에게 무엇을
요구하는지는 보지 않는다.

`fh-068`·`fh-072` 가 제일 아프다. 사용자가 **자기가 한 일을 설명하는 문장**이 사기
판정을 받는다. 이 제품에서 그런 문장은 예외 입력이 아니라 가장 흔한 입력이다.
"이미 무엇을 하셨나요" 를 물어보는 화면을 만들어 놓고, 그 답을 사기 문자로 읽는
셈이다.

`fh-060` 은 억제 규칙이 한 글자로 빗나갔다. 조건은 `요구하지 않습니다` 인데 문장은
`이런 요구를 받으면` 이다.

## 일부러 하지 않은 것

**이 결과로 규칙을 하나도 고치지 않았다.**

고치는 순간 v0.2 는 held-out 이 아니게 되고, 같은 셋으로 잰 다음 숫자는 성능이
아니라 다시 기억이 된다. 위의 표는 이 셋의 **유일한 깨끗한 측정**이고 그대로
남는다. 수정은 별도 변경으로 하며, 그때 v0.2 를 소진됨으로 표시한다. 다음 깨끗한
측정에는 v0.3 이 필요하다.

CI 도 같은 이유로 이 셋에 성능 기준선을 걸지 않는다. 걸면 빨개질 때마다 이 셋을
보고 규칙을 고치게 되고, 첫 번째 빨간불에 held-out 이 끝난다. CI 가 지키는 것은
라벨 무결성과 개발셋과의 분리뿐이다.

## 데이터셋 해시에서 `held_out` 을 뺐다

필드 하나 추가했더니 커밋돼 있던 유료 판정 결과가 `stale` 이 됐다. 문장도 라벨도
안 움직였는데 sha256 이 바뀌어서다.

해시가 식별하려는 것은 **어떤 사례를 어떤 라벨로 채점했는가** 다. `held_out` 은
사례의 성질이 아니라 파일의 성질이고, 모델에게 보낸 적도 채점에 쓴 적도 없다.
빼는 게 맞다. 파일이 섞이지 않는다는 보장은 로더가 따로 한다.

## 이 셋이 못 재는 것

- **투자·리딩방 사기.** 유형 어휘가 6종으로 고정돼 있어 라벨을 붙일 수 없었다.
  실제 피해 규모로는 상위권인데 분류 표에 자리가 없다. 데이터 문제가 아니라
  taxonomy 의 공백이다.
- **LLM 단독 판정.** `not_run`. 이 셋에 대한 3자 비교는 유료 호출을 한 번 더 해야
  나온다.
- **저자가 엔진 어휘를 안다.** 완전한 blind 가 아니다. 지킨 것은 순서뿐이고,
  그 순서는 커밋 이력이 증거다.

## 검증

```
pytest -q                              786 passed, 2 skipped   (직전 781, +5)
tests/test_fraud_evaluation.py         30 passed               (직전 25, +5)
개발셋 61건 재측정                      f1 1.000 무변경
git diff --check                        OK
```

held-out 셋에 대한 성능 단언은 테스트에 **없다.** 라벨 무결성, 상태·persona·유형
전수 커버, 개발셋과 ID·문장 비중복, 반쪽 held-out 거부, ID 접두사 위조 거부까지가
CI 몫이다.
