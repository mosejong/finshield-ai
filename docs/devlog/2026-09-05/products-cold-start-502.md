# 키를 넣었더니 502 가 됐다 — 살아 있는 백엔드를 고장으로 바꾼 8초

2026-09-05, 같은 날 네 번째 편. 앞 편
([`products-never-served.md`](products-never-served.md))에서 상품이 죽어 있던
원인을 **배포 구성에서 빠진 것**이라고 적었다. 그 절반은 맞았고, **절반은
틀렸다.** 구성을 채우고 나서야 나머지 절반이 드러났다.

VM 에 키 파일을 넣고 `-f compose.public-data.yaml` 을 붙이자 공개 URL 의
상품 호출이 **503 에서 502 로** 옮겨 갔다. 앞 편이 못 박아 둔 표대로라면
503 은 「설정 누락」, 502 는 「제공자 실패」다. 설정은 채워졌다는 뜻이고,
이제 공공데이터 쪽이 문제라는 뜻이다.

**그런데 공공데이터는 멀쩡했다.**

---

## 0. 추측을 세 번 끊었다

키가 틀렸는지, VM 이 못 나가는지, 코드가 깨지는지 — 셋 중 하나다.

**키와 망은 컨테이너 안에서 직접 갈랐다.** 값은 출력하지 않고 길이와 HTTP
결과만 봤다.

```
key_len 88
None    200  0.99s  resultCode 00  totalCount 9641
202609  200  0.48s  resultCode 00  totalCount 0
202608  200  0.54s  resultCode 00  totalCount 325
202607  200  0.88s  resultCode 00  totalCount 325
```

**키도 망도 아니었다.** 기준월 `202609` 가 0건이라 `202608` 로 물러나는 것도
설계대로다. 그러면 남는 것은 코드 경로인데, 그것도 컨테이너 안에서 그대로
돌려 봤다.

```
numOfRows=100:  200  2.33s  bytes 185601
snapshot OK     5.41s  items 325  month 202608
```

**성공했다.** 안에서는 되는데 밖에서는 502 다. 그 차이가 답이다.

## 1. 두 번 찍었더니 갈렸다

밖에서 같은 요청을 연달아 두 번 보냈다.

| | 걸린 시간 | 결과 |
|---|---|---|
| 첫 번째 (캐시 비어 있음) | **9.64초** | **502** |
| 두 번째 (캐시 차 있음) | 1.11초 | 200, 325건 |

**백엔드는 한 번도 고장난 적이 없다.** 프론트 프록시의 예산이 먼저 끝났을
뿐이다.

```ts
// web/lib/api/client.ts
const DEFAULT_TIMEOUT_MS = 8000;
```

8초는 **백엔드 한 번 왕복**을 재는 값이다. 상품 경로는 그 안에서
공공데이터포털을 여러 번 부르고, 캐시가 비어 있으면 그 값을 전부 치른다.
8초에 끊긴 요청은 `AbortError` 가 되고, 그것은 `PASSTHROUGH_STATUSES` 에
없으므로 **502 로 덮인다.**

즉 우리가 읽고 있던 「제공자 실패」는 **제공자의 실패가 아니라 우리가 기다림을
포기한 시각**이었다. 앞 편에서 만든 503/502 구분은 여전히 유용하지만, **502 는
두 가지 뜻을 겹쳐 갖고 있었다.**

## 2. 콜드 경로가 왜 그렇게 비쌌나

한 달치를 받는 데 **왕복 여섯 번**이 들고 있었다.

- 기준월 찾기 2회 — `202609`(0건) → `202608`(325건), 각각 `numOfRows=1`
- 본문 받기 4회 — 325건을 **100건씩** 끊어서 순서대로

us-west1 에서 한국 서버까지의 왕복이 여기에 곱해진다. 컨테이너 안 5.41초,
TLS·Caddy·Next·응답 조립을 더해 밖에서 9.6초다.

**그 페이지 나눔이 사는 게 없었다.** 같은 날 공식 API 에 직접 재 봤다.

| `numOfRows` | 받은 행 | 걸린 시간 |
|---|---|---|
| 1 | 1 | 0.34초 |
| 100 | 100 | 0.48초 |
| **500** | **325 (전량)** | **0.64초** |
| 1000 | 325 (전량) | 0.41초 |

**한 번에 전량을 줘도 같은 시간에 답한다.** 100건씩 끊은 것은 순수하게 왕복
횟수만 늘린 선택이었다. 로컬에서는 0.5초짜리 호출이 네 번이라 2초로 끝나
보이지 않았고, **왕복 지연이 곱해지는 곳은 배포된 VM 뿐이라 로컬 테스트가
초록인 것과 아무 상관이 없다.**

## 3. 고친 것 넷

**하나. 한 달치는 왕복 한 번에 받는다.** `PROVIDER_PAGE_SIZE` 100 → 500.
로더의 페이지 순회는 그대로 두었다 — 달이 더 커지면 그대로 넘긴다.

**둘. 캐시 수명 300초 → 3600초.** 공식 데이터는 `basYm` 단위, 즉 한 달에 한
번 바뀐다. **5분 TTL 은 새로움을 하나도 사지 못하면서 「5분 넘게 아무도 안
들어오면 다음 첫 방문자가 콜드 경로를 문다」 만 정하고 있었다.** 심사위원은
정확히 그 첫 방문자다. `fetched_at` 은 응답에 계속 실려 나가므로 얼마나
묵었는지는 그대로 보인다.

**셋. 상품 경로의 프록시 예산 8초 → 20초.** 목록·상세·비교 세 경로만이다.
늘린 예산이 실패를 감추지는 않는다 — 제공자가 정말 죽어 있으면 그때도 502 가
나가고, **살아 있는 느린 응답을 죽음으로 바꾸지 않을 뿐이다.**

**넷. 제공자 호출 하나의 예산 5초 → 10초.** 전량을 한 번에 받으면 응답이 세
배 커지고, VM 의 첫 호출은 TLS 악수를 함께 치러 2.33초였다. 5초는 여유가
아니었다.

## 4. 무엇을 못 박았나

**「보통의 한 달은 왕복 한 번」** — `test_full_month_snapshot_costs_one_page_request`.
325건짜리 달을 세는 가짜 제공자에 걸어, 호출이 정확히 세 번(찾기 2 + 본문 1)
인지 본다. 페이지 크기를 되돌리면 네 번이 되어 떨어진다.

**「상품 경로는 8초에 끊지 않는다」** — `web/app/api/proxy/catalog-timeout.test.ts`.
취소되기 전에는 답하지 않는 백엔드를 세워 두고 가짜 시계를 8초 넘겨도 요청이
살아 있는지, 예산이 끝난 뒤에는 502 가 나가는지 본다. 세 경로 모두에 건다.
**고치기 전 코드로 돌려 실제로 떨어지는 것을 확인했다** — 통과만 하는 시험은
회귀를 못 막는다.

**「TTL 은 방문자 사이 간격보다 길다」** — 300초로 되돌리면 떨어진다.

## 5. 안 한 것

**미리 데우지 않았다.** 기동할 때 스냅샷을 한 번 받아 두면 첫 방문자도 안
기다린다. 하지만 그것은 기동 경로에 외부 호출을 새로 다는 일이고, 실패했을 때
컨테이너 기동과 헬스체크에 어떻게 얽히는지 재 본 적이 없다. **마감 이틀 전에
기동 경로를 건드리지 않는다.** 지금은 첫 방문자가 여전히 콜드를 물지만,
이번엔 **기다리면 성공한다** — 그리고 한 시간에 한 명만 문다.

**502 의 두 뜻을 코드로 가르지 않았다.** 「제공자가 실패했다」와 「우리가
기다림을 포기했다」가 같은 502 로 나간다. 프록시가 `ApiError.kind === "timeout"`
을 구분해 다른 문구를 줄 수 있지만, 사용자에게 보이는 문장을 마감 전에 늘리는
것보다 **원인을 없애는 쪽**을 골랐다. 백로그에 남긴다.

**로컬은 전부 초록이다** — `pytest` 1,281 passed / 2 skipped, `vitest` 22 파일
155건, tsc·eslint·build 통과. 그리고 앞 편과 같은 말을 한 번 더 적는다:
**이번 편이 고친 것 중 공개 URL 에서 확인된 것은 아직 하나도 없다.** 새 태그를
올리고 밖에서 다시 찍기 전까지는 「고쳤다」가 아니라 「고쳤다고 믿는다」다.

이번 건이 앞 편의 교훈을 하나 뒤집는다. 앞 편은 **「셋이 조용한 것은 안
물어봤다는 뜻이다」** 였다. 이번엔 물어봤고, **답이 왔고, 그 답이 502 였는데
백엔드는 멀쩡했다.** 상태 코드는 「무엇이 깨졌나」가 아니라 **「누가 먼저
포기했나」** 를 말하기도 한다. 밖에서 한 번 찍고 원인을 정하면 안 되고,
**두 번 찍어 갈리는지 봐야 한다** — 이 건은 두 번째 요청이 200 을 주는 것
하나로 진단이 끝났다.
