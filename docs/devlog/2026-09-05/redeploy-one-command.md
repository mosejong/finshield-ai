# 절차를 지키는 일을 사람에게서 뺏었다 — 그리고 스크립트는 자기 자신을 갈아엎고 있었다

2026-09-05, 같은 날 다섯 번째 편. 앞 네 편이 전부 **배포한 것과 배포됐다고 믿은
것의 차이**에 관한 이야기였다. 이번 편은 그 차이가 어디서 생기는지를 마지막까지
따라간다. 답은 코드가 아니라 **사람이 15줄을 손으로 밟는 절차 그 자체**였다.

---

## 0. 절차는 맞았다. 밟는 쪽이 미끄러졌다

`docs/31` 3-6 은 틀린 적이 없다. 그런데 오늘 하루에 그 절차를 밟다가 **세 번**
미끄러졌고, 셋 다 문서를 더 잘 써서 막을 수 있는 종류가 아니었다.

**하나. `cd` 가 실패했는데 나머지가 계속 실행됐다.** 여러 줄을 한꺼번에
붙여넣으면 셸은 첫 줄이 실패해도 다음 줄을 읽는다. `cd ~/finshield-ai` 가
실패한 채로 뒤가 다 돌아서, **엉뚱한 위치의 홈 디렉터리에 키 파일이 생겼다.**

**둘. `read -rsp` 가 입력을 기다리지 않고 지나갔다.** 붙여넣기 버퍼 안에 있는
`read` 는 터미널이 아니라 **다음 줄**을 읽는다. 키를 한 글자도 안 쳤는데 명령은
전부 성공했고, **0바이트 키 파일**이 남았다.

**셋. 길이를 확인하기 전에 `chmod 400` 을 걸었다.** 그래서 비어 있다는 사실을
확인하려 했을 때 **읽을 권한이 이미 없었다.** 순서 하나 때문에 진단이 한 단계
늦어졌다.

셋 다 「조심하면 된다」로 끝낼 수 있다. 그러면 다음에 또 난다. 그래서
`deploy/redeploy.sh` 를 만들었다 — **절차를 바꾸지 않고, 절차를 밟는 주체만
바꾼다.**

- `cd` 가 실패하면 `set -e` 가 거기서 멈춘다. 첫 번째는 **구조적으로** 불가능해진다.
- 스크립트가 실행하는 `read -rs` 는 `/dev/tty` 에서 읽는다. 붙여넣기 버퍼가
  아니라 사람에게서 읽는다.
- 길이 확인(`stat -c %s`)이 `chown`·`chmod 400` 보다 **먼저** 온다.

`chmod` 는 여전히 **400 이고 600 이 아니다.** 소유자가 `10001` 이 아닌데 600 을
걸면 아무에게도 권한이 없고, 그것이 2026-08-25 에 서비스를 통째로 내린 실패다.

## 1. 목록이 짧아지는 사고는 목록을 또 적어서 막을 수 없다

배포 첫날부터 금융상품이 503 이었던 원인은 `-f` 목록이 저장소보다 짧았던
것이다(`docs/31` 0절). 스크립트도 목록을 들고 있어야 하는데 — **순서가 있어서**
글롭으로 대신할 수 없다. `compose.yaml` 이 마지막에 오면 `compose.deploy.yaml`
이 `!reset` 으로 지운 `build:` 가 되살아나고, e2-micro 는 그 빌드에서 OOM 으로
죽는다.

그래서 순서는 적어 두고, **적어 둔 것이 저장소와 다르면 멈춘다.**

```bash
readonly COMPOSE_ORDER=(compose.yaml compose.https.yaml compose.deploy.yaml
                        compose.gemini.yaml compose.public-data.yaml)
```

`check_compose_list` 가 이것을 실제 `compose*.yaml`(staging 제외)과 대조한다.
그리고 `tests/test_public_routing.py` 가 **문서와 스크립트 양쪽**을 같은 기준으로
검사한다. 새 override 를 만들면 두 곳에 더하는 것이 선택이 아니게 됐다.

## 2. `exec caddy` 는 아무것도 안 하고 성공한다

문서에 적혀 있던 확인 명령이 `$DC exec caddy …` 였는데, **compose 서비스 이름은
`proxy` 다.** 그 명령은 `service "caddy" is not running` 을 찍고 끝난다. 오타
하나가 확인 절차를 통째로 무력화한 것이고, 사람이 읽으면 「뭔가 안 떠 있나 보다」
로 넘어간다.

그래서 검사를 하나 더 붙였다. **문서와 스크립트에 나오는 모든 `$DC exec` /
`$DC run` 의 서비스 이름이 compose 에 실제로 있는가.** 없는 이름을 부르면
테스트가 떨어진다. 플래그를 몰라서 서비스 이름을 잘못 집는 경우에는 검사가
"모르는 플래그. 검사를 먼저 고친다" 라고 말하고 죽는다 — **조용히 통과하는
것보다 낫다.**

## 3. 네 번째 「조용한 성공」

`deploy/Caddyfile` 을 바꾼 릴리스를 올리면서 문서가 시키는 대로 `caddy validate`
와 `caddy reload` 를 돌렸다. **둘 다 성공했고 `/health` 는 계속 404 였다.**

| 어디서 | `grep -c public_health deploy/Caddyfile` |
|---|---|
| VM 호스트 | **2** |
| 같은 명령, 컨테이너 안 | **0** |

그런데 `reload` 는 `Valid configuration` 이라고 답했다. **거짓말이 아니라 다른
파일을 보고 있었다.** Docker 의 단일 파일 bind mount 는 경로가 아니라 **inode 에
붙는다.** `git checkout` 은 파일을 제자리에서 고치지 않고 **새로 써서 이름을 바꿔
단다.** inode 가 바뀌고, 컨테이너는 이름이 사라진 옛 inode 를 계속 읽는다.

고친 방법은 둘이다. 문법은 **새 컨테이너**에서 보고, 반영은 **재생성**으로 한다.

```bash
$DC run --rm --no-deps --entrypoint caddy proxy validate --config /etc/caddy/Caddyfile
$DC up -d --force-recreate proxy
```

인증서는 `caddy-data` 볼륨에 있어 재생성으로 잃지 않는다. 몇 초 끊기지만
**끊긴 것은 보이고, 반영 안 된 것은 안 보인다.**

이것으로 같은 성질의 실패가 넷이 됐다. 문서의 `-f` 목록이 짧은 것, `pull` 이
작업본에서 오는 파일을 안 건드리는 것, `up -d` 가 mount 된 파일 **내용** 변화로는
컨테이너를 안 다시 만드는 것, 그리고 이번의 inode. **넷 다 확인 명령이
통과한다.** 통과했다는 사실 자체가 반영을 뜻하지 않는다는 것이, 이 문서군에서
가장 비싸게 배운 한 줄이다.

## 4. 자동화가 **새로** 만든 위험 하나

여기서 손 절차에는 없던 위험이 하나 생긴다.

스크립트는 3절에서 `git checkout "$TAG"` 를 돌린다. 그 순간 **`deploy/redeploy.sh`
자신이 새 내용으로 바뀐다.** 그리고 bash 는 스크립트를 통째로 읽어 두지 않고
**실행하면서 조금씩 읽는다.** 파일이 바뀌면 남은 절반을 엉뚱한 바이트 위치부터
읽는다 — 운이 좋으면 문법 오류로 죽고, 나쁘면 **줄 하나가 반쯤 잘린 채**
실행된다. 이 스크립트에서 반쯤 잘려서 실행되면 곤란한 줄은 `chmod`, `sed -i`,
`up -d` 다.

손으로 붙여넣을 때는 이 문제가 없다. **자동화했기 때문에 생긴 위험이다.**

막는 방법은 한 줄이다. 시작하자마자 자기 사본을 만들어 거기서 다시 실행한다.

```bash
if [ -z "${FINSHIELD_REDEPLOY_COPY:-}" ]; then
    _root="$(cd "$(dirname "$0")/.." && pwd)"
    _copy="$(mktemp)"
    cat "$0" > "$_copy"
    FINSHIELD_REDEPLOY_ROOT="$_root" FINSHIELD_REDEPLOY_COPY="$_copy" \
        exec bash "$_copy" "$@"
fi
rm -f -- "$FINSHIELD_REDEPLOY_COPY"
```

사본은 **바로 지운다.** 실행 중이어도 열린 fd 는 살아 있어서 남은 줄은 그대로
읽히고, 중간에 죽어도 `/tmp` 에 찌꺼기가 남지 않는다.

대가가 하나 있다. 사본에서 도는 동안 `$0` 은 `/tmp/tmp.XXXX` 다. 그래서 저장소
위치는 미리 계산해 환경변수로 넘기고, 사용법에 찍는 이름은 상수로 박았다.
**사본에서 `$0` 을 다시 쓰면 저장소 밖을 가리킨다** — 그것도 검사로 막았다.

## 5. 못 박은 것 넷

전부 Docker 를 부르지 않는다. Docker 없는 개발 머신에서도, CI 에서도 돈다.

- **「부르는 서비스 이름이 실제로 있는가」** — 문서·스크립트 양쪽. `exec caddy` 가
  다시 들어오면 떨어진다.
- **「Caddyfile 은 reload 가 아니라 재생성으로 반영한다」** — `caddy reload` 라는
  글자가 다시 나타나면 떨어지고, `validate` 를 `exec` 로 하면 떨어진다.
- **「override 목록이 저장소와 같은가, `compose.yaml` 이 첫 번째인가」** —
  목록이 조용히 짧아지는 원래의 사고를 그대로 겨눈다.
- **「자기 자신을 바꾸기 전에 사본으로 옮겼는가」** — 사본 생성이 `git checkout`
  보다 앞에 오는지, 사본 이후로 `$0` 을 쓰지 않는지, 그리고 실제로 돌려서
  사용법 첫 줄이 `사용법: deploy/redeploy.sh <태그>` 인지(절대경로가 새 나오면
  사본으로 안 옮겨진 것이다).

넷 다 **가드를 뺀 스크립트로 돌려서 실제로 빨개지는 것을 확인했다.** 통과만
하는 시험은 회귀를 못 막는다.

## 6. 안 한 것

**완전 무인 자동화는 안 했다.** 사람이 아예 안 끼려면 밖에서 VM 안으로 들어오는
경로를 새로 열어야 한다 — 배포 권한을 가진 인바운드 경로다. 그것은 보안 검토가
붙는 변경이고, **마감 이틀 전에 새로 여는 문이 아니다.** 지금 줄어든 것은 **사람이
치는 명령 수 15 → 1** 이지, 사람 자체가 아니다.

**공개 URL 프로브는 스크립트에 안 넣었다.** 배포한 기계가 스스로 「배포됐다」를
확인하면 라우팅·인증서·DNS 가 검사에서 통째로 빠진다. 오늘 하루가 통째로 그
교훈이었다. 스크립트는 마지막에 **밖에서** 돌릴 명령을 안내하고 끝난다.
