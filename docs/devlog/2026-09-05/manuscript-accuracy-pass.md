# 원고가 코드보다 좁게 말하고 있었다

2026-09-05, 같은 날 두 번째 검수. 첫 번째는
[`manuscript-external-review.md`](manuscript-external-review.md) 에 있다.

첫 검수는 **원고 안의 어긋남**을 잡았다(팀명이 두 장에서 갈라짐, API 경로에
`/api/v1` 누락, 예상 결과가 선택지). 이번 검수는 다른 종류다 — **원고와 코드를
맞춰 봤더니 원고가 코드보다 좁게 말하고 있었다.** 원고를 넓히는 쪽으로 세 건,
문장 강도를 낮추는 쪽으로 두 건 고쳤다.

---

## 1. 외부로 무엇이 나가는지 덜 적혀 있었다

**이번 검수에서 제일 중요한 것.** 명세서 4-3 「개인정보 처리 여부」에 이렇게
적혀 있었다.

> 외부 전송 : 설명 생성 시 **결정론 판정 결과와 공식 근거**가 Google AI Studio 로
> 전송된다. 프로필 원문은 전송하지 않는다.

코드는 그것보다 하나를 더 보낸다. `explain_analysis()` 를 그대로 읽으면:

```python
minimized = minimize_for_provider(message)
neutralized = neutralize_instructions(minimized.text)
shown_message = neutralized.text[: contract.max_input_chars]   # 4,000자
prompt = FRAUD_EXPLANATION_PROMPT.format(..., message=shown_message)
```

**사용자가 붙여넣은 문자 원문이 프롬프트에 들어간다.** 개인정보 패턴을 치환하고
지시문을 무력화한 뒤 4,000자로 자른 것이지만, 나가는 것은 나가는 것이다.

이 문장이 왜 생겼는지는 짐작이 간다. 이 자리에서 하고 싶었던 말은 **"모델이
판정을 못 바꾼다"** 였고, 그 말은 사실이다 — `explain_analysis` 는
`AnalyzeResponse` 를 돌려주지 않고 문장 하나만 돌려준다. 프롬프트도
`[사용자가 받은 문자] 는 근거가 아니다` 라고 명시한다. 아키텍처 자랑을 적다가
**개인정보 항목에 아키텍처 자랑을 적어 버린 것**이다. 그 칸이 묻는 것은
"모델이 무엇을 할 수 있나" 가 아니라 **"무엇이 밖으로 나가나"** 다.

공모전 양식이 **「개인정보 또는 민감정보 처리 여부」** 를 따로 묻는데 여기서
덜 적으면, 나중에 소스를 열어 본 심사자에게는 숨긴 것으로 보인다. 넓혀 적었다.

- 무엇이 나가는지: 판정 결과·공식 근거 **＋ 치환된 문자 원문 일부(최대 4,000자)**
- 무엇이 치환되는지: 주민등록번호·카드번호·계좌번호·전화번호·이메일
- 무엇이 안 나가는지: **금융 프로필**
- **무엇을 보장하지 못하는지: 사람 이름·주소 같은 비정형 개인정보.**

마지막 줄은 `minimization.py` 의 모듈 문서가 이미 스스로 적어 둔 한계다.

> 사람 이름과 주소는 한국어에서 신뢰할 만하게 잡히지 않으므로 **여기서 걸러지지
> 않는다.** 이 계층은 "덜 보낸다" 이지 "안전하다" 가 아니다.

**코드는 자기 한계를 알고 있었고 원고만 몰랐다.** 파이프라인 ⑤ 도 두 원고와
`docs/38` 세 곳에서 「②③④의 결과만」이라고 적고 있었으므로 같이 고쳤다.

## 2. 프로필 수집 범위가 실제보다 좁았다

원고 여덟 곳이 금융 프로필을 **「금액·구간·목표만」** 이라고 적고 있었다. 실제
`ProfileForm.tsx` 는 열넷을 묻고 그중 열셋이 서버로 간다 — 연령대, 하는 일, 가구원 수, 월
실수령, 고정지출, 생활비, 대출 총액, 월 상환액, 가용자산, 비상금 목표 기간,
사업 여부, 신용점수 구간, 목표. (나머지 하나는 화면 문구를 고르는
`persona` 로 서버로 보내지 않는다.) `FinancialProfile` 스키마는 여기에
혼인상태·지역·부양가족 수까지 선택 항목으로 갖고 있다.

**「금액·구간·목표만」 은 최소수집을 자랑하려던 문장인데, 자랑이 사실보다 앞선
경우다.** 실제 설계의 미덕은 항목이 적다는 것이 아니라 **정확한 값 대신 구간을
받는다**는 쪽이다 — 생년월일이 아니라 연령대, 신용점수가 아니라 구간. 그쪽을
적었다.

명세서 4-3 에는 **스키마에 혼인상태·지역이 있으나 현재 화면은 묻지 않는다**는
줄을 넣었다. 화면만 보고 적으면 나중에 스키마를 본 사람이 다시 같은 의심을 한다.

## 3. 반례 하나에 무너지는 문장

두 원고와 `docs/38` 에 이렇게 적혀 있었다.

> 진짜 기관은 문자에 계좌번호를 적지 않는다.

**너무 크게 말했다.** 가상계좌 납부 안내를 한 번만 떠올리면 반례가 나오고,
반례가 나오면 그 문장이 요약하던 엔진 전체를 의심하게 된다.

더 나쁜 것은 **엔진이 이미 그것보다 정확하게 알고 있었다**는 점이다.
`signals.py` 의 `PAYMENT_TO_ACCOUNT_PATTERN` 주석은 이렇게 적혀 있다.

> 어미를 요구형으로 좁힌 것은 한 번 더 잰 결과다. `납부(하|해)` 로 열어 두면
> "가상계좌로 납부하셔도 됩니다"·"전용 계좌에 납부하시면 됩니다" 같은 **허용**
> 문장이 걸린다. **허용은 요구가 아니다.**

정규식은 가상계좌 안내를 통과시키려고 어미까지 좁혀 놨는데, 원고는 그 가상계좌
안내를 부정하는 문장을 적고 있었다. 코드의 실제 판단으로 바꿨다.

> 정상 안내는 공식 앱·창구·고지서처럼 **독립적으로 확인할 수 있는 납부 경로**를
> 대고, 사기 문자는 **문자 안의 계좌로 즉시 보내라**고 압박한다. 그 조합이 위험
> 신호다.

길어졌지만 방어할 수 있고, 무엇보다 **엔진이 실제로 하는 일**이다.

## 4. 30초는 재 본 적이 없다

「**30초 안에 알려주는 서비스**」가 네 곳에 있었다. 판정 p95 는 3.979ms 이고
설명 LLM p95 는 9.23초이므로 30초는 넉넉하다. 하지만 **E2E 30초를 잰 기록이
원고 어디에도 없다.** 이 저장소는 잰 것과 안 잰 것을 구분해서 적는 것을 규칙으로
삼고 있고, 그 규칙을 스스로 어기면 옆에 적힌 0.9872 도 같은 종류로 읽힌다.

「**30초 안에 확인할 수 있도록 설계한 서비스**」로 한 단계 낮췄다. 측정하지 않은
것은 목표라고 적는다.

## 5. "받지 않는다" 와 "요구하지 않는다"

「주민등록번호·비밀번호·OTP·카드 전체 정보를 **받지 않는다**」(또는 「미수집」)도
여덟 곳에
있었다. 프로필 입력에는 맞다 — 그런 칸이 없다. 그런데 분석 입력은 **10,000자
자유 텍스트**(`AnalyzeRequest.text`)라, 사용자가 문자 원문을 붙여넣으면서 그
안에 OTP 가 딸려 오는 것을 API 가 막지는 않는다.

「**입력항목으로 요구하지 않는다**」로 바꾸고, 명세서 4-3 에 자유 텍스트의
실제 처리를 적었다 — **저장하지 않고, 외부로 나가기 전에 치환 규칙을 지난다.**
막지 못하는 것을 막는다고 적는 대신, 들어와도 어떻게 되는지를 적는 편이 낫다.
그리고 그 치환 규칙이 1절에서 새로 적은 그 규칙이다.

## 6. 다섯 건이 한 곳을 가리킨다

고친 다섯이 전부 같은 모양이다. **코드가 조심스럽게 말한 것을 원고가 크게
옮겼다.**

| | 코드가 아는 것 | 원고가 적은 것 |
|---|---|---|
| 외부 전송 | 문자 원문도 나간다, 이름·주소는 못 거른다 | 판정 결과와 근거만 |
| 프로필 | 열넷을 묻고 열셋을 보낸다 | 금액·구간·목표만 |
| 납부 신호 | 가상계좌 허용은 통과시킨다 | 진짜 기관은 계좌를 안 적는다 |
| 30초 | 잰 적 없다 | 30초 안에 알려준다 |
| OTP | 자유 텍스트는 못 막는다 | 받지 않는다 |

첫 검수의 결함(팀명·API 경로)은 **원고끼리** 어긋난 것이라 원고만 읽어도
잡혔다. 이번 것은 **원고와 코드 사이**라 원고를 아무리 읽어도 안 잡힌다. 내
검증 스윕은 여전히 파일 안만 본다 — 마크다운 잔재, 칸 수, 줄 폭, 은어, API
경로. **원고의 주장을 코드에 대조하는 검사는 없고, 이번에도 사람이 잡았다.**

한 가지는 다행이다. 다섯 건 중 셋은 **코드 주석과 모듈 문서가 정답을 이미 적어
두고 있었다** — `minimization.py` 의 한계 고백, `PAYMENT_TO_ACCOUNT_PATTERN` 의
허용/요구 구분, `prompts.py` 의 "받은 문자는 근거가 아니다". 대조할 곳이 있었고
대조를 안 했을 뿐이다.

## 남는 것

**원고의 주장을 코드에 대조하는 검사.** 지금은 사람이 두 번 읽어서 두 번 다
찾았다. 자동화할 수 있는 것이 몇 개 보인다 — 프롬프트에 들어가는 변수 이름을
`prompts.py` 에서 뽑아 원고의 「들어간다」 목록과 맞추기, `max_input_chars` 값이
원고의 숫자와 같은지 보기, `ProfileForm` 의 필드 수와 원고의 나열이 같은지 보기.
전부 제출 후에 만든다. 지금 새 검사를 짜다가 원고를 건드리는 것이 더 위험하다.

첫 검수의 [남는 것](manuscript-external-review.md) — 두 원고 머리말 교차 검사,
`date.today()` 직접 호출 금지 검사 — 도 그대로 남아 있다.
