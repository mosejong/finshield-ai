# 11칸을 다 찍고 나서야 "고쳤다" 를 쓴다

2026-09-05 · `v0.9.1` 공개 URL 재검수

## 1. 무엇을 확인했나

앞 회차의 판정은 `FAIL` 이었다. 원인 둘은 이미 박아 두었다 — 콜드 경로에서
끊어지던 상품 요청과, 리버스 프록시에 없던 공개 `health` 경로. 고친 코드는
초록이었고 태그도 있었다. **그것으로는 아무것도 증명되지 않는다.**

이 회차의 일은 코드가 아니라 **확인**이다. `v0.9.1` 을 실제 VM 에 올리고,
올리기 전에 적어 둔 11칸을 밖에서 하나씩 찍었다.

## 2. 기준을 먼저 적었다

`docs/31` 의 「`v0.9.1` 을 올린 뒤 찍을 것」은 **배포 전에** 쓰였다. 표에
"안 됐으면, 그리고 그 뜻" 칸을 같이 만들어서, 실패했을 때 무엇을 의심할지까지
정해 두었다.

가장 신경 쓴 칸은 이것이다.

> **8번이 9초대여도 통과다.** 이번 수정은 콜드 경로를 **빠르게** 만든 것이
> 아니라 **끊기지 않게** 만든 것이다.

찍고 나서 기준을 정하면 나온 값이 기준이 된다. 그러면 다음에 제공자가 조금
느려졌을 때 또 「고장」으로 읽는다.

## 3. 결과

11칸 전부 왼쪽이다. 자세한 값은 `docs/31` 12절에 있다. 여기서는 **무엇을
말해 주는 값인지**만 적는다.

| 칸 | 값 | 무엇을 말해 주나 |
|---|---|---|
| 콜드 첫 상품 요청 | `200` **5.65초** | 직전 확인의 9.64초 `502` 가 사라졌다 |
| 바로 두 번째 | `200` **1.01초** | 캐시가 물렸다. 8번의 5.65초가 콜드 비용이었다는 뜻 |
| `/health` · `/health/ready` | `200` `ok` · `ready` | 새 `Caddyfile` 이 **돌고 있다** |
| `/internal/metrics` | `404` | 열지 않기로 한 것은 안 열렸다 |
| 상세 · 비교 | `200` · `200` 2건 | 목록만 살아난 것이 아니다 |
| 설명 계층 셋 | `ready` · `not_asked` · `low`/`0` | 앞 회차들이 그은 세 경계가 다 살아 있다 |

## 4. 두 번 찍는 것이 원인을 가른다

이번 회차에서 다시 확인된 방법 하나. `502` 는 **두 가지를 뜻한다** —
제공자가 실패했거나, 우리가 기다리기를 멈추었거나.

한 번만 찍으면 그 둘이 같은 화면으로 보인다. 연달아 두 번 찍으면
`9.64초 502` → `1.11초 200` 처럼 **모양이 갈라진다.** 두 번째가 빠르게 성공하면
제공자는 살아 있었던 것이고, 남는 설명은 하나뿐이다.

이번에는 `5.65초 200` → `1.01초 200` 이었다. 같은 모양의 앞칸만 살아난 것이고,
그것이 정확히 고치려던 것이다.

## 5. 고치지 않은 것도 찍었다

전세 판정과 상태 전환은 이번 릴리스가 손대지 않았다. 그래서 찍었다.
**회귀는 고친 곳이 아니라 안 건드린 곳에서 나온다.**

- 전세 2억 / 시세 2.5억 / 선순위 1억 → `high`, 비율 120%,
  `band_is_service_rule: true`
- 같은 문장, 상태만 `received_only` → `transferred_money`:
  점수 70점 **그대로**, 행동 5 → 9, 근거 3 → 5

상태를 바꿔도 점수가 안 움직이는 것이 맞는 모양이다. 문장의 위험도는 내가
무엇을 했는지와 무관하고, 달라지는 것은 **지금 해야 할 일**이다. 늘어난 넷은
`CONTACT_112`, `CONTACT_FINANCIAL_INSTITUTION`, `DO_NOT_FORWARD_MONEY`,
`PRESERVE_EVIDENCE` — 전부 수습 쪽이다.

## 6. 안 찍은 칸을 안 찍었다고 적었다

`docs/31` 의 프로브 목록에는 컨테이너 안에서 세는 칸이 하나 있었다.

```bash
$DC exec proxy grep -c public_health /etc/caddy/Caddyfile
```

이건 안 찍었다. 대신 밖에서 `/health` 가 `200 {"status":"ok"}` 로 왔고, 그
경로는 새 설정에만 있으므로 **돌고 있는 설정**이 새것이라는 뜻이다. 파일이
맞아도 안 물렸을 수 있지만, 라우팅이 되면 물린 것이다 — 더 강한 증거다.

그래도 **문서에 "안 찍었다" 를 적었다.** 통과한 칸만 남기면 다음 사람은 그
줄이 왜 없는지 모른다. 없는 줄은 "확인 안 함" 과 "확인했는데 실패" 를 구분해
주지 못한다. `v0.4.0` 이 정확히 그렇게 대장에서 사라졌었다.

## 7. 브라우저 두 칸도 같은 날 채워졌다

5절의 상태 전환은 **엔진이 답을 바꾼다**는 것까지만 말한다. 화면이 그 답을
다시 받아 오는지는 별개의 고장이고, 그 값은 메모리 한 칸에 살아서 `curl` 로는
흔적이 없다. 그래서 사람이 눌렀다.

- 「상황이 달라졌어요」 → 「돈을 보냈어요」: 결과 id 가
  `a-mtogd8cd-l1m7dd` → `a-mtogdvbz-11uxwu` 로 바뀌고 **행동 5 → 9, 근거 3 → 5**
- 프로필 저장 → 새로고침 유지 → 삭제 → 재접속 시 검수값 없음

**행동 5 → 9 가 화면과 API 에서 같은 값이다.** 이 한 줄이 요점이다. 두 곳이
갈릴 수 있었고, 안 갈렸다.

## 8. 못 잰 칸 하나를 적어 둔다

검수에 쓴 Cloud Browser API 에 **viewport / device emulation 이 없다.** 특정
모바일 폭에서의 배치는 이번 회차에서 재지 못했다.

지금 있는 증거는 **2026-08-13 실측**이다 — 375×812 · 768×900 · 1280×900 에서
네비 전환과 본문 폭 375 · 560 · 680px 을 직접 쟀고, 그 뒤로
`web/components/layout/` 과 `web/app/globals.css` 는 한 번도 바뀌지 않았다.
그때 잰 셸이 지금 배포된 셸이다.

**그래도 "확인함" 으로 안 적는다.** 그 사이 새로 생긴 화면이 둘 있고
(`/check/deposit`, `/offline`) 그 둘은 폭을 재 본 적이 없다. 셸이 같다는 것과
그 안의 내용이 좁은 폭에서 안 넘친다는 것은 **다른 주장**이다.

6절과 같은 규칙이다 — 못 찍은 칸을 비워 두면 「확인 안 함」과 「확인했는데
실패」가 구분되지 않는다. 이 문서에서 두 번 나온 규칙이고, 두 번 다 값이 있었다.
