# 금융상품은 공개 이후 한 번도 나간 적이 없다

2026-09-05, 같은 날 세 번째 편. 앞의 둘은 원고를 고쳤고
([`manuscript-external-review.md`](manuscript-external-review.md),
[`manuscript-accuracy-pass.md`](manuscript-accuracy-pass.md)), 이번엔 **공개
URL 을 밖에서 직접 눌러 본 결과**다.

외부 검수가 공개 주소에서 열 가지를 눌렀고 **두 가지가 죽어 있었다** —
금융상품 목록·상세·비교가 전부 실패, `/health` 와 `/health/ready` 가 404.
판정은 보류였고, 그 판정이 맞다.

다만 원인을 파 보니 **"프로젝트가 망가졌다" 가 아니었다.** 두 건 다
애플리케이션 코드는 멀쩡하고, **배포 구성에서 빠진 것**이다. 그리고 둘 다
**한 번도 동작한 적이 없다** — 회귀가 아니라 처음부터 없었던 것이라, 릴리스를
되돌려도 살아나지 않는다.

---

## 0. 먼저 추측을 끊었다

**503 인지 502 인지부터 갈랐다.** VM 에 못 들어가는 상태에서 이걸 구분할 수
있었던 것은 프론트 프록시가 상태 코드를 아무렇게나 덮지 않기 때문이다.

```ts
// web/lib/api/proxy-response.ts
const PASSTHROUGH_STATUSES = new Set([401, 404, 413, 429, 503]);
```

`503` 은 통과하고 나머지는 `502` 가 된다. 그래서 **밖에서 찍은 코드 하나가
"백엔드가 설정을 못 찾았다"(503) 와 "공공데이터 호출이 실패했다"(502) 를
가른다.** 찍으니 **503** 이었다.

`app/api/routes/products.py` 에서 503 이 나오는 자리는 하나뿐이다 —
`get_product_catalog_service()` 가 `ProductProviderConfigurationError` 를 잡는
곳, 즉 **배포된 백엔드에 `PUBLIC_DATA_SERVICE_KEY` 가 없다.**

## 1. 그 키를 켜는 파일이 재배포 목록에 없었다

`PUBLIC_DATA_SERVICE_KEY` 를 넣는 파일은 `compose.public-data.yaml` 하나다.
그런데 **`docs/31` 전체에 `public-data`·`공공데이터`·`금융위` 가 한 글자도
없었다.** 재배포 절차에 적힌 조합은 이랬다.

```
docker compose -f compose.yaml -f compose.https.yaml -f compose.deploy.yaml ...
```

**문서가 이 조합을 시키는 한, 몇 번을 재배포해도 상품은 안 켜진다.** 그래서
이건 `v0.7.0` 회귀가 아니라 **공개 배포 이후 줄곧 그랬던 것**이다.

### 왜 여드레 동안 아무도 몰랐나

두 겹으로 조용했다.

1. **`/health/ready` 가 이 제공자를 안 본다.** 인증 세션과 프로필 저장소만
   확인하므로 **컨테이너는 계속 건강했다.** 상품 제공자가 죽어도 헬스체크는
   초록이다.
2. **`verify_public_deployment.py` 가 페이지 200 만 봤다.** `PUBLIC_PATHS` 에
   `/products` 가 있고 그 경로는 **정말로 200 을 준다** — 껍데기가 서버에서
   렌더되고, 실패는 그 뒤 클라이언트 fetch 에서 난다. **페이지가 200 이라는
   것과 그 화면의 API 가 살아 있다는 것은 다른 말인데, 검사기가 그 둘을 같은
   것으로 세고 있었다.**

이 저장소에서 반복되는 문장이 여기서 또 나왔다 — **검사가 조용한 것은
안전하다는 뜻이 아니라 그 질문을 한 적이 없다는 뜻이다.** 다섯 번째다.

### 고친 것

검사기에 **`product:*` 세 칸**을 넣었다. 목록(`POST /api/proxy/recommendations`)
→ 상세 → 2개 비교를 **체인으로** 찍는다. 상세와 비교에 쓰는 상품 번호는
하드코딩하지 않고 **목록이 방금 돌려준 것**을 쓴다 — 기준월이 바뀌면 고정
번호는 404 가 되고, 그 404 는 배포 결함이 아닌데 결함처럼 보인다.

목록이 실패하면 **상세·비교는 건너뛴다.** 원인 하나를 세 번 세면 무엇이
망가졌는지가 아니라 몇 칸이 빨간지만 남는다.

그리고 상태 코드마다 **원인을 이름으로 적어 준다.** 다음에 이걸 보는 사람이
나일 이유가 없다.

| 코드 | 검사기가 뭐라고 하는가 |
|---|---|
| 503 | 설정 누락 — backend 에 `PUBLIC_DATA_SERVICE_KEY` 가 없다 (`compose.public-data.yaml`) |
| 502 | 제공자 실패 — 키는 있고 공공데이터 호출이 실패했다 |
| 404 | 그 상품이 이번 기준월 목록에 없다 |
| 400 | 요청이 스키마에 안 맞는다. 검사기 쪽 문제다 |

`docs/31` 에는 **키 파일을 올리는 절차**를 새 절로 넣었다. 8월 25일에
`chmod 600` 하나로 서비스를 통째로 내렸던 그 규칙 그대로다 — `read -rsp`(에코
없음), `printf '%s'`(줄바꿈 없음), `chown 10001:10001`, **`chmod 400`**.
확인 명령도 키 길이만 찍는다.

## 2. `/health` 는 인터넷에서 404 였다

Caddy 가 이랬다.

```
reverse_proxy web:3000
```

**catch-all 하나뿐이라 `/health` 도 Next 로 갔고**, Next 에 그런 라우트가 없어
404 다. 백엔드는 살아 있었다 — 아무도 물어보지 않았을 뿐이다.

고칠 때 **두 가지를 좁게 잡았다.**

**하나, Host.** `compose.https.yaml` 이
`FINSHIELD_TRUSTED_HOSTS: backend,localhost,127.0.0.1` 을 준다. 공개 Host 를
그대로 넘기면 백엔드가 **400** 을 준다. 신뢰 목록을 넓히는 대신
`header_up Host backend:8000` 으로 **이 경로에서만** 바꿨다.

**둘, 여는 범위.** 정확히 세 경로만 연다.

```
@public_health path /health /health/live /health/ready
```

`/internal/metrics` 는 **일부러 안 열었다.** 이름이 `internal` 인 것을 장애
고치는 김에 인터넷에 함께 붙이는 것은 별개의 결정이고, 마감 이틀 전에 같이
할 일이 아니다.

검사기에도 **`health:*` 세 칸**을 넣었는데, 여기서 한 가지를 조심했다 —
**200 이 왔다고 통과시키지 않는다.** 라우팅이 안 고쳐진 상태에서 Next 가
그럴듯한 200 을 줄 수도 있으므로, 본문에 `"ok"`/`"alive"`/`"ready"` 가 있는지
본다. 그 검사를 지키는 테스트를 따로 뒀다(`test_two_hundred_from_the_wrong_service_fails`).

## 3. 진짜 원인은 셋째 것이었다

두 장애가 서로 다른 파일에서 났지만 **같은 구멍에서 나왔다.**

`caddy validate` 도 `docker compose config` 도 **문법만 본다.** 둘 다
"문서에 적힌 목록이 코드가 필요로 하는 것보다 짧다" 는 말을 할 수 없다. 그래서
`compose.public-data.yaml` 이 여드레 동안 아무 경고 없이 빠져 있었다.

`tests/test_public_routing.py` 를 새로 만들어 **문서와 저장소를 대조**한다.

```python
line = re.search(r'^DC="docker compose (.+)"', text, re.M)
documented = set(re.findall(r"-f (compose[\w.-]*\.yaml)", line.group(1)))
actual = {p.name for p in REPO_ROOT.glob("compose*.yaml")} - {"compose.acme-staging.yaml"}
```

**새 override 를 만들고 문서에 안 적으면 테스트가 떨어진다.** Docker 없이
도는 검사라 로컬에서도 CI 에서도 같이 돈다. 같은 파일이 Caddy 의 health
matcher 가 실제 FastAPI 라우트와 일치하는지도 본다 — 라우트를
`router.routes` 에서 읽으므로, 경로 이름을 바꾸면 문서가 아니라 테스트가 먼저
운다.

CI 에는 **override 를 전부 얹은 조합**을 `docker compose config` 로 한 번
돌리는 단계를 넣었다. 파일 목록은 **다시 타이핑하지 않고 `ls` 로 만든다** —
목록을 손으로 적는 것이 이 사고의 원인이었으므로 같은 자리에서 같은 실수를
반복할 이유가 없다.

## 4. 결과 화면에서 상황을 바꿀 수 있게 했다

검수가 짚은 것 중 기능에 해당하는 것 하나. 명세서는 「결과 화면에서 상태를
바꿔 다시 확인」이라고 적었는데 실제로는 `/check` 로 돌아가는 링크뿐이었고,
**돌아가면 붙여넣은 문자가 사라진다.**

이 전환이 왜 중요한지는 이 서비스의 축이다 — 같은 문자라도 「받기만 함」과
「송금함」은 행동 5개와 9개를 받는다. 그리고 그 전환은 **결과를 읽는 도중에**
일어난다("아 맞다, 링크는 눌렀었다"). 그때 원문을 다시 붙여넣게 하면 대부분은
그냥 나간다.

**구현을 작게 유지하려고 두 가지를 정했다.**

`explanation-store` 를 고치지 않았다. 그쪽은 **요청을 만드는 즉시 원문을
버리도록** 일부러 만든 것이고, 지금 살아 있는 설명 경로를 마감 이틀 전에
건드리지 않는다. 대신 `recheck-store.ts` 를 따로 뒀다 — 메모리 한 칸, 한 건만,
「이 결과 지우기」가 같이 지운다. **sessionStorage 도 서버도 아니다.** 그래서
새로고침한 화면에서는 이 기능이 사라지고 종전 링크로 물러난다.

다시 확인하면 **새 결과 id 를 만든다.** 같은 id 에 덮어쓰면 설명 캐시가 id 로
묶여 있어서 **상황이 바뀌었는데 앞 상황으로 만든 설명이 그대로 붙는다.**
앞의 결과는 지우고 `router.replace` 로 넘어간다.

모듈 변수를 렌더 본문에서 그냥 읽지 않고 `useSyncExternalStore` 로 감쌌다 —
`session-store.ts` 의 `useHydrated` 와 같은 모양이고, 이 저장소가 이미 주석으로
적어 둔 하이드레이션·React Compiler 함정 때문이다.

## 5. 작은 것 셋

- **프로필 화면에 익명 세션 안내 문단이 두 번** 똑같이 찍히고 있었다. 하나 지웠다.
- **탭 제목에 서비스 이름이 두 번** 붙었다(`금융상품 | FinShield · FinShield`).
  루트 레이아웃의 `title.template` 이 이미 이름을 붙인다. 검수가 짚은 것은 두
  건인데 **찾아보니 세 건**이었다(`/products/simulate` 가 더 있었다). 나머지
  페이지는 `grep` 으로 확인했다.
- 제출 원고 네 곳이 `/internal/metrics` 를 공개 API 목록에 넣고 있었다. 이번에
  일부러 안 열었으므로 **「내부 전용, 공개 주소 아님」** 으로 갈라 적었다.
  심사자가 찍어서 404 를 보는 것과, 안 연다고 적힌 것을 읽는 것은 다르다.

**그때까지 문서의 「구현 완료」 주장은 확정이 아니다.**

## 안 한 것

- **`/health/ready` 에 상품 제공자 검사를 넣지 않았다.** 넣으면 공공데이터가
  흔들릴 때마다 컨테이너가 unhealthy 가 되고 **재시작 루프**로 간다. 준비
  상태와 기능 가용성은 다른 질문이라, 후자는 `verify_public_deployment.py`
  쪽에 뒀다.
- **`/internal/metrics` 공개 여부** — 위에 적은 대로 별개 결정으로 남긴다.
- **`docs/31` 의 「27/27」 숫자를 다시 재지 않았다.** 검사 칸이 여섯 늘었으니 그
  숫자는 더 이상 27 이 아니다. 실제 배포에서 재기 전까지는 틀린 숫자를 새
  숫자로 바꿔 적지 않고, **다시 안 쟀다고 적어 뒀다.**
- **재배포 자동화** — 같은 사고가 네 번째지만, 마감 이틀 전에 배포 경로를 새로
  만드는 것은 여전히 고치는 것보다 깨뜨릴 확률이 높다. 백로그.
