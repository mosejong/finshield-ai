# 코드 검증 패스 · 위험 판정·링크 검사·출처 신선도 수정

- 날짜: 2026-08-14
- 브랜치: `feature/frontend-accessibility-e2e`
- 범위: `app/domain/fraud/`, `app/main.py`, `tests/`, `web/lib/api/`, 문서

## 배경

전체 스위트가 통과한다는 사실만으로는 코드가 맞다고 볼 수 없다. 테스트가 무엇을
확인하지 **않는지**를 모르기 때문이다. 실서버 배포를 앞두고 세 가지 독립적인 방법으로
다시 확인했다.

- **독립 재계산** — 구현을 읽지 않고 표준 공식으로 따로 계산해 대조
- **적대적 E2E 탐침** — 실제 세션 두 개로 HTTP 경계를 뚫어봄
- **Mutation 감사** — 핵심 로직에 고의로 버그를 심고 스위트가 잡는지 확인

## 검증 결과

통과한 것:

- `loan_calculator` — 무작위 800케이스에서 원금 합계, 잔액 단조감소, 최종 잔액 0,
  회차별 `payment = 원금 + 이자`, 이자 = 직전 잔액 × 월이율이 전부 성립. 참조값
  `100000 / 6% / 360개월 → 599.55` 일치. 반올림은 문서화된 `ROUND_HALF_UP`.
- 세션 소유권 — 피해자/공격자 세션 2개로 프로필 GET·metrics·PUT·DELETE를 시도해
  12/12 차단. 타인 자원은 403이 아니라 **404**를 돌려 존재 여부를 감춘다. 쿠키 없음과
  위조 쿠키는 401.
- 프로필 암호화 — Fernet 키링, 첫 키만 쓰기에 사용, 봉투가 `profile_id`를 함께 묶어
  다른 행의 암호문을 옮겨 붙이는 공격을 막는다.
- 공식 출처 8건 — 1394, 경찰청 ECRM, KISA 118, 전자금융거래법 제6조,
  통신사기피해환급법 등 전부 실재. 날조 없음.
- Mutation 감사 — 상태 최소위험, 점수 상한, 반올림 방식, 로그 PII 유출,
  SQL·메모리 소유자 필터 변형을 모두 잡았다.

## 수정 1 — 위험 등급 임계값에 테스트가 없었다

Mutation 감사에서 유일하게 통과한 변형이다. `score >= 70`을 `>= 90`으로 바꿔도 199개
테스트가 전부 통과했다. 죽은 코드인지 확인하려고 등급이 달라지는 입력을 찾았고, 실제로
존재했다.

```
score=72  high -> medium   "오늘까지 인증번호 체크카드 확인 부탁드립니다"
score=77  high -> medium   "오늘까지 체크카드 앱 설치 확인 부탁드립니다"
```

사용자에게 보이는 등급을 직접 바꾸는 살아있는 로직이 무방비였다.

- 임계값을 `HIGH_RISK_SCORE_THRESHOLD` / `MEDIUM_RISK_SCORE_THRESHOLD` 로 명명해
  무엇이 안전 임계값인지 코드에서 드러나게 했다.
- `tests/test_fraud_risk_level.py` 를 추가해 경계 34/35/69/70, 신호별 최소등급,
  조합 규칙, 상태별 최소등급을 **각각 독립적으로** 고정했다. 어느 한 근거가 다른
  근거를 끌어내리지 않는다는 성질도 함께 고정했다.

## 수정 2 — 스킴 없는 링크가 검사를 통과했다

같은 주소인데 스킴 유무로 판정이 갈렸다.

```
http://1.2.3.4/login  ->  suspicious_link 발생
1.2.3.4/login         ->  신호 없음
```

`www.` 나 알려진 단축 URL로 시작할 때만 스킴을 보정했기 때문이다. 실제 스미싱 문자는
`1.2.3.4/login` 형태로 온다.

- 스킴이 없으면 https 를 가정해 호스트를 뽑고, 스킴 유무와 무관하게 같은 검사를
  적용한다.
- 본문에서도 스킴 없는 링크를 후보로 추출한다. 경로가 붙은 것만 후보로 봐서
  `report.pdf`, `3.5/5점`, `2026.08.14/기록` 같은 문자열을 링크로 오인하지 않는다.
- `javascript:`, `data:`, `mailto:` 처럼 호스트가 없는 스킴을 차단한다. 포트 표기
  (`example.com:8080`)와 구분하려고 콜론 뒤 숫자는 스킴으로 보지 않는다.
- `tests/test_fraud_urls.py` 가 의심/정상 목록과 "스킴이 판정을 바꾸지 않는다"는
  성질을 고정한다.

서버가 이 URL을 요청하지 않는다는 정책은 그대로다. 전부 문자열 검사다.

## 수정 3 — 출처 재확인이 서비스를 죽였다

`load_official_sources()` 가 8개 출처의 `retrieved_at` 이 전부 `2026-08-12` 가 아니면
`ValueError` 를 던졌다. 링크 하나를 오늘 다시 확인해서 날짜를 갱신하면 그 순간 분석
요청이 500이 된다. **출처를 최신으로 유지하려는 행동이 서비스를 멈추는 구조**였다.

게다가 `app/main.py` lifespan 에 이 호출이 없어서 startup 과 `/health/ready` 는
통과하고 분석 요청에서만 터졌다. 배포 파이프라인이 정상으로 판단하는 상태에서
사용자만 실패를 본다.

- 형식 오류(ISO-8601 아님)와 미래 날짜만 데이터 오류로 막는다. 이건 실제 데이터 버그다.
- 오래된 출처는 `SOURCE_REVIEW_INTERVAL_DAYS`(365일) 기준으로 `stale_official_sources()`
  가 목록을 돌려주고 기동 시 경고 로그를 남긴다. **분석은 막지 않는다.** 안전 안내를
  끊는 쪽이 오래된 링크를 보여주는 쪽보다 위험하다.
- `verify_official_sources()` 를 lifespan 에 추가했다. 잘못된 데이터는 이제 기동 시점에
  드러난다.
- `tests/test_official_sources.py` 가 재확인·미래 날짜·형식 오류·중복·경과 출처와
  기동 시 검증 호출을 각각 고정한다.

## 수정 4 — 프론트/백엔드 계약 드리프트

OpenAPI 생성 스크립트가 없어 zod 계약은 손으로 쓴다. 대조에서 네 곳이 어긋나 있었다.

- `marital_status` 와 `region` 을 어댑터가 흘리고 있었다. 프로필을 한 번 수정하면
  서버에 있던 값이 `null` 로 덮인다. 화면이 아직 입력받지 않는 값이라 지금은 드러나지
  않지만, 값이 생기는 순간 조용한 데이터 손실이 된다. 왕복에서 보존하도록 고쳤다.
- `marital_status`, `annual_business_revenue_band` 를 `z.string()` 에서 실제 enum 으로,
  `loan_items` 를 `z.array(z.unknown())` 에서 `BackendLoanItemSchema` 로 고정했다.
  느슨한 스키마는 드리프트를 통과시킨다.
- 금리 소수 자릿수가 백엔드 `decimal_places=4` 를 넘을 수 있었다. 요청 전에 거부하고
  전송 시 자릿수를 고정한다. 단, 자릿수를 세면 `0.1 + 0.2` 같은 부동소수점 잡음까지
  거부하므로 "4자리로 반올림해도 값이 같은가"로 판단한다.

`risk_level: z.string()` + `toRiskLevel` 이 알 수 없는 값을 `"high"` 로 떨어뜨리는 것은
의도된 fail-closed 설계이고 테스트도 있다. 그대로 뒀다.

## 남은 것

- `authority_impersonation` 오탐: `"어제 경찰서 다녀왔어요"` → medium. 키워드 기반
  bootstrap 의 구조적 한계이고, **FPR 이 측정된 적이 없다.** 정량 판단은 `docs/28`
  P2-1 평가 하네스가 있어야 가능하다. 임의로 키워드를 빼면 탐지율이 어떻게 변하는지
  알 수 없으므로 이번에는 건드리지 않았다.
- `conftest.py` 가 없어 기본 `pytest -q` 는 `InMemoryFinancialProfileRepository` 경로를
  탄다. SQLAlchemy + 암호화 경로는 `tests/test_profile_persistence.py` 안에서 별도로
  덮는다. 커버리지 구멍은 아니지만 기본 실행이 무엇을 검증하는지 알고 있어야 한다.
