# 2026-09-04 — 제출 원고의 숫자를 전부 근거에 대조했다

## 왜 했나

앞 편(`grounded-law-check.md`)에서 지연 수치 하나가 **다른 계층의 값**이라는 것을
찾았다. 찾은 방법이 문제였다 — 새로 잰 값이 문서와 안 맞아서 **우연히** 걸렸다.

우연히 걸린 것이 하나라면 안 걸린 것이 몇인지는 아무도 모른다. `docs/38` 은
제출 원고이고, 심사자가 공개 URL 에서 직접 재현할 숫자들이다. 굵은 숫자를 전부
뽑아 근거 파일과 코드에 대조했다.

### 애매했던 것 — 판정 API 지연

문서값은 개발셋 p50 2.807ms / p95 3.979ms 인데 처음 재니 **p50 3.9 / p95 5.7ms**
가 나왔다. 세 번 돌려도 같았다.

회귀가 아니었다. **재는 자리가 달랐다.**

```
판정 로직만            p50 0.265ms   p95 0.560ms
서버 측 duration_ms    p50 2.223ms   p95 3.586ms   ← 문서값과 같은 자리
클라이언트 왕복        p50 3.9ms     p95 5.7ms     ← httpx 비용이 얹힌다
```

문서는 어느 쪽인지 적어 두지 않았다. **2.21초를 만든 것과 같은 종류의 빈칸**이라
`docs/32`·`docs/36` 에 세 줄을 적었다 — 서버 측 값이라는 것, 클라이언트로 재면
5ms 대가 된다는 것, 그리고 이 표의 대부분이 **엔진이 아니라 HTTP 계층**이라는 것.

p95 는 열세 회차 동안 4ms 아래에 머물러 있고, 재측정도 그 안이다.

## 한 번 잘못 결론 낼 뻔했다

시나리오 2 를 처음 재현했을 때 행동이 **5개 그대로** 나왔다. 문서는 9개라고
적혀 있으니 원고가 틀린 것처럼 보였다 — 그것도 **서비스의 축이라고 선언한 자리**가.

내 하네스가 틀렸다. `AnalyzeRequest` 의 필드 이름은 `state` 인데 `user_state=`
로 넘겼고, Pydantic 이 그것을 조용히 버리고 기본값 `received_only` 로 돌았다.

**재현이 실패했다는 것은 문서에 대한 주장이기 전에 내 하네스에 대한 주장이다.**
그 순서를 뒤집었으면 맞는 문서를 고쳐 놓고 고쳤다고 적었을 것이다.

## 안 한 것

- **배포 환경 측정.** 위 지연은 전부 개발기 in-process 값이다. 네트워크·TLS·
  프록시·동시 사용자가 빠져 있다.
- **문장 품질.** 이 편이 센 것은 건수·비율·등급이다. 화면에 나가는 문장이
  읽을 만한가는 여기서 재지 않았다.
- **엔진 수정.** 미탐 10건·오탐 6건은 그대로다. 이번 편은 재는 일만 했다.
