# 2026-09-04 — 세 태그가 밀려 있던 공개 URL 이 `v0.7.0` 이 됐다

## 무엇이 바뀌었나

같은 날 오전에 공개 URL 은 `v0.5.0` 이었다. `v0.6.0` 과 `v0.7.0` 은 이미지가
만들어져 ghcr 에 올라가 있었지만 VM 은 받은 적이 없었다. 재배포는 사람이 Cloud
Shell 에서 하는 일이라 이 PC 에서 할 수 없었고, 그래서 명령 묶음과 확인 절차만
넘겨 뒀다. 그것이 실행됐다.

바뀐 것은 `.env` 의 `FINSHIELD_IMAGE_TAG` 한 줄이다. `v0.5.0..main` 사이에
`migrations/`·`compose*`·`Dockerfile`·`Caddyfile`·`.env.example` 변경이 없다는
것을 미리 확인해 뒀고, 실제로 `migration-1` 은 할 일 없이 `Exited` 로 끝났다.

## 확인 — 프로브 세 개, 셋 다 통과

| 프로브 | 오전 (`v0.5.0`) | 지금 (`v0.7.0`) | 가리키는 경계 |
|---|---|---|---|
| 데모 문장 → `/explanation` | **`failed`** (4/4) | `ready` · `gemini-3.6-flash` · 263자 | `v0.6.0` 이상 ✅ |
| 관리비 문장 → `/explanation` | `not_asked` | `not_asked` | `v0.4.0` 이상 ✅ |
| 예방 안내문 → `/analyze` | **`medium` · 35점** | `low` · 0점 | `v0.7.0` 이상 ✅ |

1번은 3회 반복해 263·261·232자, 8.4~12.8초로 안정적이다. 같은 입력, 같은 URL,
같은 키다. **바뀐 것은 올라간 이미지 하나뿐이다.**

곁들여:

- 데모 문장 `/analyze` → `high` · 70점 · 신호 4 · 유형 3 · 행동 5 · 근거 3.
  로컬 `main` 과 값이 같다.
- `/` `200` 0.69초.
- `verify_public_deployment --domain finshield-ai.duckdns.org` → **27/27**,
  실패 0. 내부 포트 18000·13000·5432 전부 닫힘, CSP·HSTS·share target 헤더 유지.
- `$DC images` 의 IMAGE ID 가 `a140a7a49b91`(backend)·`c99bb50e1ede`(web) 로
  릴리스 대장의 digest 앞 12자리와 일치한다.

**태그가 아니라 digest 로 확인했다.** 태그는 옮겨 붙을 수 있고 digest 는 그렇지
않다. 세 번의 "안 올라간 태그" 가 전부 "태그를 밀었으니 배포됐겠지" 에서 나왔다.

## 배포 대장에 줄을 적은 순서

이번에는 **찍은 뒤에 적었다.** `v0.4.0` 줄은 2026-08-26 에 미리 적고 확인 칸을
`*(배포 후 채운다)*` 로 비워 뒀는데, 그렇게 하면 **배포가 빠진 줄과 확인만 아직
안 한 줄이 구분되지 않는다.** 그 구분이 없어서 아흐레를 놓쳤다. 대장에 계획을
적으면 대장이 하는 일이 없어진다.

## 프로브를 셋으로 늘린 것이 값을 했나

했다. 다만 이번에는 **틀린 것을 잡은 것이 아니라 맞은 것을 확정했다.**

셋 다 통과했다는 것은 세 개의 서로 다른 릴리스 경계를 각각 넘었다는 뜻이다.
하나만 찍었다면 "설명이 나온다" 까지는 알았겠지만 PR #117 이 고친 예방 안내문
결함이 남아 있는지는 알 수 없었다. 오전에 그것으로 한 번 틀렸고, 그 실수가
그대로 절차가 됐다.

## 남은 것

배포 쪽에서 할 일은 없다. 남은 것은 전부 사람이 하는 서류·설정이다 —
팀명·구성원 성명, Google Cloud 예산 알림과 일 상한, Gemini 키 IP 제한,
양식 작성과 PDF 변환, daker.ai 두 번 제출.

**심사 기간(2026-09-07 11:00 ~ 09-11 23:59) 동안 URL 이 죽으면 결격이다.**
예산 상한은 그 기간을 지키기 위한 것이지 비용을 아끼기 위한 것이 아니다 —
상한을 너무 낮게 잡으면 그 자체가 URL 을 죽인다.

**재배포 자동화는 여전히 안 한다.** 세 번 같은 일이 났으니 이유는 충분하지만,
접수 마감 사흘 전에 배포 경로를 새로 만드는 것은 고치는 것보다 깨뜨릴 확률이
높다. 백로그에 있다.
