# 넓히기 다섯을 한 번에 — held-out v0.8 과 값을 치를 자리

2026-08-23

## 한 줄

v0.7 이 이름으로 적어 둔 결함 일곱 건은 **거의 전부 어휘를 넓히는 수정**이다. 넓히기의
값은 정상 문장에서 치러지므로, 셋을 짤 때 정상 36건을 **각 넓히기가 깨질 수 있는
자리에 하나씩** 놓았다. 작업 중에 실제로 두 번 깨졌고, 두 번 다 어휘를 좁히는 대신
**구조적 원인**에서 고쳤다.

## 0. 왜 이번 회차가 위험했나

| 회차 | 수정의 방향 | 값을 치르는 자리 |
|---|---|---|
| v0.2~v0.5 | 넓히기 | 정상 문장 (오탐) |
| v0.6 | 좁히기 | 사기 문장 (미탐) |
| v0.7 | 올리기 | 정상 문장의 등급 (천장) |
| **v0.8** | **넓히기 5 + 좁히기 1** | **양쪽 다** |

동결 시점 baseline 이 precision 1.0000 / FPR 0.0000 이었다. **올라갈 자리가 없고
내려갈 자리만 있다.** 넓히기 다섯 개를 한 회차에 몰아 놓았으니 이 두 숫자는 이번
회차가 실패하면 반드시 움직인다.

그래서 정상 36건을 그룹별로 배치했다. A' 는 정상 권한 위임, B' 는 정상 돈 이동, C' 는
**진짜 예방 안내문**, D' 는 정상 기관·입금이다. C' 여섯 건은 유일한 좁히기(`드리지 않`)가
값을 치를 자리라서, 이 회차는 좁히기의 값도 정상 쪽에서 낸다.

## 1. held-out v0.8 (72건, fh-601~fh-672)

36 사기 / 36 정상. **정상 36건 전부가 천장을 선언한다** (`fh-645`·`fh-646` 만 medium,
나머지 34건 low).

세 개의 통합 테스트가 이 배치를 센다 — taxonomy·천장 규율, **다섯 넓히기가 각각 깨질
자리에 정상 문장이 있는지**, 좁히기가 양쪽에서 값을 내는지.

### 얼리기 전에 두 건의 라벨을 고쳤다

- `fh-643` 이 `transferred_money` 상태를 아무도 쓰지 않아 `_validate_collection` 이
  거부했다. 상태를 바꾸고 본문을 그에 맞게 다시 썼다.
- `fh-660` 이 `["money_mule", "money_transfer_request"]` 를 요구했다.
  `project_public_signals` 는 `receive_and_forward_money` 가 켜지면 공개 응답에서
  `money_transfer_request` 를 **일부러 뺀다.** API 가 절대 내보내지 않는 이름을
  요구하고 있었다. `["money_mule"]` 로 고쳤다.

**둘 다 측정 전이다.** 측정 후에 라벨을 고치면 그것은 채점표를 고치는 일이다.

### 그룹 C 가 처음에는 결함을 재현하지 못했다

`fh-523` 의 결함은 `말씀드리지 않` 이 문장 전체를 예방 안내문으로 누르는 것이다. 그런데
초안에 "저와만 연락 주세요" 라고 적었더니 `주세요` 가 억제를 풀어 버려서 baseline 에서
이미 잡혔다. 맨 명령형("저와만 연락하세요")으로 바꾸고 나서야 진짜 미탐이 됐다.

**셋이 결함을 재현하는지 동결 전에 확인해야 한다.** 재현하지 않는 사례는 수정의 값을
재지 못하고, 만점만 하나 더 얹는다.

## 3. 일곱 가지 수정

### 3-1. 예방 안내문 표지가 보조용언 자리를 넘어갔다 (`8243915`, 미탐 16→14)

`PREVENTION_STATEMENT_MARKERS` 의 맨 `"드리지 않"` 이 `말씀드리지`·`건드리지` 를 함께
잡았다. 보조용언 구성이 아니라 한 낱말인데도. **읽는 사람에게** 말하지 말라는 요구가
보내는 쪽의 서술로 읽혔다.

```python
PREVENTION_STATEMENT_PATTERNS = (
    re.compile(r"(?:^|[\s,·\"'()\[\]])드리지\s*않"),
    re.compile(r"(?:해|려|어|아|워)\s*드리지\s*않"),
)
```

어간이 아니라 **앞자리**를 본다. `안내드리지 않으며` 처럼 놓치는 것이 있지만 그런
문장은 다른 표지를 함께 달고 있고, 놓치는 방향이 억제를 **덜** 하는 쪽이라 안전한
실패다.

**이 수정이 오탐 하나를 만들었다.** `fh-632`("OTP를 대신 입력해 드리지 않습니다")가
high 로 올라갔다. 원인은 `_demanding_clauses` 도 같은 표지 목록으로 절을 거른다는
것이다 — 표지를 빼자 그 예방 절이 요구를 공급하게 됐다(`입력` 이 요구 표지다).
정규식을 `_demanding_clauses` 에도 걸어 고쳤다. **C' 여섯 건이 정확히 이걸 잡으려고
있었다.**

### 3-2. 계좌 권한을 사람에게 넘기라는 요구 (`3bc57f6`, 미탐 14→9)

`fh-508` 은 신호가 **하나도** 안 켜졌다. `세무서` 자칭은 다른 민감 요구가 있어야
켜지고, `계좌 접근 권한` 은 어느 어휘에도 없었다. **두 게이트가 서로를 기다렸다.**

`SignalRule` 에 `demand_gated_sequences` 를 더했다. 낱말 하나에 담기지 않고 사이에
다른 말이 끼는 요구를 순서로 본다.

```python
_ACCOUNT_AUTHORITY_TERMS = ("계좌", "뱅킹", "통장")
_AUTHORITY_HANDOVER_TERMS = ("에게 위임", "쪽으로 위임", "에게 양도", "넘겨", "넘기")
ACCOUNT_AUTHORITY_SEQUENCES = tuple(
    (account, "권한", handover)
    for account in _ACCOUNT_AUTHORITY_TERMS
    for handover in _AUTHORITY_HANDOVER_TERMS
)
```

권한 위임 자체는 정상 제도다. 신호는 위임이 아니라 그 권한을 **누구에게** 넘기라는
요구이고, 그래서 수령자 표현을 어휘에 함께 넣었다. "영업점에서 위임장을 제출하셔야
합니다"(A')에는 수령자가 없다.

열다섯 조합을 손으로 적지 않고 곱했다. 손으로 적으면 하나가 조용히 빠지고, 빠진 것을
알아차릴 방법이 없다.

### 3-3. 재전달 요구의 구멍 셋 (`304f418`, 미탐 9→3)

세 가지를 한 커밋에 넣었다. 셋 다 같은 규칙의 같은 조건이라 따로 재면 서로의 값을
가린다.

- `MONEY_OBJECT_TERMS` 에 `정산금` (`fh-539`)
- `money_gated_keywords` 에 `돌려보내`·`나눠 보내` (`fh-542`·`fh-543`)
- `MONEY_DESTINATION_TERMS` 를 목적어의 **대안**으로 (`fh-542` — 돈을 가리키는 말이
  완료 보고 절에 들어가 걸러졌다)

**이 수정도 오탐 하나를 만들었다.** `fh-625`("회비는 나눠 보내지 마시고 총무 계좌로 한
번에 보내 주세요")가 money_mule 로 올라가 천장까지 넘었다. 같은 문장이 그 행동을
**하지 말라고** 하고 있다.

어휘를 좁혀서 피하지 않았다. `"나눠 보내 주"` 처럼 어미를 붙여 적으면 그 어미만 잡고
다음 회차에 다른 어미로 다시 뚫린다. 금지형은 어휘의 문제가 아니라 **자리의 문제**다.

```python
PROHIBITION_ENDINGS = ("지 마", "지말", "지 말")
```

그 동사의 **모든** 출현이 금지 어미를 달고 있을 때만 건너뛴다. `-지 않` 은 일부러
넣지 않았다 — "보내지 않으면 계좌가 정지됩니다" 는 협박이고 요구의 다른 얼굴이다.

### 3-4. 지검도 사칭당한다 (`5946595`)

`authority_impersonation` 의 **조건부** 어휘에 `지검` 을 넣었다. 무조건 목록이 아니다 —
다른 민감 요구가 같은 메시지에 있어야 켜진다.

### 3-5. 높임 명령형도 요구다 (`202c5c1`, 미탐 3→0)

`입금하셔`·`송금하셔`·`이체하셔`. "먼저 이체하셔야 처리됩니다" 는 부탁 어미도 반말
어미도 아니라서 어느 목록에도 걸리지 않았다.

### 3-6. high 판정이 0점과 함께 나가지 않는다 (`6034290`)

`risk_score` 는 `LEGACY_RULES` 의 가중치만 더하고, `risk_level` 은 canonical 신호와
사용자 상태까지 본다. 그래서 **화면에 "높음" 과 "0점" 이 나란히** 실렸다. v0.7 이
이름으로만 적어 두고 미룬 것이다.

등급을 점수에서 다시 계산하는 방향은 택하지 않았다. 그러면 여섯 회차에 걸쳐 쌓은
canonical 판단과 상태 하한이 전부 legacy 가중치 표로 되돌아간다. **점수를 등급이
함의하는 띠까지 올린다** (high 70, medium 35). 점수는 등급의 근거가 아니라 등급을
거스르지 않는 표시값이 된다.

바닥은 `determine_risk_level` 이 돌려준 **뒤에** 깔린다. 순서가 뒤집히면 상태가 올린
등급이 자기 근거를 만들어 낸다.

`determine_risk_level` 은 점수 띠에서 출발해 **올리기만** 하므로 `점수 띠 <= 등급` 은
원래도 성립했다. 바닥을 깔면 반대 방향도 성립해서 둘이 정확히 같아진다. 그 불변식을
작은 코퍼스 위의 테스트로 못 박았다.

`test_legacy_baseline_exact_scores` 는 이제 API 를 거치지 않고 채점기를 직접 부른다.
그 표가 못 박으려는 것은 `LEGACY_RULES` 의 가중치이지 응답에 실리는 숫자가 아니었다.

### 3-7. 목적지 계좌 하나가 돈 이야기를 만들지 않는다 (`55a3a2d`)

**옛 셋 재측정이 잡아낸 회귀다.** 3-3 이 목적지를 목적어의 대안으로 들이자 v0.5
`fh-317`("계좌가 묶였어. 일단 안전계좌로 옮겨 놔")이 자금 재전달 요구가 됐다.

받은 돈이 없다. 피해자 제 돈을 옮기라는 안전계좌 이체 요구다. 이진 판정과 등급은 둘 다
그대로라서 움직인 지표는 필수 signal coverage 하나뿐이었다(1.0 → 0.9836). 손해는
**이름**에 있다 — `money_transfer_request` 가 `money_mule` 이 되면 사용자에게 나가는
행동이 "받은 돈을 보내지 마세요" 로 어긋난다. 아무것도 받지 않은 사람에게.

목적지를 들인 이유(`fh-542` — 돈을 가리키는 말이 걸러진 절에 있다)는 그대로 유효하다.
절이 걸러졌을 뿐 메시지에는 남아 있다. 그래서 조건을 절이 아니라 **메시지 전체**에
걸었다. 넓힌 자리는 그대로 두고, 목적지 하나로 돈 이야기를 **만들어 내는** 것만 막는다.

| `fh-638` | 유형 과다 | `대포통장으로 등록되어` 의 `통장` 이 `account_access_request` 의 조건부 어휘를 채운다. **고발 문구이지 요구 대상이 아니다** |
| `fh-657` | 유형 과다 | `기존 체크카드는 배송 기사에게 전달해 주세요` → `account_access_request`. 이건 엔진 쪽이 맞을 수 있다. 라벨을 다시 봐야 한다 |
| `fh-603`·`fh-627`~`fh-629`·`fh-631` | action 누락 | `isolation_coercion` 이 medium 에서 `VERIFY_BY_KNOWN_CONTACT` 를 선택하지 않는다. 고립 요구에 가장 필요한 행동이 **아는 창구로 확인하기**인데 |
| `fh-663` | 등급 미달 | 위협 + 통장·체크카드 전달 요구인데 medium 에서 멈춘다. 기관 자칭이 없어 high 조합이 켜지지 않는다 |

이 회차의 이진 판정은 만점이고, 남은 결함은 **이름과 행동과 등급** 쪽에 있다. 다음
회차가 볼 자리가 옮겨 갔다.

### 이번 회차 밖으로 미룬 것

- **판정 프롬프트.** 프롬프트 밖 유형이 여전히 넷이다. 고치면 sha256 이 바뀌어 유료
  판정 결과의 출처가 끊긴다. `llm_only` 를 비교표에 쓸 때는 프롬프트 버전을 함께 적는다.
- **`대환 대출`(띄어쓰기)** 이 `loan_policy_offer` 어휘에 없다. `대환대출` 만 있다.
