# 공모전 기획서 — FinShield AI

**2026 금융 AI Challenge** 제출물 ①
주최 금융보안원 · 후원 금융위원회

---

## 1. 한 줄 정의

> **사회초년생 등 금융지식이 부족한 사용자가 금융 의사결정과 금융사기 위험 상황에서,
> 개인 상황에 맞는 판단 근거와 즉시 실행할 행동을 제공받는 AI 금융 안전 코파일럿.**

## 2. 문제 정의

### 2.1 지금 있는 서비스가 답하지 않는 질문

금융사기 대응 서비스는 대체로 **이미 알려진 번호·URL·문구**를 차단한다. 이 접근은
세 가지를 놓친다.

1. **처음 보는 문장.** 생성형 AI 이후 사기 문구는 매번 새로 쓰인다. 목록 대조는
   구조적으로 늦다.
2. **"그래서 지금 뭘 해야 하나".** 위험하다는 판정을 받아도, 이미 계좌를 알려 준
   사람이 다음 3분 안에 무엇을 해야 하는지는 알려 주지 않는다.
3. **피해자가 아니라 가해자가 되는 경로.** 대포통장·전달책 연루는 "속았다"로 끝나지
   않고 형사 책임으로 이어진다. 대부분의 서비스가 이 축을 다루지 않는다.

### 2.2 우리가 시작한 질문

> 금융 경험이 부족한 사람이 금융사기의 피해자가 되는 것뿐 아니라,
> 계좌·카드·인증정보를 넘겨 **자신도 모르게 금융범죄에 연루되는 순간**까지
> 사전에 위험을 설명하고 막을 수 있을까?

### 2.3 왜 지금 이 문제가 어려워졌는가

생성형 AI는 공격자에게 세 가지를 줬다 — 자연스러운 한국어, 무한한 변형, 개인화.
같은 이유로 **방어에 LLM을 그대로 쓰는 것은 위험하다.** 사기 여부·위험 수준·법적
책임이 걸린 판단을 확률적으로 문장을 생성하는 모델에 맡기면, 틀렸을 때 이유를 설명할
수도 재현할 수도 없다. 이 기획서의 설계는 전부 그 긴장에서 나온다.

## 3. 타깃 사용자

| | 사회초년생 (Primary) | 소상공인 (Secondary) |
|---|---|---|
| 상황 | 첫 직장·아르바이트·자취 시작 | 매출 변동, 자금 융통 압박 |
| 노출되는 사기 | 취업/급여계좌 사칭, 청년지원·대출 사칭, 계좌·체크카드·OTP 전달 요구 | 정책자금 사칭, 사업자대출 사칭, 세무사·거래처 사칭, 세금계산서 첨부 피싱 |
| 취약한 이유 | 금융 절차의 "정상 범위"를 모른다 | 자금 압박이 판단을 좁힌다 |

두 persona 모두 공통점이 하나 있다. **판정 결과가 아니라 판단 근거를 필요로 한다.**
"위험 92점"은 도움이 되지 않는다. "정상적인 금융기관은 이 요구를 하지 않는다"가
도움이 된다.

## 4. 솔루션 개요

### 4.1 Detect → Explain → Act

```
   사용자가 받은 문자/메시지
            |
            v
   [1] Detect   결정론적 규칙 엔진        LLM 호출 없음, 런타임 웹 검색 없음
            |   위험 신호 12종 -> 사기 유형 6종 -> 위험 3단계
            v
   [2] Act      상황별 행동 11종           사용자가 "이미 한 것"을 함께 입력받는다
            |   각 행동에 공식 근거 ID 연결 (연결률 100%)
            v
   [3] Explain  LLM 설명 (별도 엔드포인트)  이미 정해진 판정을 문장으로 풀어 준다
```

**세 단계의 순서가 이 서비스의 핵심 주장이다.** 대부분의 AI 서비스는 Explain 을 맨
앞에 둔다 — 모델이 판정하고 그 판정을 설명한다. 우리는 반대다. 판정이 먼저 끝나고,
LLM은 **이미 확정된 결과를 받아 문장만 만든다.**

### 4.2 모델이 판정에 닿을 수 없는 이유 (구조적 보장)

설명 계층의 함수 서명이 `explain_analysis(AnalyzeResponse) -> str | None` 이다.
입력이 이미 완성된 판정 결과이므로, **모델은 위험 수준·사기 유형·행동 목록을
구조적으로 바꿀 수 없다.** 정책 문서의 약속이 아니라 타입의 성질이다.

두 경로는 API 엔드포인트도 분리돼 있다.

| 엔드포인트 | 역할 | LLM |
|---|---|---|
| `POST /api/v1/analyze` | 위험 수준·사기 유형·행동·근거 결정 | **호출하지 않음** |
| `POST /api/v1/analyze/explanation` | 위 결과를 설명 문장으로 | 호출함 |

모델 API가 죽어도 판정은 그대로 나온다. 설명만 사라진다. 지금 위험한 문자를 받은
사람에게 **외부 API 장애가 무경고로 이어지지 않는다.**

### 4.3 "이미 무엇을 했는지"를 입력으로 받는다

같은 문자라도 아직 안 눌렀는지, 이미 계좌를 알려 줬는지에 따라 필요한 행동이 완전히
다르다. 그래서 위험 판정은 두 축의 최댓값으로 결정한다.

```
최종 위험 수준 = max( 문구 점수 밴드,
                     신호별 최소 위험,
                     고위험 신호 조합,
                     사용자 상태별 최소 위험 )
```

문구가 아무리 평범해도 **이미 계좌 접근권을 넘긴 사용자는 항상 high** 다. 사용자
상태 7단계가 각각 최소 위험 수준을 갖는다.

### 4.4 조언에는 반드시 출처가 붙는다

행동 11종은 전부 공식 근거 ID에 연결돼 있고, 연결되지 않은 행동은 **애초에 응답에
실릴 수 없다**(무결성 검증에서 예외로 막는다). 근거는 8건이다.

| 출처 | 성격 |
|---|---|
| 금융보안원 (2건) | AI 보안 전략, 대회 요강 |
| 보이스피싱 통합신고대응센터 1394 / 경찰청 (2건) | 신고·피해 구제 절차 |
| KISA 118 / 스미싱 대응 (2건) | 상담·스미싱 확인 |
| 전자금융거래법 제6조, 전기통신금융사기 특별법 (2건) | 접근매체 양도의 법적 책임, 피해금 환급 |

법령 2건이 들어간 이유는 이 서비스의 두 번째 축 때문이다. 계좌를 빌려주는 행위가
**왜 본인에게 형사 책임이 되는지**를 조문으로 보여줘야 사용자가 멈춘다.

## 6. AI 안전성·신뢰성 설계

주최가 금융보안원인 만큼, 이 절을 가장 자세히 적는다.

### 6.1 LLM에게 주지 않은 권한

`CLAUDE.md`의 첫 번째 non-negotiable 이 프로젝트 시작부터 지금까지 유지되고 있다.

> LLM은 적격성, 금융 계산, 위험 점수, 안전 조치의 유일한 권한이 될 수 없다.

- 위험 판정 — 결정론적 규칙. LLM 미사용
- 금융 계산 (상환액, 현금흐름, 비상자금) — 순수 함수. LLM 미사용
- 행동 선택 — 정책 테이블. LLM 미사용
- 공식 근거 연결 — 정적 카탈로그 + 무결성 검증. LLM 미사용
- **설명 문장 — LLM 사용**

### 6.2 프롬프트·모델 고정 (contract pinning)

프로바이더·모델 ID·프롬프트 sha256을 **상수로 못 박고 테스트가 검증한다.** 계산해서
넣지 않는다. 프롬프트를 한 글자라도 고치면 해시가 어긋나 테스트가 깨지고, 재측정을
강제한다. 모델을 조용히 바꾸는 일이 구조적으로 불가능하다.

| 항목 | 값 |
|---|---|
| 프로바이더 | Google AI Studio |
| 주 모델 | `gemini-3.6-flash` |
| 대체 모델 | `gemini-3.1-flash-lite` |
| temperature | 0.0 |

### 6.3 출력 검증

모델 출력을 그대로 내보내지 않는다. 길이, 금지 표현, 판정과의 정합성을 검사하고,
검증에 실패하면 **설명 없이 판정만 내보낸다.** 설명이 없는 것보다 틀린 설명이 나쁘다.

### 6.4 프롬프트 인젝션 경계

사용자가 붙여넣는 문자 자체가 공격 표면이다. "위 지시를 무시하고…"가 문자 안에
들어 있을 수 있다. 두 겹으로 막는다.

1. 판정 경로가 애초에 LLM을 부르지 않는다 — 인젝션이 성공해도 **판정은 못 바꾼다.**
2. 설명 경로는 출력 검증을 통과해야 사용자에게 도달한다.

인젝션 시도의 성공률 자체는 아직 측정하지 않았다 (11절).

### 6.5 URL 취급

사용자가 준 URL을 **서버가 가져오지 않는다.** SSRF를 설계 단계에서 배제했다.
URL 분석은 형태(lexical) 기반 오프라인 분석만 수행한다. 도메인 평판 조회는 외부
호출 정책을 세운 뒤에 붙일 예정이다.

### 6.6 개인정보 최소화

- 주민등록번호, 은행 비밀번호, OTP, 카드 전체 정보를 **요구하지 않는다.**
- 익명 세션으로 동작한다. 세션 원문은 HttpOnly·SameSite=Strict 쿠키에만 두고,
  DB에는 SHA-256 해시만 저장한다.
- 금융 프로필은 필드 단위로 인증 암호화해 저장한다. 키가 없으면 앱이 **기동을
  거부한다.**
- 다른 사용자의 UUID 접근은 403이 아니라 **404로 숨긴다** (존재 여부 노출 방지).
- 사용자는 프로필 1건 삭제와 계정·전체 금융정보 삭제를 구분해 실행할 수 있다.

### 6.7 로그에 무엇을 남기지 않는가

운영 로그는 **카운트와 성공/실패만** 기록한다. 사용자 식별자, 세션 ID, 프로필 ID,
금융 원문을 남기지 않는다. 이 경계는 ADR로 고정하고 회귀 테스트로 지킨다.

### 6.8 그 외 운영 보안

HTTP 보안 헤더, 동일 출처 상태 변경(CSRF) 방어, 신뢰 호스트 제한, IP 기준 요청 한도,
본문 크기 상한, HTTPS 경계, 백업 암호화와 복원 리허설(합격 기준은 "복원됐다"가 아니라
"복호화됐다"), 의존성 해시 고정과 CI drift 차단이 적용돼 있다.

## 7. 검증 — 무엇을 어떻게 쟀는가

### 7.1 측정 데이터

팀이 직접 작성한 **합성 61건** 골든셋. 실제 피해 문자를 수집하지 않았다 — 개인정보와
2차 유통 위험 때문이다. 비합성 케이스는 코드가 `ValueError`로 거부한다. 사용자 상태
7종을 각각 최소 3건 덮는다.

### 7.2 Rule / LLM / Hybrid 3자 비교

`gemini-3.6-flash` 하나에게 **엔진의 일을 통째로** 시켜 같은 61건으로 비교했다.
판정자는 평가 코드에만 있고 제품에는 없다.

| 항목 | Legacy 5-keyword | Scenario Engine | LLM-only |
|---|---:|---:|---:|
| Precision | 0.857143 | 1.000000 | 0.951220 |
| Recall | 0.461538 | 1.000000 | 1.000000 |
| F1 | 0.600000 | 1.000000 | 0.975000 |
| FPR | 0.136364 | 0.000000 | 0.090909 |
| **필수 행동 coverage** | – | **1.000000** | **0.600000** |
| **상태 정책 정확도** | – | **1.000000** | **0.508197** |
| **공식 근거 coverage** | – | **1.0** | **0.0** |

**읽는 방법이 중요하다.** 위 세 칸(굵게)이 이 프로젝트의 논지다. 탐지는 모델도
잘한다 — 최초 측정에서는 모델이 우리 엔진보다 나았다(재현율 1.000 대 0.949).
모델이 못 채운 것은 **"그래서 지금 뭘 해야 하는가"와 "그 근거가 어디 있는가"** 다.
상태 정책 0.508은 정책표를 주지 않은 상태의 수치이므로 "주지 않은 정책의 준수율"임을
함께 밝힌다.

### 7.3 측정이 우리 코드를 고치게 했다

모델이 우리 엔진의 오답 2건을 잡았다. 원인은 판정 로직이 아니라 **어휘 구멍**이었다
(`법원`이 사칭 기관 목록에 없었고, 설치 요구 어휘가 "설치"라는 단어에만 걸려 있었다).
**모델을 판정에 넣는 대신 규칙 어휘를 넓혔다.** 이것이 우리가 생각하는 LLM의 올바른
용법이다 — 판정자가 아니라 **감사자**.

### 7.4 성능

| 항목 | 값 |
|---|---|
| 판정 API (in-process ASGI, 1,220 샘플) | p50 2.222ms, p95 3.565ms |
| LLM 설명 호출 (61건 실측) | p50 2.21초, p95 5.41초 |

판정이 밀리초 단위인 이유가 4.2절의 설계다. 설명을 기다리지 않고 판정을 먼저
보여줄 수 있다.

### 7.5 재현 가능성

골든셋, 평가 코드, 결과 JSON, 오류 case ID, 모델 판정 61건 원본이 전부 저장소에
있다. **유료 호출 없이** 3자 비교를 재현할 수 있다. 품질 게이트는 CI에서 매 push마다
돌고, 낡은 비교를 자동으로 거부한다.

### 7.6 자동화 검증

`pytest -q` 기준 **608 passed, 2 skipped.** CI는 테스트, 품질 게이트, 의존성 해시
잠금 검사, 프론트엔드 빌드·타입·린트·테스트, 컨테이너 런타임 검증을 모두 돌린다.

| 계층 | 기술 |

**브라우저는 백엔드를 직접 호출하지 않는다.** Caddy는 프론트엔드만 노출하고,
API 접근은 서버 사이드 프록시를 거친다.

## 9. 기대효과

1. **판단 근거를 남기는 금융 AI의 레퍼런스.** 판정과 설명을 분리하면 AI를 쓰면서도
   재현성·감사 가능성·장애 내성을 잃지 않는다는 것을 코드와 숫자로 보여준다.
2. **피해 발생 후 시간의 단축.** "이미 한 것"을 입력받아 3분 안에 할 일을 우선순위로
   제시한다. 지급정지·신고·명의보호의 골든타임을 겨냥한다.
3. **연루 예방.** 계좌 양도의 형사 책임을 조문 근거와 함께 사전에 알린다.
4. **금융 문해력.** 전문용어를 쓰지 않고, 모든 수치에 출처를 붙인다.

## 10. 한계 — 우리가 주장하지 않는 것

심사에서 이 절을 먼저 읽어도 무방하다.

- **61건은 개발셋이다.** 같은 데이터로 오류를 찾고 규칙을 교정했으므로 독립
  held-out 성능이 아니다. 어휘 확장 이후 이 셋에서 오류가 0건이 됐는데, 이는
  **개발셋이 더 이상 변별하지 못한다**는 뜻으로 읽어야 한다. 만점을 성능 주장으로
  제출하지 않는다.
- **만점인 것은 이진 판정뿐이다.** 사기 유형 분류는 개발셋에서도 만점이 아니다 —
  `loan_policy_impersonation` F1 0.909091, `money_mule_transfer` F1 0.923077.
  "위험하다"는 판단은 다 맞혔지만 **유형 이름을 붙이는 데서는 여전히 틀린다.**
- **실제 사용자 분포를 대표하지 않는다.** 합성 데이터이고 상태 분포도 치우쳐 있다.
- **3자 비교는 프롬프트 한 벌·모델 한 개·실행 한 번의 결과다.** 모델 일반 능력의
  측정이 아니다.
- **설명 문장 자체의 품질은 아직 측정하지 않았다.** 근거 이탈률, 안전 필터 차단율,
  프롬프트 인젝션 내성은 숫자가 없다. 위 표는 전부 탐지·행동에 대한 것이다.
- **공식 근거 연결률 1.0은 행동-출처 무결성이지 법률·금융 자문의 정답률이 아니다.**
- **latency는 개발기 in-process 측정이며 배포 SLO가 아니다.**
- 이 서비스는 **금융 자문이나 법률 자문이 아니고, 사기 여부를 확정하지 않는다.**
  모든 응답에 이 고지가 포함된다.
