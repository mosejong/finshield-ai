# 24. 익명 세션·금융 프로필 데이터 생명주기

## 목적

익명 사용자가 저장한 금융 프로필을 직접 삭제할 수 있게 하고, 접근할 수 없게 된 만료 세션의 데이터를
운영자가 안전하게 정리한다. 로그아웃과 개인정보 삭제를 서로 다른 행위로 취급하며 삭제 작업은 금융
원문이나 사용자 식별자를 로그에 남기지 않는다.

## 사용자에게 보이는 두 삭제

| 동작 | 범위 | 복구 |
| --- | --- | --- |
| `입력한 내용 지우기` | 현재 사용자의 FinancialProfile 1건 | 불가 |
| `익명 사용자와 모든 데이터 삭제` | 현재 익명 사용자, 모든 세션, 소유한 모든 FinancialProfile | 불가 |

`DELETE /api/v1/auth/session`은 현재 세션만 폐기하는 내부 계약이다. 프로필을 삭제하지 않으므로 공개 UI의
개인정보 삭제 버튼으로 사용하지 않는다. 익명 계정에는 이메일·전화번호 같은 복구 수단이 없기 때문에 세션
쿠키를 잃거나 계정을 삭제하면 기존 데이터에 다시 접근할 수 없다.

## API와 트랜잭션 경계

- `DELETE /api/v1/auth/account`: 현재 쿠키를 인증한 뒤 소유 프로필 전체와 익명 사용자·세션을 삭제하고
  세션 쿠키를 만료시킨다.
- profile 삭제가 먼저 완료된 후 사용자 삭제를 수행한다. 두 저장소 작업 사이에 장애가 생겨도 금융정보가
  남는 방향보다 먼저 지워지는 방향을 선택한 privacy-first 경계다.
- SQL 저장소에서 사용자 삭제는 `users → auth_sessions`, `users → financial_profiles` 외래키 cascade를
  사용한다. 서비스는 사용자 소유 프로필을 먼저 명시적으로 삭제해 저장소 경계를 문서화한다.
- 실패 응답은 내부 DB·키·식별자를 숨긴 일반화된 `503`이다.

## 만료 데이터 정리

정리 대상은 현재 시각 기준으로 활성 세션이 하나도 없는 익명 사용자다. 만료 세션 하나가 있어도 같은
사용자에게 다른 활성 세션이 있으면 삭제하지 않는다. 함께 닫힌 rate limit window 행도 지운다. 삭제 순서는
만료 세션 → 소유 프로필 → rate limit 카운터이며, 개인정보를 먼저 지운다. 뒤 단계가 실패해도 보존기간
약속은 이미 지켜져 있어야 하기 때문이다.

### 자동 실행 (2026-08-15부터)

compose의 `retention` 서비스가 `scripts/run_retention_scheduler.py`를 상주 실행한다. 주기는
`FINSHIELD_RETENTION_INTERVAL_SECONDS`이며 기본 1시간, 허용 범위는 60초~24시간이다. 기동 직후 한 번
실행한 뒤 주기를 센다. 배포 직후 한 주기를 기다리면 그동안은 보존기간이 지켜지지 않는 상태가 된다.

실행 결과는 한 줄 JSON 로그로 남는다. 성공은 건수 4종과 소요시간, 실패는 **예외 타입만** 남긴다. 예외
메시지는 기록하지 않는다 — SQLAlchemy가 실패한 문장과 바인딩 값을 메시지에 붙이기 때문에, 그대로 남기면
정리 로그가 개인정보 유출 경로가 된다.

실패는 컨테이너 healthcheck로 드러난다. **성공한 실행만** heartbeat 파일에 시각을 쓰고, healthcheck는 그
시각이 `주기 × 2 + 60`초보다 오래됐으면 unhealthy를 낸다. 프로세스가 살아 있는지를 보지 않는 이유는
계속 실패하는 loop도 살아 있기 때문이다.

```powershell
# 컨테이너 밖에서 상태만 확인 (DB에 접근하지 않는다)
.\.venv\Scripts\python.exe -m scripts.run_retention_scheduler --check-heartbeat
```

### 수동 실행

정리 명령은 기본이 미리보기이며, `--execute`를 명시해야 실제 삭제한다. 스케줄러와 같은 `RetentionRunner`를
쓰므로 미리보기 건수와 실제 삭제 건수가 갈라지지 않는다.

```powershell
# 삭제 예정 건수만 출력
.\.venv\Scripts\python.exe -m scripts.cleanup_expired_anonymous_data

# 만료 데이터 삭제
.\.venv\Scripts\python.exe -m scripts.cleanup_expired_anonymous_data --execute
```

실행 결과는 만료 세션, 대상 익명 사용자, cascade 대상 FinancialProfile, rate limit 카운터 건수와 실제
실행 여부만 JSON으로 출력한다. 사용자 UUID, 세션 해시, 프로필 UUID, 금융 원문은 출력하지 않는다.

`DATABASE_URL`이 필요하다. 없으면 exit 2로 거부한다. in-memory 저장소를 상대로 0건을 세고 끝나면
"지울 것이 없다"와 "아무 데도 안 봤다"가 출력만으로는 구분되지 않는다. 저장소 오류는 exit 1이며, 대개
migration이 올라가지 않은 DB를 가리키고 있는 경우다.

## 보존 정책

- 활성 익명 세션: 설정된 `AUTH_SESSION_TTL_SECONDS`까지 유지한다. 기본값은 30일이다.
- 만료 후: 다음 정리 주기(기본 1시간 이내)에 익명 사용자와 소유 데이터 전체를 삭제한다. 별도의 장기 유예
  보존은 하지 않는다. 현재 제품에는 본인 확인이나 복구 수단이 없어 유예 보존이 사용자 복구로 이어지지
  않기 때문이다.
- 서버 로그: 사용자·세션·프로필 ID와 금융 원문을 기록하지 않고 집계와 요청 상태만 남긴다.

## 백업과 삭제 한계

온라인 DB에서 삭제해도 이미 생성된 암호화 백업·WAL에는 정해진 보존기간 동안 과거 암호문이 남을 수 있다.
따라서 운영 배포 전 백업 보존기간, 접근권한, 파기 절차를 정하고 복원된 DB에도 만료 정리 작업을 즉시
실행해야 한다. 현재 기능은 백업 파일 내부의 선택적 레코드 삭제를 보장하지 않는다.

## 검증 기준

- 미리보기는 DB를 변경하지 않는다.
- 활성 세션이 있는 사용자는 보존한다.
- 만료 세션만 가진 사용자의 세션·프로필은 함께 삭제한다.
- 계정 삭제 후 기존 쿠키는 401이며 DB의 사용자·세션·프로필 행은 남지 않는다.
- 프론트는 서버 삭제 성공 뒤에만 로컬 profile identity를 지운다.
- 삭제 응답과 정리 로그에 금융정보·토큰·식별자를 포함하지 않는다.
- 정리가 실패하면 heartbeat가 갱신되지 않고 `retention` 컨테이너가 unhealthy로 떨어진다. 성공 로그만으로
  판단하지 않는다.

상세 결정 근거는 `docs/adr/0004-anonymous-data-lifecycle.md`를 따른다.
