# ADR 0003: 익명 세션과 FinancialProfile 소유권

- 상태: Accepted
- 결정일: 2026-08-13
- 범위: 브라우저 인증, FinancialProfile 접근 제어

## 배경

암호화 DB 저장은 평문 노출 위험을 줄였지만 profile UUID를 아는 요청자를 구분하지 못했다. UUID는
비밀 인증 수단이 아니므로, 이 상태에서는 다른 사용자의 profile을 조회·교체·삭제할 수 있다. 한편 MVP에
이메일·비밀번호 계정을 도입하면 개인정보 수집, 인증 메일, 비밀번호 복구와 운영 범위가 크게 늘어난다.

## 결정

1. MVP는 개인정보를 받지 않는 익명 사용자 UUID와 불투명 세션 토큰을 사용한다.
2. 토큰은 `secrets.token_urlsafe(32)`로 발급하고 브라우저의 HttpOnly·SameSite Strict 쿠키에만 둔다.
3. DB에는 토큰 원문이 아니라 SHA-256 해시만 저장한다.
4. 배포 환경 쿠키에는 `Secure`를 강제하며 세션 기본 수명은 30일이다.
5. 모든 profile CRUD와 metrics query는 인증 사용자 ID를 함께 조건으로 사용한다.
6. 타 사용자 접근은 존재하지 않는 ID와 같은 404로 처리한다.
7. 기존 owner 없는 row는 자동 귀속하지 않는다. 안전한 마이그레이션 근거가 없기 때문이다.
8. 브라우저는 Next same-origin 프록시를 사용하고, 프록시는 FinShield 세션 쿠키만 백엔드로 전달한다.

## 대안

- profile UUID를 bearer secret로 사용: 브라우저 저장소 노출과 공유·로그 유출에 취약하고 소유권 모델이
  없어 기각했다.
- 이메일·비밀번호 계정: 장기적으로 필요할 수 있으나 현재 개인정보와 복구 운영 범위를 초과해 보류했다.
- JWT 원문 저장: 즉시 폐기·서버 상태 확인과 최소 공개 payload가 필요한 현재 구조에서 이점이 작고,
  브라우저 토큰 노출 위험을 줄이지 못해 선택하지 않았다.

## 결과

- 장점: 개인정보 추가 수집 없이 사용자 간 profile 격리, DB 유출 시 세션 원문 비노출, 기존 API의
  금융 데이터 계약 유지.
- 비용: DB 조회가 필요한 stateful 인증, 쿠키 삭제 시 익명 profile 복구 불가, 만료 데이터 정리 정책
  필요.
- 한계: XSS·TLS 종료·운영자 권한·secret 유출을 단독으로 해결하지 않는다. 정식 공개 전 보안 헤더,
  계정 전환과 삭제·보존 정책이 필요하다.
